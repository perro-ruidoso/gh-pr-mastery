Located, Specific, Severity-Marked

A review comment the author can act on without asking a question has three properties: it says where, it says what and why with the source, and it says how much it matters. This page takes the five comments actually submitted on PR #15 apart against those three properties, and rewrites two of the findings from M21 as comments that fail them — so you can see the difference in the same words.

The test: could the author start typing?

Read a comment as its recipient. If the first thing they would have to do is reply with a question — "which line?", "what should it be instead?", "is this blocking?" — the comment has failed, however correct it is. Each of the three properties closes one of those questions:

PropertyCloses the questionWhat it looks like
Located"Where?"An inline comment on the line (or range) that has to change — not a Conversation comment that describes the line. If the line is not in the diff, anchor to the nearest one that is and say so.
Specific"What, and why?"The rule being broken, quoted or cited so the author can read it; the concrete consequence (a value, an exception, a wrong day); and the change that would fix it — as a suggestion block when it is one line.
Severity-marked"Do I have to?"The first word: must-fix, nit, or a question mark you own. The author can plan their afternoon from the first words of each thread.

Google's reviewer guide (practitioner material, fetched 2026-09-14) gives the same shape from the other side: "Explain your reasoning", "Balance giving explicit directions with just pointing out problems and letting the developer decide", and "Consider labeling the severity of your comments, differentiating required changes from guidelines or suggestions" — because "without comment labels, authors may interpret all comments as mandatory, even if some comments are merely intended to be informational or optional."

The five comments on PR #15, dissected

As submitted in the batched review (M19 page 2), each is checked against the three properties. Line numbers are those of the planted head b0fac63.

scheduler.py line 45 (RIGHT) — the early clamp

must-fix — ADR 0001, Ease Factor: "the update is applied first and the 1.3 floor is applied after, never before." This clamps before the update on line 53, so a grade of 3 from 1.3 yields 1.16 — which Card.__post_init__ then rejects with ValueError. Nine consecutive grade-3 reviews from 2.5 reach that point. Move the max(MIN_EASE, …) to wrap the updated value on line 53 and delete this line.

Located: the clamp line, and it names the second line involved (53). Specific: the ADR sentence quoted; a concrete consequence with numbers (1.16, nine reviews); the fix as two verbs. Severity: first word. The author can start typing.

scheduler.py line 50 (RIGHT) — the failure reset, with a suggestion

must-fix — ADR 0001, Failure: "leaves the Ease Factor untouched." The SM-2 parenthetical you quote is about intervals ("use intervals I(1), I(2) etc."), not the E-Factor; the sentence before it says "without changing the E-Factor." Keep the card's own ease factor:

```suggestion
        reps, ef, interval = 0, card.ease_factor, 1
```

Specific in a second way worth copying: it answers the author's own justification (the code comment quoted "as if the item was memorized anew") by pointing at what that sentence is actually about. A comment that ignores the author's stated reason invites a reply that restates it. The suggestion block makes "how" a click — and in M23 the author applied it as written.

scheduler.py line 55 (RIGHT) — round()

must-fix — ADR 0001, Rounding: "Do not reach for the built-in round(), which uses banker's rounding — round(2.5) is 2, not 3." A card with interval 5 and ease 2.5 is now due in 12 days, not 13. Use math.floor(card.interval * ef + 0.5) (and import math), which is what round_half_up did before this PR removed it.

No suggestion block here, deliberately: the fix touches two places (the expression and an import), and a suggestion replaces only the commented lines. When the fix is not one contiguous edit, say it in words and let the author make it.

scheduler.py line 15 (LEFT) — the nit

nit — anchored on the deleted import math because the module docstring (lines 1–12) is outside the diff: that docstring still promises all three rules ("update first, then the 1.3 floor", "leaves the Ease Factor untouched", "not round()") and the code below now breaks each one. The fix for the rounding item needs this import back.

Located honestly: the thing being discussed is not in the diff, so the comment says where it is anchored and why, instead of pretending line 15 is the problem. A reader who lands on it from the Files changed tab is not confused.

tests/domain/test_scheduler.py line 69 (RIGHT) — the changed assertion

must-fix — this assertion was 2.36 before this PR and it was right: it pinned the ADR's failure rule. Changing an expected value inside a "behaviour unchanged" refactor is the tell; ticket #14 says tests "must assert the same behaviour". Restore 2.36 here and on line 80, and restore the exact-half case (5 * 2.5 → 13) that was deleted with round_half_up.

One comment, three edits requested — but each is located (line 69, line 80, a named deleted test), and the source is the ticket's own criterion. A comment may ask for several things if each is findable.

The same findings, written so the author has to ask

Two of M21's must-fixes, rewritten as the comments a hurried reviewer leaves. Both are correct. Neither is actionable.

As a Conversation comment

"The ease factor handling looks off compared to the ADR, and I think the rounding might be wrong too. Can you double-check?"

Not located (which lines?). Not specific ("looks off" — which rule, what value?). Not marked ("I think… might" — is this blocking?). The author's only possible reply is a question, and the thread it starts costs both of you a day.

As submitted

Line 45: "must-fix — ADR 0001, Ease Factor: 'the update is applied first and the 1.3 floor is applied after, never before.' … a grade of 3 from 1.3 yields 1.16 … Move the max(MIN_EASE, …) to wrap the updated value on line 53 and delete this line."

Line, rule, number, fix, weight. The author's reply, in M23, was a commit SHA.

Inline, but a question

On line 50: "Are you sure SM-2 resets EF here?"

Located, and that is all. The author is sure — they wrote a comment saying why. This forces them to defend, not to fix; the reviewer has done half the reading and asked the author to do the other half.

Inline, answered

On line 50: "must-fix — ADR 0001, Failure: 'leaves the Ease Factor untouched.' The SM-2 parenthetical you quote is about intervals … Keep the card's own ease factor:" + the suggestion block.

The reviewer read the author's justification, read the source it cites, and wrote down what it says. Nothing is left for the author to look up.

Where the words come from

Every specific comment above quotes a document the repository already had — the ADR, CONTEXT.md, the ticket. That is not a coincidence: M21's Standards axis found the same sentences, because they are what makes a finding hard rather than a taste. A comment that can quote a rule is specific for free; one that cannot has to earn it with a reproduction (a value, a failing test) instead. If you have neither, you have an opinion, and page 2 says how to mark one.

Hands-on checklist

Assignment A4, item 3: your review of your peer's drill PR. Before you submit the batch, for every comment:

Self-check

1. A reviewer leaves, on the Conversation tab: "The rounding is wrong per the ADR." Which property does this comment lack first?

B. All of A–C are missing, but the first question the author must ask is "where?" — a Conversation comment about a line is not located. C is the next failure; A the third. D is not one of the three properties (and the comment is not discourteous).

2. Why did the round() comment on line 55 not carry a suggestion block, when the failure comment on line 50 did?

D. A suggestion is a replacement for the lines it sits on; a fix that also needs an import elsewhere is said in words. There is no per-file limit (A), no rule tying suggestions to smells (B), and C describes the comment's second sentence, not its form.

3. The line-50 comment spends a sentence on the SM-2 parenthetical the author quoted ("as if the item was memorized anew"). What does that sentence buy?

A. The author had a reason written in the code; a comment that ignores it gets that reason back as a reply. Answering it is what makes the comment actionable rather than merely correct. B, C, and D invent rules.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

The three properties, and the question each closes?
Located ("where?"), specific ("what, and why?"), severity-marked ("do I have to?").
The one-line test for an actionable comment?
Could the author start typing without replying with a question first?
What makes a comment specific "for free"?
Quoting the rule it rests on — an ADR sentence, a CONTEXT.md entry, a ticket criterion. Otherwise, a reproduction with a concrete value.
When to use a suggestion block, and when not?
When the fix is one contiguous edit to the commented lines (line 50). Not when it needs a second edit elsewhere (line 55: expression + import math).
How was the nit on PR #15 located, given the docstring was outside the diff?
Anchored on the deleted import math (LEFT, line 15) with the first sentence saying so and why.
Why answer the author's stated justification?
Otherwise it comes back as the reply. The line-50 comment answered "as if memorized anew" by saying what that sentence is about.
Google's reason to label severity?
"Without comment labels, authors may interpret all comments as mandatory, even if some comments are merely intended to be informational or optional."
What was the author's reply to each of the five comments, in M23?
A commit SHA (0c5a18d) and one sentence on what changed — the sign the comments were actionable.
Ask your teacher

Draft your five comments, then hand them to Claude Code with the peer's diff and ask it to play the author: "for each comment, either start the fix or tell me the question you would have to ask first." Every question it asks is a property your comment lacks. Rewrite until it asks none — then bring the before-and-after of one comment to the weekly meeting.
