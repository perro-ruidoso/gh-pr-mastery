Direct Claude, Push, Reply

Review has landed on your PR: three must-fixes, a nit, and a verdict of CHANGES_REQUESTED. The author's job is not to defend the diff but to turn each thread into a commit — through Claude Code — and then to close the loop in the same threads so the reviewer can verify without re-reading the whole PR. This page is that sequence on PR #15, with the prompt, the commit, the five replies, and the thread state before and after.

Direct Claude

The prompt given to Claude Code, in a session inside the clone with the PR's branch checked out. It names the PR, says what to do with each thread, sets the boundary, and asks for the loop to be closed — nothing about how to fix the arithmetic, because the comments already say that:

Author → Claude Code

Address the review on PR #15. Read every inline thread on it. For each one: fix the code the way the comment asks — the suggestion on the failure line can be applied as written — but keep the flatter one-function shape ticket #14 asked for. Restore the ADR 0001 rules and the tests on main that pinned them, under their original names. Run pytest, ruff check ., ruff format --check ., and mypy. Commit with a message that names which ADR rule each change restores, push, then reply in each thread with the commit that fixes it and one sentence on what changed. Do not touch anything outside scheduler.py and its tests, and do not resolve the threads yet — I will read the replies first.

Three things in that prompt do the work. "Read every inline thread" points the agent at the review comments, not the PR body, so nothing is addressed from memory. "Keep the flatter shape ticket #14 asked for" prevents the lazy fix — git revert — which would also throw away the ticket. And "do not resolve the threads yet" keeps the author in the loop: replies are the agent's, resolution is the author's judgement (page 2 explains why the order matters). On the throwaway the direction came from the build session rather than a typed prompt; the actions below are what it produced.

The scheduler still reads top to bottom in one function; the three rules read as the ADR states them, each with a comment naming its ADR section:

    if grade < PASSING_GRADE:
        # ADR 0001, Failure: "start repetitions for the item from the beginning
        # without changing the E-Factor" -- repetitions restart, the Ease Factor
        # is the card's own.
        repetitions, ease_factor, interval = 0, card.ease_factor, 1
    else:
        repetitions = card.repetitions + 1
        # ADR 0001, Ease Factor: the update first, the 1.3 floor after.
        ease_factor = max(
            MIN_EASE,
            card.ease_factor + (0.1 - (5 - grade) * (0.08 + (5 - grade) * 0.02)),
        )
        # ADR 0001, Rounding: I(1) = 1, I(2) = 6, then I(n-1) * EF rounded half-up
        # with a floor of one day -- math.floor(x + 0.5), not round().
        if repetitions == 1:
            interval = 1
        elif repetitions == 2:
            interval = 6
        else:
            interval = max(1, math.floor(card.interval * ease_factor + 0.5))

in_reply_to_id ties each reply to its comment — that is "without losing the thread" in the literal sense. A Conversation-tab comment saying "addressed all feedback, PTAL" loses all five: the reviewer has to rediscover which line each remark was about and check each fix by hand. One side effect worth knowing from M20 page 2: GitHub records each of these replies as a COMMENTED review in gh pr view --json reviews. They are not verdicts and change nothing about reviewDecision.

"Done" is not a reply

The reviewer cannot verify "done". They can verify "0c5a18d, line 53 now wraps the updated value, the nine-review test passes" in thirty seconds, from the thread, without opening the diff. Every reply above has the SHA and one checkable fact; that is the whole standard. The mirror image is M22's unsourced "wrong" — a reply the reviewer cannot act on.

Hands-on checklist

Assignment A4, item 4 — on your own drill PR, once your peer's review has landed:

Self-check

1. The author's prompt says "keep the flatter one-function shape ticket #14 asked for." What would have gone wrong without that sentence?

B. A review that says "the old behaviour was right" invites git revert; the prompt keeps the refactor's purpose while restoring its rules — which is what the ticket's criteria actually require. A, C, and D describe nothing that happens.

2. Why reply inside each review thread rather than post one Conversation comment saying the review is addressed?

D. "Without losing the thread" is literal. There is no such requirement (A); a Conversation comment changes no review state (B — and neither do replies); C mistakes a side effect for the reason, and the checker does not grade replies at all.

3. After the push and the five replies, the threads read isOutdated: true, isResolved: false. Is anything wrong?

A. Outdated is GitHub's fact about the diff; resolved is a person's judgement (M20 page 1). Replies never resolve (B); outdated threads resolve fine — page 2 resolves these five (C); the verdict has no bearing on resolution (D).

The author's first command after review lands?
gh api repos/O/R/pulls/N/comments — the review comments with their ids; replies go to those ids.
Three load-bearing phrases in the prompt to Claude Code?
"Read every inline thread"; "keep the flatter shape ticket #14 asked for" (no revert); "do not resolve the threads yet".
The route for replying in a thread?
POST /repos/O/R/pulls/N/comments/{comment_id}/replies with body; the reply carries in_reply_to_id.
What must a reply contain?
The fixing commit's SHA and one fact the reviewer can check from the thread — never just "done".
What did PR #15's fix commit restore, and what did it keep?
Restored the three ADR rules and main's tests (49 passing); kept the one-function shape ticket #14 asked for.
How do the replies appear in --json reviews?
As COMMENTED reviews, one each — not verdicts; reviewDecision stays CHANGES_REQUESTED.
Thread state after push + replies, before resolving?
isOutdated: true, isResolved: false, line: null on changed lines. Correct hand-off state.
Who resolves, and when?
The author, after reading the replies and deciding each concern is met — page 2. Not the agent, not the push.
Ask your teacher

Before you let Claude Code push, ask it: "list each review thread, the change you made for it, and the one sentence you will put in the reply — and tell me which comments you did not act on and why." A thread with no change and no reason is a thread you have to decide about yourself. Bring the ones where you disagreed with your peer to the weekly meeting; that disagreement is the thread's real content.
