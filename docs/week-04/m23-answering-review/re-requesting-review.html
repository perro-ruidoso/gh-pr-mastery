Re-request Without Losing the Thread

Two moves remain for the author, and their order is the point: resolve the threads you have answered, then re-request review from the person who requested changes. This page does the first on PR #15, shows the state it leaves, explains why the second could not be done there and what it looks like where it can — and gives the four-line sequence Assignment A4's checker reads back.

Resolve what you answered — and only that

You may resolve, as the author ("if you opened the pull request"). The question is which threads. The rule the course uses: resolve a thread when your reply in it names a commit that does what the comment asked, or when the thread is a question you have answered and the reviewer has said so. Do not resolve a thread you have declined — leave it open with your reason in it, so the reviewer sees the disagreement instead of a collapsed conversation. On PR #15 every thread had a fixing commit, so all five were resolved (13:42:07–13Z):

$ gh api graphql -f query='mutation { resolveReviewThread(input:{threadId:"PRRT_kwDOUZOL3M6iIMw_"}) { thread { id isResolved resolvedBy { login } } } }'
{"data":{"resolveReviewThread":{"thread":{"id":"PRRT_kwDOUZOL3M6iIMw_","isResolved":true,"resolvedBy":{"login":"acatlin"}}}}}
# … and the four must-fix threads the same way
$ gh api graphql … threads.graphql --jq '[.data.repository.pullRequest.reviewThreads.nodes[] | "\(.path):\(.line // "outdated")  resolved=\(.isResolved) by \(.resolvedBy.login)"]'
["src/flashcards/domain/scheduler.py:outdated  resolved=true by acatlin",
 "src/flashcards/domain/scheduler.py:outdated  resolved=true by acatlin",
 "src/flashcards/domain/scheduler.py:outdated  resolved=true by acatlin",
 "src/flashcards/domain/scheduler.py:15  resolved=true by acatlin",
 "tests/domain/test_scheduler.py:outdated  resolved=true by acatlin"]

Resolution is recorded on the thread with the resolver's login and nowhere else (M20 page 1). A reviewer who disagrees can unresolve — unresolveReviewThread — which is the honest way to say "not yet": the conversation reopens where it was, with the reply still in it.

Why reply, then resolve — not resolve, then reply

A resolved thread collapses. If you resolve first and reply after, the reviewer's notification points at a collapsed thread whose last visible line is their own comment; they expand it to find your reply. If you reply first, the notification carries your SHA and your fact, and the collapse that follows reads as "answered", not "dismissed". Same two actions, opposite impression. And the checker cannot tell the orders apart — this one is for the human on the other end.

Re-request: the move PR #15 could not make

GitHub's own sequence (fetched 2026-09-14): "After someone reviews your pull request and you make changes, you can request another review from the same reviewer." The command is the one that requested them in the first place — gh pr edit N --add-reviewer <login>, "Add or re-request reviewers by their login." The event it writes is review_requested, timestamped, naming the reviewer. On PR #15 the only identity that had requested changes was a bot, and M20 page 1 showed the result of asking for it: "Could not resolve user with login 'github-actions[bot]'." The author is not a candidate either. So the throwaway's PR has no review_requested event, its reviewDecision is still CHANGES_REQUESTED, and that is where it stays until a human reviewer exists — which, on your Instance, is your peer.

The author's side of that record is three moves in order: push (15:35), re-request (17:31:39), and — one more commit later — wait. The reviewer came back the next day and approved. Nothing the author did between 17:31 and 14:36 could have changed the field; only babakks could, and the re-request was the author's way of saying it was their turn.

The four-line sequence, and what the checker reads

$ git push                                            # 1. the fix lands on the PR
$ gh api -X POST repos/O/R/pulls/N/comments/<id>/replies -f body="Fixed in <sha>: …"   # 2. once per thread
$ gh api graphql -f query='mutation { resolveReviewThread(input:{threadId:"PRRT_…"}) { thread { isResolved } } }'   # 3. once per answered thread
$ gh pr edit N --add-reviewer <peer>                  # 4. after the push, never before
$ gh pr view N --json reviewRequests,reviewDecision   # the peer is listed; the decision has not moved yet

check_a4.py reads three of those from your PR: a commit on the PR dated after your peer's verdict (step 1), at least one thread with isResolved: true (step 3), and a ReviewRequestedEvent for your peer dated after your last commit (step 4). It does not read the replies (step 2) — that is the part only your peer can grade, and the rubric asks them to.

Order matters to the checker for one reason

A review_requested event before the commit could not have been about the commit. If you re-request and then remember one more fix, push it and re-request again; the second event is the one that counts. "Without losing the thread" applies here too: the reviewer should be summoned to the version they will review, and the SHA in your replies should be the head they find.

Hands-on checklist

Self-check

1. You disagree with one of your peer's must-fix comments and have written why in the thread. What do you do with that thread?

C. Resolve what you answered; leave what you declined visible. The checker needs one resolved thread, not all (A). Deleting is not an option anyone should take (B). The pair settles it in the thread or at the weekly meeting (D).

2. Why does PR #15 have no review_requested event, even though its author did everything else on this page?

A. M20 page 1's two refusals. gh pr edit --add-reviewer is the terminal route (B); the event is written when the request is made (C); open threads have nothing to do with it (D).

3. Which three things does check_a4.py read from the author's side of the drill PR?

D. Evidence only. Replies are not graded by script (A, B) — the peer grades them; APPROVED is noted, not required (B); outdated flags and request-removed events are not rules (C).

Which threads does the author resolve?
Those whose reply names a commit that does what was asked (or an answered question the reviewer accepted). Declined threads stay open with the reason.
Reply then resolve, or resolve then reply?
Reply first: the notification carries the SHA and the fact; the collapse then reads as "answered".
How does a reviewer undo a resolution they disagree with?
unresolveReviewThread — the thread reopens with the reply still in it.
The re-request command, and its timing rule?
gh pr edit N --add-reviewer <peer>, after the push — the event's timestamp must follow the last commit's.
Why does PR #15 have no re-request on record?
Its only verdict came from a bot, which cannot be a requested reviewer; the author cannot request themself. Needs a peer.
The author's three moves on cli/cli#14136?
Push (08-20 15:35), re-request babakks (17:31:39), wait — approved 08-21 14:36.
The three author-side facts check_a4.py reads?
A commit after the peer's verdict; ≥ 1 resolved thread; a review_requested for the peer after the last commit.
What does the checker not read, and who does?
The replies' content — the peer grades them against the rubric (SHA + one checkable fact).
Ask your teacher

After you re-request, ask Claude Code to run the timeline query from M20 page 2 on your PR and "check that my review_requested event is later than my last commit, and tell me what my peer will see first when they open the PR." If the answer is "your resolved threads, collapsed", ask whether your replies are visible in the notification they received. Bring a PR where the order went wrong to the weekly meeting — it is a common one.
