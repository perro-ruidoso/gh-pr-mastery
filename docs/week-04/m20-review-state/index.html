Threads, Resolution, Re-request

Every inline comment starts a thread. A thread can be resolved, and it becomes outdated when the lines it sits on change. When the author has pushed, they re-request review. None of these three moves has a gh pr subcommand; two are one GraphQL call each, and the third is gh pr edit --add-reviewer. This page does all three on PR #15 and shows what GitHub refuses along the way.

M20 · Review mechanics Bloom: Apply Assessed by: A4 (checker)

Objective: Resolve conversations, re-request review, and read a PR's review state correctly.

Threads are a GraphQL object

REST gives you review comments (page 2 of M19 read them). The thread that groups a comment with its replies — and carries the resolved flag — exists only in GraphQL, as PullRequestReviewThread. Its fields, from the reference (fetched 2026-09-14): isResolved "Whether this thread has been resolved."; isOutdated "Indicates whether this thread was outdated by newer changes."; isCollapsed "Whether or not the thread has been collapsed (resolved)."; resolvedBy "The user who resolved this thread."; plus path, line, diffSide, and comments. The query the course uses, saved as threads.graphql:

query($owner:String!, $name:String!, $number:Int!) {
  repository(owner:$owner, name:$name) {
    pullRequest(number:$number) {
      reviewDecision
      reviewThreads(first: 20) {
        nodes {
          id isResolved isOutdated path line diffSide
          resolvedBy { login }
          comments(first: 1) { nodes { author { login } createdAt body } }
        }
      }
    }
  }
}

Run right after the batched review landed (13:33:29Z):

$ gh api graphql -F owner=perro-ruidoso -F name=flashcards-w3probe -F number=15 -f query="$(cat threads.graphql)" --jq '.data.repository.pullRequest | {reviewDecision, threads: [.reviewThreads.nodes[] | {id, isResolved, isOutdated, path, line, diffSide}]}'

Outdated: what a push does to a thread

The author's fix (M23) was pushed at 13:41:11Z as commit 0c5a18d. The same query, 23 seconds later:

{"reviewDecision":"CHANGES_REQUESTED","threads":[
 {"first":"**must-fix** — ADR 0001, *Ease","id":"PRRT_kwDOUZOL3M6iIMwu","isOutdated":true,"isResolved":false,"line":null,"path":"src/flashcards/domain/scheduler.py"},
 {"first":"**must-fix** — ADR 0001, *Fail","id":"PRRT_kwDOUZOL3M6iIMwy","isOutdated":true,"isResolved":false,"line":null,"path":"src/flashcards/domain/scheduler.py"},
 {"first":"**must-fix** — ADR 0001, *Roun","id":"PRRT_kwDOUZOL3M6iIMw6","isOutdated":true,"isResolved":false,"line":null,"path":"src/flashcards/domain/scheduler.py"},
 {"first":"**nit** — anchored on the dele","id":"PRRT_kwDOUZOL3M6iIMw_","isOutdated":true,"isResolved":false,"line":15,"path":"src/flashcards/domain/scheduler.py"},
 {"first":"**must-fix** — this assertion ","id":"PRRT_kwDOUZOL3M6iIMxD","isOutdated":true,"isResolved":false,"line":null,"path":"tests/domain/test_scheduler.py"}]}

Every thread flipped to isOutdated: true, and line went to null on the four RIGHT-side threads — the lines they pointed at no longer exist in the new head. The LEFT-side nit kept line: 15, because a deleted line is a fact about the base, and the base did not move. Outdated is not resolved. GitHub marked the code as changed; nobody has yet said the concern is addressed. That is the author's next move, not GitHub's.

Resolving a thread

Who may: "You can resolve a conversation in a pull request if you opened the pull request or if you have write access to the repository where the pull request was opened." The mutation, from the reference: resolveReviewThread — "Marks a review thread as resolved." — with one required input, threadId (ID!). (There is a resolutionReason too, described as "The reason a Copilot code review thread was resolved"; not for us.) On the nit thread first:

$ gh api graphql -f query='mutation { resolveReviewThread(input:{threadId:"PRRT_kwDOUZOL3M6iIMw_"}) { thread { id isResolved resolvedBy { login } } } }'
{"data":{"resolveReviewThread":{"thread":{"id":"PRRT_kwDOUZOL3M6iIMw_","isResolved":true,"resolvedBy":{"login":"acatlin"}}}}}
PRRT_kwDOUZOL3M6iIMwu resolved=true
PRRT_kwDOUZOL3M6iIMwy resolved=true
PRRT_kwDOUZOL3M6iIMw6 resolved=true
PRRT_kwDOUZOL3M6iIMxD resolved=true

The other four followed the same way, 13:42:13Z. unresolveReviewThread reverses it. The docs describe the effect in the UI: "The entire conversation will collapse and be marked as resolved. This makes it easier to find conversations that still need to be addressed." — and, one paragraph on, the sentence that is M24's whole premise: "If the suggestion in a comment is out of your pull request's scope, you can open a new issue that tracks the feedback and links back to the original comment."

Resolution leaves no timeline event

The REST issue timeline of PR #15 shows commented, reviewed, committed — and nothing for the five resolutions. The only record that a thread was resolved, and by whom, is isResolved/resolvedBy on the GraphQL thread. check_a4.py reads exactly that. A student who says "I resolved everything" and a student who did are told apart by one query, not by the Conversation tab's scroll.

Re-requesting review

GitHub's requesting page: "After someone reviews your pull request and you make changes, you can request another review from the same reviewer." The gh manual gives the flag its full name — --add-reviewer <login>: "Add or re-request reviewers by their login." — so the same command serves first request and re-request. What it cannot do, verified on PR #15:

$ gh pr edit 15 --add-reviewer acatlin          # the author, asking for a review from themself
https://github.com/perro-ruidoso/flashcards-w3probe/pull/15
$ gh pr view 15 --json reviewRequests
{"reviewRequests":[]}
$ gh pr edit 15 --add-reviewer "github-actions[bot]"   # the bot identity that reviewed it
GraphQL: Could not resolve user with login 'github-actions[bot]'. (requestReviewsByLogin)
$ gh api -X POST repos/perro-ruidoso/flashcards-w3probe/pulls/15/requested_reviewers -f "reviewers[]=github-actions[bot]" --jq '.requested_reviewers'
[]

Requesting the author: exit 0, URL printed, nothing recorded — a silent no-op. Requesting a bot by gh: refused; by REST: accepted with a 201 and an empty requested_reviewers — also nothing. A review request needs a human (or a team) with read access, and the author is not a candidate. PR #15 therefore has no re-request on record, and cannot: the course account is the author and its only other identity is a bot. This is the second-identity problem, and it is why the assignment pairs you and why the pages show the full transition on a public repository instead — page 2.

The bot identity, and what it could not do

To have any verdict other than the author's, a workflow_dispatch workflow on the throwaway ran gh pr review as github-actions[bot]. It could --request-changes (13:34:14Z, and reviewDecision became CHANGES_REQUESTED). It could not approve: "failed to create review: GraphQL: GitHub Actions is not permitted to approve pull requests." — a setting, can_approve_pull_request_reviews: false, read back at both repository and organization level and left as it was. And it cannot be a requested reviewer at all, above. A bot is a reviewer of last resort for a demonstration; it is not a peer, and the pages do not pretend otherwise.

Hands-on checklist

Self-check

1. After the author pushed 0c5a18d, every thread on PR #15 read isOutdated: true. What does that tell a reviewer?

C. "Outdated by newer changes" is a fact about the diff, not a judgement. Resolved is a separate flag (A) that a person sets. The comments persist (B). Any commit that touches the lines does it (D) — 0c5a18d was an ordinary push.

2. Where is the record that a thread on a PR was resolved, and by whom?

B. The page ran the REST timeline after five resolutions and it showed none of them. There is no such event (A), no state change on the review (C), and no such field on the comment (D).

3. The author of a PR runs gh pr edit N --add-reviewer <their own login>. What does GitHub record?

D. The transcript above: a silent no-op. The bot case (B) is what produced the GraphQL error; the author case did not. No event is written (C), and no request exists to dismiss (A).

Where do review threads live in the API?
GraphQL only: pullRequest.reviewThreads, objects of type PullRequestReviewThread with ids beginning PRRT_.
The three thread flags?
isResolved (a person marked it), isOutdated ("outdated by newer changes"), isCollapsed ("collapsed (resolved)").
What does a push do to a thread on a changed line?
isOutdated: true, line: null. Not resolved — that is still the author's move.
The mutation that resolves a thread, and its input?
resolveReviewThread(input:{threadId:"PRRT_…"}) — "Marks a review thread as resolved." Undo: unresolveReviewThread.
Who may resolve a conversation?
"If you opened the pull request or if you have write access to the repository where the pull request was opened."
Does resolving leave a timeline event?
No. The REST timeline shows commented, reviewed, committed — resolution is visible only on the GraphQL thread.
The command that re-requests review, in the manual's words?
gh pr edit N --add-reviewer <login> — "Add or re-request reviewers by their login."
What happens when the author requests review from themself? From a bot?
Self: exit 0, nothing recorded. Bot: "Could not resolve user with login 'github-actions[bot]'" (REST: 201, empty list). A request needs a human or team with read access.
Can GitHub Actions approve a PR?
Not by default: "GitHub Actions is not permitted to approve pull requests." (can_approve_pull_request_reviews: false). It could request changes.
Ask your teacher

After your peer's review lands, ask Claude Code: "run the reviewThreads query on my PR and tell me which threads are outdated, which are resolved, and which are neither — and for each unresolved one, quote the first comment." If it answers from the Conversation tab instead of the query, ask it for the query. Anything it cannot explain about the difference between outdated and resolved is a question for the weekly meeting.
