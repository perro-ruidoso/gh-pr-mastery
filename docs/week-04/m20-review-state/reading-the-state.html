Reading reviewDecision Correctly

One field summarises a PR's review state, and it is easy to read wrong: it ignores comment-only reviews, it does not reset when the author pushes, and gh prints it as an empty string where GraphQL says null. This page follows it through every transition on PR #15 with timestamps, then through a public PR on cli/cli that goes all the way to APPROVED.

M20 · Review mechanics Bloom: Apply Assessed by: A4 (checker)

Objective: Resolve conversations, re-request review, and read a PR's review state correctly.

The field and its three values

GraphQL's PullRequestReviewDecision enum (fetched 2026-09-14): APPROVED "The pull request has received an approving review."; CHANGES_REQUESTED "Changes have been requested on the pull request."; REVIEW_REQUIRED "A review is required before the pull request can be merged." The field itself is "The current status of the pull request with respect to code review." There is no fourth value for "nobody has decided anything": that state is null, which gh pr view --json renders as "". REVIEW_REQUIRED only appears once a ruleset requires reviews — Week 1 saw it on cli/cli; you will see it on your Instance after M26.

Read the surprises. Seven reviews, five of which nobody wrote as reviews: the five COMMENTED entries at 13:42:00–07Z are the author's five thread replies (M23) — GitHub wraps each reply in a single-comment review record. reviews lists them all; latestReviews keeps one per reviewer and drops the author entirely, leaving the bot's verdict alone. --comments interleaves Conversation comments (status: none) with review summaries and labels each with its verdict in words. Which view you want depends on the question: "what has been said" (reviews, --comments), "where does each reviewer stand" (latestReviews), "can this merge as far as review is concerned" (reviewDecision).

So PR #15 ends this week still CHANGES_REQUESTED — correctly. The reviewer who requested changes has not said otherwise, and nothing the author did (push, reply, resolve) can say it for them. The last two transitions — a re-request, and the reviewer's APPROVED — need a second human. Here is what they look like when one exists.

Request → CHANGES_REQUESTED (five days later) → two commits addressing it → review_requested for the same reviewer, two hours after the commits → two more commits → APPROVED the next day → merge. The field went null → CHANGES_REQUESTED → APPROVED, and the only thing that moved it each time was a review with a verdict. The re-request did not change it; it told babakks to look again. That review_requested event, placed after the new commits, is precisely what check_a4.py looks for on your PR.

Why the re-request comes after the push

A re-request before the fix is a request to re-read the same code. GitHub's own description of the move puts the order in the sentence: "After someone reviews your pull request and you make changes, you can request another review." Push first, then gh pr edit N --add-reviewer <peer>. The checker compares the review_requested timestamp with the last commit's; a request that predates the commit does not count, because it could not have been about it.

Hands-on checklist

On your own drill PR, at each step of Assignment A4 items 3–5:

Self-check

1. A reviewer requested changes; the author pushed a fix and resolved every thread. What does reviewDecision read now, on a repository with no ruleset?

B. PR #15 at 13:42:13Z. Pushes and resolutions do not touch the field; only a review with a verdict does (or a ruleset that dismisses stale approvals — not requests — in Week 5). A's value needs a required-review rule; C and D invent effects.

2. gh pr view --json reviews on PR #15 lists seven reviews but latestReviews lists one. Why?

D. Six of the seven are the author's (one batched review, five thread replies recorded as comment reviews); latestReviews shows where each non-author reviewer stands, so only the bot remains. There is no time window (A), pending reviews are invisible to others (B), and the bot's review is at b0fac63, not the current head (C).

3. On cli/cli#14136, what evidence shows the re-request was about the fix rather than the original code?

A. Ordering is the evidence — the same test check_a4.py applies. The field did not move on the re-request (B); a review records the head it reviewed, not the merge commit (C); anyone with write access may request at any time (D).

The three values of reviewDecision, and the fourth state?
APPROVED, CHANGES_REQUESTED, REVIEW_REQUIRED; no decision is null in GraphQL and "" in gh pr view --json.
Does a COMMENTED review change reviewDecision?
No. PR #15 read "" after a five-comment batched review; the bot's CHANGES_REQUESTED was the first thing to set it.
Does the author's push clear CHANGES_REQUESTED?
No — the verdict stands until that reviewer reviews again. Neither do replies or resolving threads.
What are the five extra COMMENTED reviews on PR #15?
The author's five thread replies — GitHub records each reply as a single-comment review.
reviews vs latestReviews?
All submitted reviews, versus one per non-author reviewer — where each stands now.
When does REVIEW_REQUIRED appear?
Only when a ruleset or branch protection requires a review before merging (Week 5, M26).
cli/cli#14136's transitions?
CHANGES_REQUESTED 08-18 11:46 → commits 08-20 15:35 → review_requested 17:31 → APPROVED 08-21 14:36 → merged 15:11.
What evidence does the checker read for "re-requested after the fix"?
A ReviewRequestedEvent for the peer whose createdAt is after the PR's last commit.
Ask your teacher

Pick any merged PR on a repository you follow and ask Claude Code to run the timeline query from this page on it, then "narrate reviewDecision through every event, and say which events could not have changed it." If its narration has the field changing on a push or a resolve, it is wrong, and this page says why. Bring a PR whose history you cannot narrate to the weekly meeting.
