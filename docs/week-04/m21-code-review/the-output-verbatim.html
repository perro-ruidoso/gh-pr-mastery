# Standards review — `b0fac63` (scheduler simplification)

## (a) Documented-standard violations — **hard**

**`scheduler.py`, failure branch** — `reps, ef, interval = 0, STARTING_EASE, 1`
Resets the Ease Factor to 2.5 on a failing Grade. Contradicts ADR 0001 *Failure* ("start repetitions from the beginning **without changing the E-Factor**") and CONTEXT.md *Repetition* ("does **not** reset the Ease Factor"). The new comment misquotes SM-2 — "as if memorized anew" is not the published wording the ADR reproduces. Tests `test_failure_restarts_the_card_from_scratch` / `test_fail_then_recover_starts_over` were rewritten to pin the wrong behaviour.

**`scheduler.py`, floor ordering** — `ef = max(MIN_EASE, card.ease_factor)` then `ef = ef + (...)`
ADR 0001: "the update is applied *first* and the 1.3 floor is applied *after*, never before." Here the floor precedes the update, so no floor is applied to the result at all. Worse: the pre-check is a no-op (`Card.__post_init__` already rejects `ease_factor &lt; 1.3`), and a 1.3 card graded 3 now yields 1.16, which `replace()` raises on. The replacement test dodges this by using grade 5.

**`scheduler.py`, interval** — `max(1, round(card.interval * ef))`
ADR 0001 *Rounding*: "Do not reach for the built-in `round()`, which uses banker's rounding." The ADR gives the exact required expression (`math.floor(raw + 0.5)`). `test_exact_half_interval_rounds_up_not_to_even` — the test that pins this trap — was deleted.

**Module docstring** now states three rules the body contradicts (floor after update, EF untouched on failure, "not `round()`"). Stale documentation of a caller-facing function (CLAUDE.md *Conventions*, docstrings).

**CLAUDE.md *Working here*** — "A pull request that changes scheduling arithmetic must say which rule in ADR 0001 it implements." The commit message names none; if the PR body matches, that's a breach. `docs/agents/domain.md` also requires ADR conflicts to be surfaced explicitly, not silently overridden.

**CLAUDE.md *Conventions*** — "Name tests after the behaviour they pin." `test_ease_factor_never_drops_below_the_floor` asserts 1.3 → 1.4 and never exercises the floor.

## (b) Baseline smells — judgement calls

- **Mysterious Name** — `ef`, `reps`; CONTEXT.md says `ease_factor` is the code form and `docs/agents/domain.md` says use glossary vocabulary. Replacing `PASSING_GRADE`, `FIRST_INTERVAL`, `SECOND_INTERVAL` with bare `3`, `1`, `6` loses the names the ADR gives them.
- **Primitive Obsession (magic literals)** — `1 if reps == 1 else 6 if reps == 2 else …`: a nested conditional expression that the reader must decode against the ADR table. CLAUDE.md rule 2's rationale ("one small, pure, **well-named** place… a reviewer can check by reading") cuts against inlining `next_interval`/`round_half_up`.
- **Speculative Generality (inverse)** — the up-front `max(MIN_EASE, …)` guards an impossible state and is overwritten in one branch; delete it and restore the post-update floor.

Ruff/mypy-enforced items (unused `math` import etc.) skipped.

One artefact to notice: &lt; in the floor-ordering paragraph. The agent wrote the HTML entity for < instead of the character. It is left as returned; it is the kind of thing a reader corrects in their head and a copy-paster ships.

# Spec review — commit b0fac63 vs. issue #14 / ADR 0001

The refactor's shape matches the issue, but it changes the scheduling rules in three places. The new test suite passes (48/48) only because the tests were rewritten to pin the new, wrong behaviour. Running the pre-change `main` tests against the new code fails 5 of them.

## (c) Requirements that look implemented but are wrong

**1. Ease-factor floor moved before the update — inverts the ADR ordering.**
Spec: *"`review()` behaviour is unchanged for every grade and every starting state; ... nothing in the diff contradicts [ADR 0001]"*. ADR: *"the update is applied first and the 1.3 floor is applied after, never before."*
New code does `ef = max(MIN_EASE, card.ease_factor)` and then adds the delta with no floor afterward. A card at EF 1.3 graded 3 now lands at **1.16**; on `main` it stayed at 1.3. The "exactly one place" criterion is met, but in the wrong place. The old test `test_ease_factor_floor_is_applied_after_the_update_not_before` was deleted and replaced with one that grades 5 (delta +0.1) so the floor is never exercised.

**2. Failure now resets EF to 2.5 — contradicts the ADR's quoted SM-2 wording.**
ADR: *"start repetitions for the item from the beginning **without changing the E-Factor**"* ... *"leaves the Ease Factor untouched."*
New code: `reps, ef, interval = 0, STARTING_EASE, 1`. The code comment quotes "as if the item was memorized anew" — text that appears nowhere in the ADR. A card at EF 2.36 failed now returns EF 2.5 (was 2.36). Two tests were rewritten to assert the new value (`test_failure_restarts_the_card_from_scratch`, `test_fail_then_recover_starts_over`).

**3. `round()` replaces half-up rounding — the exact trap the ADR names.**
Spec: *"Interval rounding is one expression"*. ADR: *"Do not reach for the built-in `round()`, which uses banker's rounding ... `interval = max(1, math.floor(raw + 0.5))`."*
New code: `max(1, round(card.interval * ef))`. Interval 5 × EF 2.5 = 12.5 now gives **12** (was 13). The `math` import and `round_half_up` were removed; `test_exact_half_interval_rounds_up_not_to_even` was deleted.

## (a) Missing / partial requirements

**Tests no longer pin every ADR rule.**
Spec: *"`tests/domain/test_scheduler.py` still pins every ADR rule by name; tests may be renamed or reorganised but must assert the same behaviour."*
Three rules lost their tests: floor-after-update, exact-half rounds up, interval floor of 1 day (`test_interval_never_drops_below_one_day` deleted; the replacement `test_later_intervals_are_whole_days` checks 35.4→35, which `round()` and half-up agree on). Two others now assert the opposite of the ADR.

## (b) Scope creep

All three behaviour changes above fall under the issue's *"Out of scope: Any change to the scheduling rules themselves."* Also, `PASSING_GRADE`, `FIRST_INTERVAL`, `SECOND_INTERVAL` were deleted (not just inlined) — acceptable under "fold the helpers back in", but the module docstring still promises "Ease Factor update first, then the 1.3 floor" and "leaves the Ease Factor untouched", which the code below it no longer does.

`Card`, storage, and CLI are untouched — that criterion is met.

**Verdict:** does not satisfy #14. Recommend restoring the three rules (floor after update, EF unchanged on failure, `math.floor(x + 0.5)`) and reinstating the deleted tests.

Before you turn the page

Two facts about this output that page 3 will use. First, it is not the ground truth: it is two agents' reading of a diff against documents, in under 400 words each, and it contains at least one number and one claim that a reviewer should check before repeating. Second, the same three defects appear on both axes — once as breaches of the ADR (Standards), once as departures from the ticket's "behaviour is unchanged" (Spec). That is the separation working: two independent routes to the same three lines is stronger evidence than one.

Self-check

1. Both reports name the failure-branch reset. Where does each say it looked to establish that it is wrong?

D. Read the two paragraphs: each names its source in the text. The routes differ (a documented standard versus the originating issue) and converge on one line — which is the point of two axes. A describes what Spec did elsewhere (it ran the old tests), not for this finding; B and C misattribute.

2. The Spec report says "Running the pre-change main tests against the new code fails 5 of them." What should a reviewer do with that sentence?

B. A number an agent reports is a claim, and this one is cheap to check. Page 3 does, and gets 4 (plus an import failure). A repeats an unverified claim; C invents a restriction the brief does not have; D asks the agents to agree with each other, which is not verification.

3. Why does the page show the reports as Markdown source in <pre> blocks instead of rendering them?

A. seed/SPEC.md's rule for this drill: "Do not curate the agent's output — run it and use what it says." Rendering is a kind of curation. B, C, and D are not true.
