Two /code-reviews, Two Axes

There are two things called /code-review on a course machine, and they produce differently shaped output. This objective is about the one that reports along two axes — Standards and Spec — because the separation is what makes its findings checkable. This page tells the two apart, walks the skill's five steps as written, and shows the run on PR #15 up to the moment the two sub-agents were launched.

M21 · Agentic review Bloom: Analyze Assessed by: A4 (written)

Objective: Run /code-review on a branch and separate verified findings from noise across its Standards and Spec axes.

Which /code-review?

Claude Code ships a built-in command of that name. Anthropic's Code Review page (fetched 2026-09-14) describes it under "Review a diff locally": "The /code-review command reviews a diff in your terminal without installing the GitHub App. It reports correctness bugs and reuse, simplification, and efficiency cleanups." It "runs as a background subagent with its own context window", takes an effort level ("At low and medium, the review reports only the findings it's most confident in … high through max broaden coverage and may include findings the review is less sure about"), and has flags: "--fix: applies the findings to your working tree after the review"; "--comment: posts the findings on a GitHub pull request as inline comments". /code-review ultra escalates to a cloud review. Its findings come back as a list with file, line, one-sentence summary, and a category tag.

The course's M21 skill is a different thing: the code-review skill from mattpocock/skills, installed under ~/.agents/skills/code-review/SKILL.md and shipped in the plugin students install (skills/engineering/code-review, in the manifest's 25). Its description: "Review the changes since a fixed point (commit, branch, tag, or merge-base) along two axes — Standards (does the code follow this repo's documented coding standards?) and Spec (does the code match what the originating issue/PRD asked for?). Runs both reviews in parallel sub-agents and reports them side by side." On this machine the installed skill is what the Skill tool lists under the name; students with the plugin may see it namespaced. Tell them apart by the output: the course's skill ends with ## Standards and ## Spec headings and a one-line summary per axis; the built-in ends with a findings list carrying severities.

Why the course uses the two-axis one

The skill's own reason: "A change can pass one axis and fail the other: Code that follows every standard but implements the wrong thing → Standards pass, Spec fail. Code that does exactly what the issue asked but breaks the project's conventions → Spec pass, Standards fail. Reporting them separately stops one axis from masking the other." Each finding therefore comes tagged with what it was checked against — a documented standard, or a spec line — and that tag is what you verify on page 3. A finding with no source to check against is an opinion.

The five steps, as installed

From the installed SKILL.md (dated 2026-07-09, read 2026-09-14; upstream head 3cca18b differs only in punctuation — em-dashes became colons, "issue/PRD" became "issue/spec", and the instruction to run /setup-matt-pocock-skills became "tell the user to run" it):

  1. Pin the fixed point. "Whatever the user said is the fixed point — a commit SHA, branch name, tag, main, HEAD~5, etc. If they didn't specify one, ask for it." Then: "Capture the diff command once: git diff <fixed-point>...HEAD (three-dot, so the comparison is against the merge-base). Also note the list of commits via git log <fixed-point>..HEAD --oneline." And a guard: "confirm the fixed point resolves (git rev-parse <fixed-point>) and the diff is non-empty."
  2. Identify the spec source, in order: "Issue references in the commit messages (#123, Closes #45…) — fetch via the workflow in docs/agents/issue-tracker.md"; a path the user passed; a spec file under docs/, specs/, or .scratch/; else ask — "If they say there isn't one, the Spec sub-agent will skip and report 'no spec available'."
  3. Identify the standards sources — "Anything in the repo that documents how code should be written" — plus the skill's fixed smell baseline, twelve Fowler smells, bound by two rules: "The repo overrides. A documented repo standard always wins" and "Always a judgement call. Each smell is a labelled heuristic ('possible Feature Envy'), never a hard violation — and, like any standard here, skip anything tooling already enforces."
  4. Spawn both sub-agents in parallel, each with the diff command and commit list; the Standards one with the standards files and the baseline "pasted in full — the sub-agent has no other access to it"; the Spec one with the spec's contents. Each brief ends "Under 400 words."
  5. Aggregate: "Present the two reports under ## Standards and ## Spec headings, verbatim or lightly cleaned. Do not merge or rerank findings" and "End with a one-line summary: total findings per axis, and the worst issue within each axis (if any). Don't pick a single winner across axes."

Notice that M03's three-dot diff is step 1's own rule, that step 2 reads the issue tracker configuration A1 had you write, and that step 5 forbids the thing a human reviewer does by instinct — ranking everything into one list. The skill hands you two lists and the job of judging them.

Fixed point resolves (main = bba30dd; the merge base is 309b051, one commit behind, because main had moved since the branch was cut — the three-dot form handles that). Diff non-empty: two files. Spec source found at step 2's first rung — Closes #14 in the commit — and fetched as docs/agents/issue-tracker.md says, with gh issue view. Standards sources: CLAUDE.md, CONTEXT.md, docs/adr/0001-sm2-rounding-and-the-clock.md, and docs/agents/domain.md. Then two general-purpose sub-agents were launched in one message, each with the diff command, the commit list, and its brief; the Standards one carried the four standards paths and the full smell baseline. They ran 64 s and 56 s, three tool calls each. Their reports are page 2, exactly as returned.

What the skill needed from Weeks 1–3

Step 2 only works because docs/agents/issue-tracker.md exists (A1, M05) and because the commit says Closes #14 (M15's keyword). Step 3 only bites because the repository has a written standard for this arithmetic — the Seed's ADR 0001 — and a binding vocabulary in CONTEXT.md. On a repository with none of that, the Spec sub-agent is skipped and the Standards one has only the smell baseline: twelve judgement calls and nothing hard. The skill is as good as the documents you gave it.

Self-check

1. You run /code-review in Claude Code and the output ends with a severity-tagged findings list and no ## Standards heading. What ran?

C. The built-in "reports correctness bugs and reuse, simplification, and efficiency cleanups" as a findings list. The Pocock skill has no effort levels (A), always prints both headings and notes a skipped Spec axis (B), and has no ultra (D) — that is the built-in's escalation.

2. Why does the skill refuse to merge or rerank the Standards and Spec findings into one list?

A. The skill's "Why two axes" section, quoted on this page. B confuses a scheduling detail with the design reason; C and D are inventions.

3. On PR #15 the skill found its spec source without asking. Which two Week 1–3 artifacts made that possible?

B. Step 2's first rung is "issue references in the commit messages", fetched "via the workflow in docs/agents/issue-tracker.md". D names real inputs to step 1 and step 3, not step 2; A and C name artifacts the skill never reads for this purpose.

The two /code-reviews, and how to tell which ran?
Claude Code's built-in (correctness + cleanups, a severity-tagged findings list, --fix/--comment/ultra) versus the Pocock skill (## Standards and ## Spec headings, one-line summary per axis).
The skill's two axes, in its words?
"Standards — does the code conform to this repo's documented coding standards? Spec — does the code faithfully implement the originating issue / PRD / spec?"
Step 1's diff command, and why that form?
git diff <fixed-point>...HEAD — "three-dot, so the comparison is against the merge-base" (M03).
Where does step 2 look for the spec first?
Issue references in the commit messages, fetched via docs/agents/issue-tracker.md. On PR #15: Closes #14 → gh issue view 14.
The two rules that bind the smell baseline?
"The repo overrides" (a documented standard wins) and "Always a judgement call" (a smell is a labelled heuristic, never a hard violation; skip what tooling enforces).
What does step 5 forbid?
Merging or reranking across axes: "Don't pick a single winner across axes — that's the reranking the separation exists to prevent."
Standards sources found on the throwaway?
CLAUDE.md, CONTEXT.md, docs/adr/0001-sm2-rounding-and-the-clock.md, docs/agents/domain.md — plus the baseline.
Installed vs upstream code-review?
Same process; upstream (head 3cca18b) has colons for em-dashes, "issue/spec" for "issue/PRD", and "tell the user to run /setup-matt-pocock-skills". In the plugin.
Ask your teacher

Before running the skill on your peer's PR, ask Claude Code: "which code-review will the Skill tool run if I type /code-review here, and what headings will its output have?" Then run it and compare. If the answer and the output disagree, you have found the naming collision this page describes on your own machine — bring the transcript to the weekly meeting.
