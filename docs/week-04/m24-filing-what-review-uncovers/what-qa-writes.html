What /qa Writes, and What It Does Not

Read one of the filed issues back with gh issue view and you learn three things: the body has a fixed shape, the shape has rules about what may not appear in it, and the skill applies no label and no type — because its text never mentions either. This page reads #17 field by field, shows the two templates the shape comes from, and says what that means for triage and for the checker.

And the body, as filed:

#17 — body

## Parent issue
Reported during QA session (from review of PR #15).

## What's wrong
When a deck file is refused because one Card is invalid, the error names the Card by its position in the file (card 1: …) rather than by its id — and the position is zero-based, so card 1 is the second Card in the file.

## What I expected
Cards are identified by id, unique within the Deck — that is how a person finds one in the file and how every other part of the tool refers to them. The error should say which Card by id, e.g. card es-002: Card.ease_factor must be at least 1.3, optionally with the position too.

## Steps to reproduce
1. Take a deck file with several cards and set the ease_factor of a card in the middle to 1.2.
2. Run flashcards list --deck <that file>.
3. Observe the message: card 1: Card.ease_factor must be at least 1.3 for the second card. Nothing in it says es-002, so in a large Deck the reader has to count entries in the file — from zero — to find the Card.

## Blocked by
None — can start immediately

## Additional context
The existing due-date error uses the same card <index> shape, so a fix should cover every per-card message, not only the Ease Factor one. Independent of whether the whole Deck should be refused (filed separately); even a per-card warning needs to name the Card. Consistent, not intermittent. Out of scope of PR #15.

Where the shape comes from

The skill carries two templates. For a single issue: ## What happened, ## What I expected, ## Steps to reproduce, ## Additional context. For one slice of a breakdown: ## Parent issue ("or 'Reported during QA session'"), ## What's wrong, ## What I expected, ## Steps to reproduce, ## Blocked by ("Or 'None — can start immediately' if no blockers."), ## Additional context. #16 and #17 are the breakdown shape — one report, two separable concerns — and #18 the single shape. Both share three headings, which is what makes the shape recognisable across a backlog and what check_a4.py looks for: What happened or What's wrong, then What I expected, then Steps to reproduce.

Then the rules the skill imposes on every body, quoted: "No file paths or line numbers — these go stale"; "Use the project's domain language"; "Describe behaviors, not code — 'the sync service fails to apply the patch' not 'applyPatch() throws on line 42'"; "Reproduction steps are mandatory — if you can't determine them, ask the user"; "Keep it concise — a developer should be able to read the issue in 30 seconds." Read #17 against them: Card, Deck, Ease Factor capitalised as CONTEXT.md spells them; no json_store.py, no line; the behaviour ("names the Card by its position") rather than the code that produces it; three numbered steps with a concrete input. The one internal detail that is in there — the zero-based index — is a fact about the message the user sees, so it stays.

Durable means "still true after the refactor"

The skill's word for the standard is "durable — they should still make sense after major refactors." A body that says "line 52 of json_store.py" is wrong the moment someone adds an import; a body that says "when a deck file is refused because one Card is invalid" is true until the behaviour changes, which is the moment the issue closes. The same logic sits behind Week 2's M07: an issue is a contract with whoever picks it up next, and a fresh agent session picks up what is written, not what was meant.

What it does not write: labels and type

$ gh issue list --state open --json number,title,labels,issueType,createdAt --jq '.[] | "#\(.number)  labels=\([.labels[].name])  type=\(.issueType.name // "none")  \(.title[0:50])"'
#18  labels=[]  type=none  ADR 0001 says SM-2 leaves rounding open; the cited pu
#17  labels=[]  type=none  Deck-file errors name a card by zero-based position, n
#16  labels=[]  type=none  A deck with one invalid card cannot be listed at all
#14  labels=[]  type=none  Simplify the scheduler: one bounds check, one reset pa

Empty labels, no type — on a repository that has the five triage labels and belongs to an org with Task, Bug, and Feature types. This is not an omission of the run; it is the skill. Its text says gh issue create and nothing about --label or --type; docs/agents/triage-labels.md exists for /triage, which "moves issues … through a state machine" and applies the labels as it goes. A freshly filed /qa issue is, in that machine's terms, an unlabeled issue — the first bucket /triage shows: "Unlabeled — never triaged." The division of labour is deliberate: the reporter's skill writes what happened; the maintainer's skill decides what to do about it. That maintainer seat is Week 6.

So check_a4.py grades the body shape and reports the labels and type as a note — "labels none, type none — the installed /qa applies none; triage is Week 6" — rather than failing an issue for lacking what the skill was never going to add. If you want a bug label on your filed issues now, gh issue edit N --add-label bug is one line; it is your act, not the skill's, and the checker will note it either way.

One thing the run did leave behind

The body files were written on Windows and the issues' bodies carry \r\n line endings — visible in the raw JSON, invisible on the web. GitHub renders them fine; but a --jq that splits the body on \n gets a trailing \r on every line, which is why the read-back above ends with rtrimstr("\r") — and why a first attempt with scan("^## .*") returned one heading swallowing the whole body. A small thing, recorded so the next person does not lose ten minutes to it.

Hands-on checklist

Assignment A4, item 5, second half — after /qa has filed:

Self-check

1. #17's body mentions that the index is zero-based but not the name of the module that formats the message. Which rule is that obeying?

C. Durability. A module name rots with the next refactor; the message the user sees is the behaviour under complaint. A and B pick real rules for the wrong reason; D is about ordering, not content.

2. The three issues have no labels and no type. What is the correct reading?

A. The skill says gh issue create and nothing more; the labels file maps roles for /triage. The labels exist on the throwaway (created before the run) (C); nothing in triage-labels.md addresses creation (B); D is invented.

3. Which headings does check_a4.py require to count an issue as filed by /qa?

B. The intersection of the two templates. A would fail every single-shape issue like #18; C would accept any bug report; D requires what the skill never adds.

Ask your teacher

Give Claude Code one of your filed issues and ask it to "implement this in a fresh session with no other context — tell me first what you would have to ask." If it has a question, the body failed the skill's own standard somewhere; find the rule. Then ask it which triage label it would apply and why — and notice that answering is Week 6's job, not this week's. Bring an issue the fresh session could not start to the weekly meeting.
