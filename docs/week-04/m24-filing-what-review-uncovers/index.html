Out of Scope Means an Issue, Not a Commit

Review always turns up things that are true and not the PR's business. The reflex is to fix them "while you're in there" — and Week 3 spent a page on why that reflex produces unreviewable diffs. The alternative is a filed issue, and /qa turns a spoken complaint into one with a shape a developer can pick up cold. This page runs it on the two things PR #15's review uncovered outside the PR, and shows the PR untouched afterwards.

M24 · Bug capture Bloom: Apply Assessed by: A4 (checker)

Objective: Turn what review uncovers into filed issues with /qa rather than fixing out of scope in the open PR.

GitHub says it in one sentence

The commenting page, under "Resolving conversations" (fetched 2026-09-14): "If the suggestion in a comment is out of your pull request's scope, you can open a new issue that tracks the feedback and links back to the original comment." The author's page repeats it as a heading of its own — "Opening an issue for an out-of-scope suggestion": "If someone suggests changes to your pull request and the changes are out of the pull request's scope, you can open a new issue to track the feedback." Both pages describe the web button; the course does it from Claude Code, because the hard part is not creating the issue but writing one that survives.

What review uncovered that was not #15's business

Ticket #14's out-of-scope line: "Any change to the scheduling rules themselves. Due-date filtering (T05). The review command (T04)." — and, implicitly, anything outside scheduler.py and its tests. Two things surfaced while reviewing against the ADR and its source:

  1. The Standards agent noted that Card.__post_init__ rejects an ease factor below 1.3. Following that thread: what happens when a deck file already holds such a card? Probed on the throwaway: flashcards list --deck bad.json prints card 1: Card.ease_factor must be at least 1.3, exits 1, and shows none of the other cards. Storage and CLI — not the scheduler.
  2. Reading ADR 0001's rounding section against the SuperMemo page it cites: the ADR says the original "does not settle" rounding; the source says "If interval is a fraction, round it up to the nearest integer." The ADR's decision stands; its claim about its source does not. Documentation — not the PR.

Both would have been a two-line "while I'm here" in 0c5a18d. Both would have widened a PR whose reviewer had just checked exactly two files, and turned "restore three rules" into "restore three rules, change how decks load, and rewrite an ADR". Neither went in.

The skill, as installed — and where students get it

~/.agents/skills/qa/SKILL.md, description: "Interactive QA session where user reports bugs or issues conversationally, and the agent files GitHub issues. Explores the codebase in the background for context and domain language. Use when user wants to report bugs, do QA, file issues conversationally, or mentions 'QA session'." Its five steps: listen and lightly clarify ("Ask at most 2-3 short clarifying questions … Do NOT over-interview. If the description is clear enough to file, move on."); explore the codebase in the background ("The goal is NOT to find a fix — it's to: Learn the domain language … Understand what the feature is supposed to do … Identify the user-facing behavior boundary"); assess scope: single issue or breakdown; file the GitHub issue(s) ("Create issues with gh issue create. Do NOT ask the user to review first — just file and share URLs."); continue ("Each issue is independent — don't batch them.").

Not in the plugin — vendored by the course

Upstream removed qa on 2026-08-05 (commit c66bdee, "chore: remove six unused skills and the personal bucket"; it had already been in the deprecated bucket), and the plugin students install never carried it. The changeset names /triage and /to-tickets as what absorbed it — but triage moves existing issues through states and to-tickets decomposes a spec; neither takes a complaint and files it. So the course vendors the last upstream copy (MIT) at skills/qa/SKILL.md, byte-identical to the installed one, with a one-command install in skills/README.md. Do that before Assignment A4 item 5.

The run

Invoked in Claude Code inside the clone of the throwaway, with the report given in one message (steps, expected versus actual, consistency — so step 1 had nothing to ask):

Reporter → /qa

Reviewing PR #15 turned up two things that are not the PR's business. First: if a deck file contains one card whose ease factor is below 1.3 (say a deck written by an older or buggy version), flashcards list --deck that.json refuses to show the deck at all — I get "card 1: Card.ease_factor must be at least 1.3" and exit 1 — and it identifies the card by its position, not its id, so in a 200-card deck I would not know which card to fix. Second: docs/adr/0001 says the original SM-2 publication "does not settle" rounding, but the SuperMemo page it cites says "If interval is a fraction, round it up to the nearest integer" — the ADR's decision (half-up) stands, but its claim about the source is wrong. File these as issues; do not touch PR #15.

/qa

No clarifying questions — expected, actual, steps, and "consistent" were all in the report. An Explore sub-agent was launched (read-only, "medium" breadth) for the domain vocabulary and the list command's documented behaviour. Scope: the first report has two separable concerns — the whole deck refused, and the card named by position — so it becomes two thin issues; the ADR claim is one issue.

Explore sub-agent (96 s, 13 tool uses) — returned

CONTEXT.md vocabulary quoted (Card "Identified by id, unique within its Deck"; Ease Factor "never falls below 1.3"). The list command's help: "print every card in a deck"; documented exit codes: 0, and 1 "if the deck could not be read". One storage error type; per-card messages are shaped <path>: card <index> — "Note the index is 0-based, so 'card 1' is the second Card." No test covers a below-floor ease factor in a deck file. The ADR sentence, verbatim: "The original publication does not settle these, and both are places where a plausible implementation is silently wrong."

/qa

Filed three issues with gh issue create --body-file, in dependency order (none blocks another):
#16 A deck with one invalid card cannot be listed at all
#17 Deck-file errors name a card by zero-based position, not by its id
#18 ADR 0001 says SM-2 leaves rounding open; the cited publication says to round up
"Next issue, or are we done?"

Two things the exploration changed in the issues before they were filed: "card 1" became "the second card" (the index is zero-based — worse than the report thought), and the documented exit-code contract went into #16's context so the fixer knows today's behaviour is within the letter of the docs and the issue is about whether it should be.

That pair of facts — the PR's file set unchanged, and issues with the skill's shape filed after it opened — is what check_a4.py reads for this objective.

Hands-on checklist

Assignment A4, item 5 — on your own Instance, after your peer's review:

Self-check

1. While fixing the three review threads, the author notices the deck loader rejects a whole deck for one bad card. It is a two-line fix. Why not include it in 0c5a18d?

B. Scope is the argument, and GitHub's own docs give the alternative: "open a new issue that tracks the feedback." A verdict locks nothing (A); no such CI rule exists (C); /qa is the tool for the alternative, not a gate (D).

2. Why does the course vendor qa rather than tell students to use /triage or /to-tickets, which upstream named as its replacements?

D. The fit to the objective is the reason recorded in skills/README.md. A is false (A1 creates the labels in Week 1); B is a half-truth about to-tickets but not the reason; C is not the policy (the S1 decision is still open).

3. The report said "card 1". The filed issue says "the second card". Where did the correction come from?

A. "Note the index is 0-based, so 'card 1' is the second Card" is a sentence from the Explore sub-agent's report. No question was asked (B); gh edits nothing (C); no thread mentioned it (D).

Ask your teacher

After your review, ask Claude Code: "list everything we noticed about this repository during the review that ticket N does not cover." Each item is either a /qa report or a thing you decide to forget — say which, out loud. Then run /qa on one and read the issue it files as if you were a stranger picking it up next month. Bring one you would not have understood to the weekly meeting.
