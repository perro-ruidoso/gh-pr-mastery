GitHub Pull Requests for Agentic Coders Week 4

Week 4 — Owning the Diff

A pull request with three planted defects and a green test suite. This week you sit on both sides of it: review a peer's copy with the terminal and with /code-review, judging what the agent found rather than repeating it; then answer review on your own copy through Claude Code, and file what the review uncovered but the PR must not absorb.

Weeks 1–3 built the machinery — issues with edges, branches from issues, PRs that close them. Week 4 is about the conversation in the middle: what a comment, a review, and a suggestion each are (M19); what resolving, re-requesting, and reviewDecision actually record (M20); how to read an automated review's findings as candidates and give each a verdict (M21); how to write a comment the author can act on without asking a question (M22); how to answer review as the author without losing the thread (M23); and how to turn out-of-scope discoveries into issues instead of drive-by commits (M24). Every transcript on these pages is from one pull request on a throwaway Instance, flashcards-w3probe#15, run on 2026-09-14 — a "refactor" of a correct SM-2 scheduler that quietly breaks three rules of the Seed's ADR and rewrites the tests that pinned them.

Suggested order, and the pairing

Read M19 and M20 first — they are the mechanics everything else stands on. M21 and M22 are the reviewer's week; M23 and M24 the author's. Assignment A4 pairs you with another student: you review their drill PR and they review yours, so both seats get played for real. The instructor publishes the pairing before the meeting; the drill PR is opened on your Instance by you, with seed/tools/plant_review_pr.py, because GitHub will not let an author approve or request changes on their own pull request — the week's first verified fact.

Three things that surprised the course itself

A push does not clear CHANGES_REQUESTED — the throwaway's PR still reads it after the fix landed, every thread was replied to, and every thread was resolved; only the reviewer's next review can move it. The installed /code-review is not Claude Code's /code-review — same name, different tool, different output shape; M21 tells them apart. And /qa applies no labels and no type — the issues it files are unlabelled by design, because labelling is /triage's job in Week 6. The M20, M21, and M24 pages have the transcripts.

Assignment A4

Due before the Week 5 meeting. Paired. The full brief is in assignments/a4.md; in short:

  1. Open the drill PR on your own Instance with seed/tools/plant_review_pr.py — you are its author.
  2. On your peer's drill PR: one Conversation comment, then a batched review with inline comments, a suggestion block, and a REQUEST_CHANGES verdict.
  3. Run /code-review on your peer's branch; write up both reports unedited and a verdict per finding in a4-writeup.md on your Instance.
  4. On your own PR: direct Claude Code to address your peer's threads, push, reply in each thread with the SHA, resolve, re-request review from your peer.
  5. Run /qa on something review uncovered outside the PR's scope; leave the PR's files alone.
  6. When your peer approves, merge; the drill ticket closes itself.

Items 1–2 and 4–6 leave evidence checkers/check_a4.py --handle you --peer them reads: a review with a verdict by the peer, inline comments with a suggestion, a resolved thread, a commit after the verdict, a review_requested event after that commit, issues with /qa's headings filed after the PR opened, the PR's file set unchanged. Whether the comments were actionable, whether the verdicts were right, and whether the out-of-scope call was sound are graded by a human against the rubric.
