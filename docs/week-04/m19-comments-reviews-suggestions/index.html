Three Things That Look Alike

A comment on the Conversation tab, a review with inline comments and a verdict, and a suggested change are three different objects on GitHub, stored in three places, with three different consequences. This page tells them apart with GitHub's own definitions and with gh against a real pull request — including what happens when the author tries to review their own.

M19 · Review mechanics Bloom: Apply Assessed by: A4 (checker)

Objective: Distinguish a single comment, a review, and a suggested change; batch comments and submit a review with a verdict.

The exhibit

Every transcript on the M19–M24 pages comes from one pull request on the course's throwaway Instance, perro-ruidoso/flashcards-w3probe, run on 2026-09-14: PR #15, "Simplify the scheduler: one bounds check, one reset path, one rounding call". It refactors the SM-2 scheduler that PR #13 had landed correctly, and its body claims "the rules themselves are unchanged". Three of them are not — the three defects seed/SPEC.md plants for this week — and its tests pass anyway. The PR was opened by the course account, which matters on this page: some of what a reviewer does, GitHub does not let the author do.

Three objects

GitHub's commenting page draws the line in two sentences (fetched 2026-09-14): "You can comment on a pull request's Conversation tab to leave general comments, questions, or praise. You can also suggest changes that the pull request author can apply directly from your comment." and "You can also comment on specific files or sections of a file in a pull request's Files changed tab as individual line or file comments, or as part of a pull request review."

ObjectWhere it livesWhat it carriesgh
Single commentThe Conversation tab — an issue comment on the PR's timeline (/issues/N/comments)Markdown. No file, no line, no verdict. One notification.gh pr comment N --body
ReviewThe Files changed tab — a group of inline comments plus a summary, submitted together with one of three verdicts (/pulls/N/reviews)Pending until submitted; inline comments anchored to a file and a diff line; the state COMMENTED, APPROVED, or CHANGES_REQUESTED. One notification for the batch.gh pr review N --comment | --approve | --request-changes for the verdict and summary; gh api for inline comments (page 2)
Suggested changeInside an inline comment: a fenced ```suggestion blockReplacement text for the commented lines. The author can commit it from the comment; the commit is co-authored.Written into a comment body, from either of the above

The REST reference puts the second object in one sentence: "Pull Request Reviews are groups of pull request review comments on a pull request, grouped together with a state and optional body comment." And it separates the inline kind from the first: "Pull request review comments are comments made on a portion of the unified diff during a pull request review. These are different from commit comments and issue comments in a pull request." So a "comment" on a PR is one of two things, and only the inline kind can carry a suggestion.

The single comment, from gh

The first move on PR #15 was a Conversation-tab comment: a note on what the reviewer was about to do, and one observation that did not belong on any line — the test file's changed expected values.

$ gh pr comment 15 --body "Reading this against \`docs/adr/0001\` now. Before I go line by line: the body says the rules are unchanged, but the test file changes three expected values (2.36 → 2.5 twice, and the 12.5 → 13 case is gone). A refactor with the same behaviour should not need new assertions — so I am treating those three lines as the map of where to look."
https://github.com/perro-ruidoso/flashcards-w3probe/pull/15#issuecomment-5664781550
$ gh api repos/perro-ruidoso/flashcards-w3probe/issues/15/comments --jq '.[] | {id, user: .user.login, created_at}'
{"created_at":"2026-09-14T13:31:29Z","id":5664781550,"user":"acatlin"}

Note the route it was read back from: /issues/15/comments. A PR is an issue with code attached, and a Conversation-tab comment is an issue comment. It will never appear at /pulls/15/comments, which is where the inline review comments live.

The three verdicts

GitHub's reviewing page (fetched 2026-09-14) defines them when you submit: "Select Comment to leave general feedback without explicitly approving the changes or requesting additional changes. Select Approve to submit your feedback and approve merging the changes proposed in the pull request. Select Request changes to submit feedback that must be addressed before the pull request can be merged." The same three are the event values of the REST create-review endpoint — COMMENT, APPROVE, REQUEST_CHANGES — and the three flags of gh pr review: -c/--comment, -a/--approve, -r/--request-changes.

"Must be addressed" is not enforced by default

From the same page: "The Request changes option is purely informational and will not prevent merging unless a ruleset or classic branch protection rule is configured with the 'require a pull request' option." Your Instance has no ruleset yet — Week 5 adds one (M26). Until then a CHANGES_REQUESTED verdict changes reviewDecision (M20) and nothing about the merge button.

What the author cannot do — verified live

The reviewing page says it once, flatly: "Pull request authors cannot approve their own pull requests." The course account opened PR #15, so every route was tried:

$ gh pr review 15 --approve
failed to create review: GraphQL: Review Can not approve your own pull request (addPullRequestReview)
$ gh pr review 15 --request-changes --body "The failure path resets the ease factor; ADR 0001 says it must not."
failed to create review: GraphQL: Review Can not request changes on your own pull request (addPullRequestReview)
$ gh api -X POST repos/perro-ruidoso/flashcards-w3probe/pulls/15/reviews -f event=APPROVE
{"message":"Unprocessable Entity","errors":["Review Can not approve your own pull request"],"documentation_url":"https://docs.github.com/rest/pulls/reviews#create-a-review-for-a-pull-request","status":"422"}
gh: Unprocessable Entity (HTTP 422)
$ gh api -X POST repos/perro-ruidoso/flashcards-w3probe/pulls/15/reviews -f event=REQUEST_CHANGES -f body=x
{"message":"Unprocessable Entity","errors":["Review Can not request changes on your own pull request"],"documentation_url":"https://docs.github.com/rest/pulls/reviews#create-a-review-for-a-pull-request","status":"422"}
gh: Unprocessable Entity (HTTP 422)

Both verdicts refused, by both routes; gh pr review surfaces the GraphQL mutation's message, gh api the REST 422. What the author can submit is a review with the COMMENT verdict — page 2 does exactly that — and Conversation-tab comments. This is the reason Assignment A4 is paired and the reason the student, not the instructor, opens the drill PR on their Instance: the person who is going to review with a verdict must not be the author.

Who may review at all

The pull-request-reviews reference (fetched 2026-09-14): "Anyone with read access can review and comment on proposed changes." Your Instance is public, so your peer can review it with no collaborator invitation. Requesting a review is the narrower permission: "To request a review, you need write access to the repository. You can request a review from a person or team with read access to the repository." That is M20's business.

Hands-on checklist

On your peer's drill PR (Assignment A4, items 2–3), before you write anything substantive:

Self-check

1. A colleague writes "I left a comment on your PR." Which of these is the only one that could carry a ```suggestion block?

B. A suggestion replaces the commented lines, so it needs a file and a line to anchor to — only an inline (review) comment has them. A Conversation comment (A) and a review summary (C) have no line; a commit comment (D) is a different object again ("different from commit comments and issue comments").

2. The author of PR #15 ran gh pr review 15 --request-changes --body "…". What happened?

D. The transcript above. GitHub refuses both verdicts from the author, by GraphQL and by REST; nothing is downgraded (B) or parked (C). A would also be wrong for a second reason: without a ruleset, Request changes "is purely informational".

3. Your peer's Instance is public and you are not a collaborator on it. Which is true?

A. "Anyone with read access can review and comment on proposed changes," and a public repository gives everyone read access. Requesting a review is the thing that needs write access. B, C, and D each invent a permission the reference does not describe.

Flashcards

Where does a Conversation-tab comment live in the API?
As an issue comment: /repos/O/R/issues/N/comments. Never under /pulls/N/comments.
GitHub's one-sentence definition of a review?
"Pull Request Reviews are groups of pull request review comments on a pull request, grouped together with a state and optional body comment."
The three verdicts, and their gh pr review flags?
COMMENT (-c), APPROVE (-a), REQUEST_CHANGES (-r).
What can an author submit on their own PR?
Comments and a COMMENT-verdict review. APPROVE and REQUEST_CHANGES are refused: "Can not approve your own pull request".
Does Request changes block the merge on your Instance?
No — "purely informational" until a ruleset with "require a pull request" exists (Week 5).
Who can review a public repository's PR?
"Anyone with read access can review and comment" — so any GitHub user. Requesting a review needs write access.
Where can a suggested change appear?
Only in an inline (review) comment, as a ```suggestion block — it needs a file and a line to replace.
Ask your teacher

Open your peer's drill PR and ask Claude Code, in a session inside your clone of their Instance: "list every comment on PR N and tell me, for each, whether it is an issue comment, a review, or a review comment, and which API route you read it from." If it lumps them together, it has not learned the distinction this page makes — and neither has a reviewer who reads only the Conversation tab. Bring the cases you are unsure about to the weekly meeting.
