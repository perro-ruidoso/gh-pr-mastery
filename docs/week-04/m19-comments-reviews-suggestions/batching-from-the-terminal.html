A Batched Review from gh

gh pr review submits a verdict and a summary, but it has no flag for a file or a line. Inline comments — and the suggestion block that rides inside one — go through the REST create-review endpoint, which gh api calls. This page builds one review with five inline comments and one suggestion, submits it in a single call, and shows the two 422s GitHub returned on the way.

Objective: Distinguish a single comment, a review, and a suggested change; batch comments and submit a review with a verdict.

Why batch

GitHub's commenting page (fetched 2026-09-14): "If you want to add multiple comments, click Start a review, then continue adding comments. When you're finished, click Submit review, leave a summary of your review, and click Submit review." And the reason: "Anyone watching the pull request or repository will receive a notification of your comments. Batching your comments avoids sending multiple notifications." Until you submit, "your line comments are pending and only visible to you." From the terminal there is no pending state to manage — the whole batch is one request with the verdict in it.

The endpoint

POST /repos/{owner}/{repo}/pulls/{pull_number}/reviews. Its body takes event (APPROVE, REQUEST_CHANGES, COMMENT; "By leaving this blank, you set the review action state to PENDING"), body ("Required when using REQUEST_CHANGES or COMMENT"), and comments, "an array of objects" each with path, body, and a location: either position — "the number of lines down from the first '@@' hunk header in the file" — or line with side (LEFT for deletions, RIGHT for additions and context) and optionally start_line/start_side for a range. line is a line number in the file as shown on that side of the diff; position is a count into the diff text. Use line.

The review, as a file

The suggestion block's content is the exact text that will replace line 50 if the author clicks Commit suggestion — indentation included, which is why it starts with eight spaces. GitHub's incorporating-feedback page says what that click produces: "Applying one suggested change or a batch of suggested changes creates a single commit on the compare branch of the pull request. Each person who suggested a change included in the commit will be a co-author of the commit."

Two refusals before it landed

The first attempt put the docstring nit on line: 11, in the module docstring. GitHub:

$ gh api -X POST repos/perro-ruidoso/flashcards-w3probe/pulls/15/reviews --input review1.json
{"message":"Unprocessable Entity","errors":["Line could not be resolved"],"documentation_url":"https://docs.github.com/rest/pulls/reviews#create-a-review-for-a-pull-request","status":"422"}
gh: Unprocessable Entity (HTTP 422)

Lines 1–12 are not in the diff — the first hunk starts at line 13 — and an inline comment can only anchor to a line the diff shows. The second attempt tried the review-comment endpoint's subject_type: "file" (a comment on the file rather than a line):

{"message":"Unprocessable Entity","errors":["Variable $comments of type [DraftPullRequestReviewComment] was provided invalid value for 0.subjectType (Field is not defined on DraftPullRequestReviewComment), 0.position (Expected value to not be null)"], …}

Two facts in one error: the comments array of a review does not accept subject_type (the docs list it only on the single-comment endpoint, POST /pulls/N/comments), and behind the REST route is a GraphQL type, DraftPullRequestReviewComment. The nit moved to the deleted import math line — line: 15, side: "LEFT", a line that is in the diff — and said so in its first sentence. Third attempt:

$ gh api -X POST repos/perro-ruidoso/flashcards-w3probe/pulls/15/reviews --input review1.json --jq '{id, state, submitted_at, html_url}'
{"html_url":"https://github.com/perro-ruidoso/flashcards-w3probe/pull/15#pullrequestreview-5198312441","id":5198312441,"state":"COMMENTED","submitted_at":"2026-09-14T13:33:07Z"}

Reading it back

$ gh pr view 15 --json reviewDecision,reviews,reviewRequests --jq '{reviewDecision, reviewRequests, reviews: [.reviews[] | {author: .author.login, state, submittedAt, commit: .commit.oid[0:7]}]}'
{"reviewDecision":"","reviewRequests":[],"reviews":[{"author":"acatlin","commit":"b0fac63","state":"COMMENTED","submittedAt":"2026-09-14T13:33:07Z"}]}

Three things to read off this. All five comments share one created_at — the batch is atomic, one submission, one notification. Each carries pull_request_review_id 5198312441, the review that groups them, which is how a later reader (or check_a4.py) knows they were a review and not five separate comments. And reviewDecision is still the empty string: a COMMENTED review is a review, but it is not a decision — M20 explains what moves that field.

One review, or many single comments?

The single-comment endpoint POST /pulls/N/comments exists too, and in_reply_to on it is how you answer inside a thread (M23 uses that). But five separate calls are five notifications, five timeline entries, and no verdict. The batched review is the unit GitHub designed for the job, and the one the checker looks for: comments grouped under a review whose state is a verdict.

Hands-on checklist

Assignment A4, item 3 — your review of your peer's drill PR.

Self-check

1. Your create-review call returns 422 "Line could not be resolved". What is the most likely cause?

C. That is exactly what happened on PR #15 with line: 11: the module docstring is above the first hunk. Inline comments anchor to lines the diff shows. A, B, and D would each produce a different error, if any.

2. After the batched review was submitted, why did all five review comments show the same created_at?

A. One POST, one review (id 5198312441 on each), one moment. Timestamps are to the second (B); the input has no such field (C); the verdict has nothing to do with it (D) — a REQUEST_CHANGES batch would look the same.

3. Which location fields does a comment inside the create-review comments array accept?

D. The documented properties of comments. subject_type (A) is on the single-comment endpoint only — GitHub said so: "Field is not defined on DraftPullRequestReviewComment". line/side work in a review (B) — the page used them. in_reply_to (C) is the single-comment endpoint's reply mechanism.

Flashcards

The endpoint that submits a batched review with inline comments?
POST /repos/O/R/pulls/N/reviews with event, body, and a comments array — gh api -X POST … --input review.json.
line versus position?
line is the file's line number on the given side; position counts lines down from the first @@ hunk header. Use line.
What does side: LEFT anchor to?
A deleted line (red). RIGHT is additions and unchanged context. The nit on PR #15 sat on the deleted import math, LEFT line 15.
"Line could not be resolved" means?
The line is not in the diff on that side — outside every hunk. Move the comment to a line that is.
Can a review's comments array carry subject_type: file?
No — "Field is not defined on DraftPullRequestReviewComment". File-level comments exist only on the single-comment endpoint.
What does applying a suggestion create?
"A single commit on the compare branch of the pull request"; the suggester is a co-author, the applier is co-author and committer.
How do you tell a batched review from five single comments afterwards?
Same created_at and the same pull_request_review_id on each comment; a review record with a state.
Why batch, in GitHub's words?
"Batching your comments avoids sending multiple notifications" — and pending comments are "only visible to you" until submitted.
Ask your teacher

Have Claude Code draft your review JSON from your notes, then ask it: "for each comment, which hunk of gh pr diff contains the line you chose, and which side is it on?" If it cannot point at the hunk, the line is a guess and GitHub will tell you so with a 422. Bring the JSON and the response to the weekly meeting if anything is refused.
