The Keyword and Its Two Conditions

Closes #1 in a PR body makes GitHub do two things: link the PR to the issue now, and close the issue when the PR merges. Both happen only if the PR targets the default branch. This page shows the link appearing a second late, the close arriving a second after the merge, and the case where neither happens at all.

M15 · PR authoring Bloom: Create Assessed by: A3 (checker + rubric)

Objective: Write a PR body that states intent, scope, verification, and risk, and closes its issue on merge with a linking keyword.

The nine words and the syntax

GitHub's linking page lists the keywords — close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved — and the syntax by case:

Linked issueSyntaxExample
Issue in the same repositoryKEYWORD #ISSUE-NUMBERCloses #10
Issue in a different repositoryKEYWORD OWNER/REPOSITORY#ISSUE-NUMBERFixes octo-org/octo-repo#100
Multiple issuesUse full syntax for each issueResolves #10, resolves #123, resolves octo-org/octo-repo#100

"The keywords can be followed by colons or in uppercase. For example: Closes: #10, CLOSES #10, or CLOSES: #10." And on unlinking: "To unlink an issue that you linked using a keyword, you must edit the pull request description to remove the keyword." The keyword also works in a commit message — "The issue will be closed when you merge the commit into the default branch, but the pull request that contains the commit will not be listed as a linked pull request" — which is why the course puts it in the body: the link is the point, not only the close.

Condition one: the PR targets the default branch

The sentence this week turns on, from the same page:

"The special keywords in a pull request description are interpreted only when the pull request targets the repository's default branch. If the pull request targets any other branch, then these keywords are ignored, no links are created, and merging the PR has no effect on the issues."

Observed twice. On the throwaway, PR #5 was opened with Closes #2 in its body against the branch of PR #4, not main:

$ gh pr view 5 --json number,baseRefName,closingIssuesReferences --jq '{number, base: .baseRefName, closes: [.closingIssuesReferences[].number]}'
{"base":"1-add-review-state-to-card-repetitions-ease-factor-interval-due-date","closes":[],"number":5}

Empty, 20 seconds after creation, and still empty after the parent merged. It populated the moment the base was changed to main — M16 page 2 has that transcript. The course repository's own PR #14 did the same: opened at 15:06:47 with Closes #13 against the Week 1 branch, closingIssuesReferences empty until the retarget at 15:40:05, merged at 15:43:30 closing #13 at 15:43:31.

Condition two: the PR merges — and what "link" looks like meanwhile

On a PR that does target the default branch, the link is created when the body is saved, not when the PR merges — but not in the same second. PR #4, created at 17:00:19:

$ gh pr create --title "Add review state to Card" --body-file pr1.md
https://github.com/perro-ruidoso/flashcards-w3probe/pull/4
$ gh pr view 4 --json number,baseRefName,closingIssuesReferences --jq '{number, base: .baseRefName, closes: [.closingIssuesReferences[].number]}'
{"base":"main","closes":[],"number":4}

…fifteen seconds later:
$ gh pr view 4 --json closingIssuesReferences,createdAt --jq '{createdAt, closes: [.closingIssuesReferences[].number]}'
{"closes":[1],"createdAt":"2026-09-13T17:00:19Z"}

$ gh api repos/perro-ruidoso/flashcards-w3probe/issues/1/timeline --jq '.[] | select(.event=="connected" or .event=="closed") | "\(.created_at)  \(.event)"'
2026-09-13T17:00:21Z  connected
2026-09-13T17:02:48Z  closed

The issue's timeline records a connected event — GitHub's event-types reference: "The issue or pull request was linked to another issue or pull request" — at 17:00:21, two seconds after the PR was created. A script that reads closingIssuesReferences in the same second as gh pr create sees []; check_a3.py is run long after, so it does not care, but your own verification should ask twice.

Then the merge, and the close:

$ gh pr merge 4 --squash
$ gh pr view 4 --json state,mergedAt,mergeCommit --jq '{state, mergedAt, mergeCommit: .mergeCommit.oid[0:7]}'
{"mergeCommit":"0b9a901","mergedAt":"2026-09-13T17:02:47Z","state":"MERGED"}
$ gh issue view 1 --json state,stateReason,closedAt
{"closedAt":"2026-09-13T17:02:48Z","state":"CLOSED","stateReason":"COMPLETED"}

Merged at 17:02:47, closed at 17:02:48, stateReason: COMPLETED. The same machine-time gap M06's worked examples turn on — two seconds on cli/cli, one on the course repo — now produced by your own PR. The other two tickets on the throwaway closed the same way — #3 at 17:09:15 after a 17:09:14 merge, #2 at 17:12:48 after a 17:12:47 merge — and check_a3.py reads exactly this: a closedAt within seconds of the linking PR's mergedAt, with reason COMPLETED. An issue closed by hand with gh issue close has a gap of minutes, or a close before the merge, and fails the rule.

Two dotted edges, two conditions: the link (default-branch base + keyword) and the close (link + merge). Every timestamp is from a command on this page.
Reading the link from either end

From the PR: gh pr view N --json closingIssuesReferences — an array of {id, number, repository, url}. From the issue: gh issue view N --json closedByPullRequestsReferences — same shape, and it lists only PRs that are open or merged; the closed-unmerged drive-by on M14 page 2 dropped out of it while gh pr list --json closingIssuesReferences still showed the keyword link on the PR side.

Hands-on checklist

Self-check

1. A PR with Closes #2 in its body targets another feature branch. What happens to #2 when the PR merges into that branch?

C. The docs: "these keywords are ignored, no links are created, and merging the PR has no effect on the issues." PR #5 showed closes: [] for as long as its base was #4's branch. B describes what people expect; it is not what happens.

2. gh pr view 4 --json closingIssuesReferences printed [] right after creation and [1] fifteen seconds later. What should a verification script conclude?

A. The issue's timeline shows connected at 17:00:21, two seconds after the 17:00:19 creation — server-side latency, not a client cache (B) and not CI (C). The body did not change (D).

3. Which pair of timestamps is the evidence that a keyword, not a person, closed issue #1?

D. The M06 argument: a one-second gap between merge and close, with reason COMPLETED, is what the keyword produces and what a human cannot. A is evidence of the link, not the close; B and C prove nothing about who closed it.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

The nine closing keywords?
close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved — colons and uppercase allowed.
The two conditions for a keyword to close an issue?
1. The PR targets the default branch (otherwise "ignored, no links are created"). 2. The PR merges.
How long after gh pr create did closingIssuesReferences populate for PR #4?
Not in the same second; connected landed at 17:00:21 for a 17:00:19 creation. Read twice.
Merge-to-close gap on the throwaway's three tickets?
One second each: 17:02:47→48, 17:09:14→15, 17:12:47→48, all COMPLETED.
Keyword in a commit message instead of the body — difference?
Closes the issue on merge to the default branch, but "the pull request that contains the commit will not be listed as a linked pull request."
Syntax for an issue in another repository?
KEYWORD OWNER/REPOSITORY#ISSUE-NUMBER, e.g. Fixes octo-org/octo-repo#100.
How do you unlink a keyword-linked issue?
Edit the PR description and remove the keyword; only manually linked PRs can be manually unlinked.
Field on the issue side that mirrors closingIssuesReferences?
gh issue view N --json closedByPullRequestsReferences — open or merged PRs only.
Ask your teacher

Ask Claude Code: "open a draft PR against a throwaway branch with Closes #N in the body, show me closingIssuesReferences, retarget it to main with gh pr edit --base, show it again, then close the PR unmerged." Watch whether it waits before reading the field, and whether it knows why the first read was empty. Bring anything still unclear to the weekly meeting.
