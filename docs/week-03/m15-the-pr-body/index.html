Intent, Scope, Verification, Risk

A PR body is the author's half of the review. It tells the reviewer what to expect before the diff, what not to look for, how the author knows it works, and what could go wrong. Four sections; a real one that passed the checker; and why --fill is not a substitute.

M15 · PR authoring Bloom: Create Assessed by: A3 (checker + rubric)

Objective: Write a PR body that states intent, scope, verification, and risk, and closes its issue on merge with a linking keyword.

What GitHub calls the body

GitHub's linking page defines it in passing: the pull request description is "the summary text added by the author when they created the pull request." The creating-a-PR page says only "Type a title and description for your pull request." Nothing in the docs says what a description should contain — that is a team's convention, and this course's convention is four headings. The convention exists because the reviewer in Week 4 will be a peer with ten minutes, and the ticket in Week 2 already taught the shape: a document another person can act on without asking a question.

The four sections

SectionAnswersA good one…A bad one…
IntentWhy does this PR exist? What will be true after it merges?names the ticket's purpose and the next thing it unblocksrestates the title, or the diff
ScopeWhich files, and — just as important — which files not?lists what was touched and says what was deliberately left alone"see diff"
VerificationHow does the author know it works?quotes the commands and the numbers they printed"tests pass"
RiskWhat could this break, and how would we know?names a concrete failure mode and what mitigates it"Low." with no reason

Then the closing keyword on its own line — page 2 is about what it does and when it does nothing.

A body that passed: PR #4

The PR from M14 page 1, written to a file and passed with --body-file. This is the text verbatim:

pr1.md — the body of PR #4, perro-ruidoso/flashcards-w3probe, 2026-09-13 
## Intent
Give `Card` the four pieces of review state SM-2 needs — repetitions, ease factor, interval, due date — so the scheduler (T03) and the deck file (T02) have something to read and write.

## Scope
- `src/flashcards/domain/models.py`: four defaulted fields on `Card`, validated in `__post_init__`.
- `tests/domain/test_models.py`: defaults, a populated card, `dataclasses.replace`, and the three rejections.

Nothing else. Persistence is #2; the scheduler is a later ticket.

## Verification
- `pytest`: 26 passed (20 before).
- `ruff check .`, `ruff format --check .`, `mypy` (strict): clean.
- `flashcards list --deck decks/starter.json` output unchanged — the fields have defaults, so no caller changes.

## Risk
Low. Additive fields with defaults; every existing constructor call still works. The ease-factor floor of 1.3 is SM-2's own rule (`docs/adr/0001`), enforced here so a bad file cannot smuggle in a lower value once #2 lands.

Closes #1

Read it against the table. Intent names what the fields are for (two later tickets). Scope says "Nothing else" and names the two tickets that own what was left out — a reviewer who wonders where persistence is has the answer before asking. Verification has numbers: 26 tests, up from 20, and the one manual check that proves the CLI is untouched. Risk says "Low" and then earns it: additive, defaulted, and one deliberate guard with the rule it enforces. Nothing in the body is a restatement of the diff; everything is something the diff cannot say about itself.

Why not --fill

The gh pr create manual: "use --fill to autofill these values from git commits," with --fill-first and --fill-verbose variants. A commit message is written for the history; a PR body is written for a reviewer. The commit behind #4 says "Four defaulted, validated fields: repetitions, ease_factor, interval, due. Nothing reads or writes them yet" — true, and missing three of the four sections. --fill is fine for a one-line fix; for a ticket, write the file. (--body-file - reads standard input, if you would rather pipe it from a heredoc.)

The commands

$ gh pr create --title "Add review state to Card" --body-file pr1.md
https://github.com/perro-ruidoso/flashcards-w3probe/pull/4

# fix the body after the fact — the keyword included:
$ gh pr edit 4 --body-file pr1.md

# see what would be created without creating it:
$ gh pr create --title "…" --body-file pr1.md --dry-run

From the manual: --dry-run "Print details instead of creating the PR. May still push git changes"; --template <file> uses "Template file to use as starting body text"; and on gh pr edit, "Without an argument, the pull request that belongs to the current branch is selected." A repository can also ship a pull-request template so that the four headings appear in every new body — that is a Week 5 configuration item for your Instance, not a requirement now.

Hands-on checklist

For the PR you open for ticket A in Assignment A3. check_a3.py reads the four headings and the keyword; the rubric reads what is under them.

Self-check

1. The Scope section of PR #4 says "Nothing else. Persistence is #2; the scheduler is a later ticket." What is that sentence doing for the reviewer?

B. Scope's second job is to say what was deliberately not touched. There is no length check (A); #2 is a separate review by design (C); a bare #2 creates a cross-reference, not a dependency edge (D — dependencies are Week 2's flags).

2. Why does the page say a body produced by --fill is not a PR body, even when the commit message is accurate?

C. The audiences differ. --fill-first is the first-commit variant (A is not --fill); nothing strips headings (B); the manual says --title alongside --fill takes precedence (D).

3. Which Risk section would the rubric mark "Excellent"?

A. It names a concrete failure mode (old files without the keys), the path that handles it, and the test that pins it. B and D are adjectives; C confuses correctness with risk — green checks did not catch the drive-by PR either.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

The four PR-body sections, and the question each answers?
Intent (why; what becomes true), Scope (what, and what not), Verification (how you know), Risk (what could break and how you would know).
What does Scope say that the diff cannot?
What was deliberately left out, and which ticket owns it — "Nothing else. Persistence is #2."
What makes a Verification section good?
Numbers and command names: "pytest: 26 passed (20 before); ruff check, ruff format --check, mypy: clean."
Why not gh pr create --fill for a ticket PR?
It copies commit messages, written for the history; a body is for a reviewer and needs scope, verification, risk.
How do you fix a body after opening the PR?
gh pr edit N --body-file file.md; with no argument it edits the current branch's PR.
What does --dry-run do on gh pr create?
"Print details instead of creating the PR. May still push git changes."
Where does GitHub define "pull request description"?
The linking page: "the summary text added by the author when they created the pull request."
Ask your teacher

After Claude Code implements a ticket, ask it to draft the four-section body — then check its Verification section against the terminal: did it actually run the commands it quotes, with those numbers? An agent will happily write "tests pass" from memory. Make it paste the output. Bring anything still unclear to the weekly meeting.
