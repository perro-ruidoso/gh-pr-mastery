Splitting a Drive-by

Ticket #3 asked for one field on Card. The first PR for it touched seven files. This page reads that diff hunk by hunk, decides which hunks belong to #3, and shows the split: close the PR with a comment, open a clean one from a second linked branch, and let the evidence stand.

M14 · Diff craft Bloom: Evaluate Assessed by: A3 (rubric); Quiz 1

Objective: Judge whether a diff is reviewable — single purpose, bounded size, no drive-by changes — and split one that is not.

The ticket, and the shape of the first PR

Issue #3, Tag field on Card: tags: tuple[str, ...] = (), two rejections in __post_init__, a has_tag method, tests, and a Tag entry in CONTEXT.md (the Seed's CLAUDE.md requires a new domain term to land in the same PR). Out of scope by name: persistence, every CLI command, flashcards list's output. Shape test, before reading a line: the ticket implies models.py, its test file, and CONTEXT.md. Four of the seven files are in layers the ticket named as out of scope. The PR body admitted it — "While I was in there: format_deck → render_deck (better name), a README roadmap section, and a tidier json_store docstring" — which is honest and still wrong. The sentence for this PR cannot be written without an "and."

Three of six hunk groups belong. The rename is the expensive one: a reviewer of #3 now has to confirm every caller of format_deck was updated, in files they had no reason to open, to approve a change about tags. That is what "drive-by" costs — not the lines, the attention.

The split

Closing with a comment that says what is being split out, then a second linked branch for the same issue with only the ticket's commit on it:

$ gh pr close 6 --comment "Splitting: the rename, the README section, and the docstring tidy are not #3. Reopening the ticket work alone as a new PR; the rename can be its own issue if anyone wants it."

(clean-3-snapshot was a local branch pointing at the ticket-only commit, kept before the drive-bys were added; in your case the equivalent is git rebase -i to drop the extra commit, or git checkout main -- <file> for each drive-by file, then a new commit.) Three files, all implied by the ticket. #7 was merged; #6 stays closed. The issue records both:

$ gh issue view 3 --json state,closedByPullRequestsReferences --jq '{state, prs: [.closedByPullRequestsReferences[].number]}'
{"prs":[7],"state":"OPEN"}      # before #7 merged; #6 is closed and not listed

$ gh pr list --state all --json number,state,changedFiles,closingIssuesReferences --jq '.[] | select(.closingIssuesReferences[].number == 3) | "#\(.number) \(.state) files=\(.changedFiles)"'
#7 MERGED files=3
#6 CLOSED files=7

That last listing is what check_a3.py reads for M14: one issue, an earlier PR closed unmerged with more files than a later merged one. The checker records that a split happened; whether the split was right — whether the rename deserved its own issue, whether the README line was worth anything — is the rubric's question, and yours.

The drive-by was green

PR #6 passed lint, tests, and mypy. Nothing automated objected to it. That is the point of an Evaluate objective: the machine can tell you a diff is correct; only a reader can tell you it is one thing.

Hands-on checklist

The exercise for A3. Do it on your own PR for ticket A, or reproduce it deliberately as the throwaway did.

Self-check

1. Of PR #6's seven files, which set belongs to ticket #3 and why?

D. Criterion 4 in #3 explicitly requires the CONTEXT.md entry (A is wrong about that). "Eventually" (C) is a different ticket, by definition. Out-of-scope is the fence M07 taught, not advice (B).

2. Why is the format_deck → render_deck rename the most expensive of the three drive-bys?

B. The cost is attention: correctness of a rename is checked at its call sites, which live in the CLI and its tests, not in the model. Line count (C) was small; the name's merit (D) is beside the point; the package is not published (A).

3. What does check_a3.py actually verify about the split, and what does it leave to the rubric?

A. The checker grades evidence — the pair of PRs and their sizes — and never judgement. It does not read comments (B) or impose a file limit (C); and there is evidence to read (D).

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

PR #6's shape versus ticket #3's implied files?
7 files, +50 −10; the ticket implies 3 (model, its tests, CONTEXT.md). Four files were in layers the ticket named out of scope.
The three drive-bys in PR #6?
A CLI rename (format_deck → render_deck) with its tests, a README Roadmap section, a rephrased json_store docstring.
What does a drive-by cost a reviewer?
Attention, not lines: the rename had to be checked at call sites in files unrelated to the ticket.
The three-step split?
gh pr close N --comment "Splitting: …"; gh issue develop <issue> --name <clean>; commit only the ticket's work and open a new PR.
What evidence of the split survives on GitHub?
Two PRs referencing one issue: #6 CLOSED with 7 files, #7 MERGED with 3. closedByPullRequestsReferences lists only #7.
Did CI catch the drive-by?
No — #6 was green. Correctness is the machine's; "one thing" is the reader's.
Two ways to remove a drive-by from a branch?
git rebase -i to drop its commit, or git checkout main -- <file> per file and recommit.
