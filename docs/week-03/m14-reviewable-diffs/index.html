What a Reviewable Diff Looks Like

A diff is reviewable when a reviewer can hold the whole of it in their head, say in one sentence what it is for, and find nothing in it that the sentence does not cover. Three tests, in that order, applied to a real pull request.

M14 · Diff craft Bloom: Evaluate Assessed by: A3 (rubric); Quiz 1

Objective: Judge whether a diff is reviewable — single purpose, bounded size, no drive-by changes — and split one that is not.

M14 pages 1What a Reviewable Diff Looks Like 2Splitting a Drive-by

Why this is an agentic-coder skill

When Claude Code implements a ticket, it produces a diff you did not type. You are its first reviewer, and you are the one who decides whether it goes to a second. The course's mission puts the bottleneck at "reviewing what comes back"; this objective is the eye you bring to that. There is no GitHub feature for it and no primary source — RESOURCES.md lists it as a course exercise "built on the cohort's own PRs." The nearest practitioner source is Google's engineering-practices guide on small changes, quoted here as ancillary material: "the right size for a CL is one self-contained change," which "makes a minimal change that addresses just one thing," and "100 lines is usually a reasonable size for a CL, and 1000 lines is usually too large, but it's up to the judgment of your reviewer."

The three tests

TestQuestion to askHow to check it from the terminal
Single purposeCan you state what the diff does in one sentence that names the ticket, and does every hunk serve that sentence?gh pr diff N --name-only — every file should be one the ticket implies
Bounded sizeCan a reviewer read it in one sitting, with the tests, and still have attention left for the arithmetic?gh pr view N --json additions,deletions,changedFiles
No drive-bysIs there a hunk a reviewer would have to ask about — a rename, a reformat, a doc edit — that the ticket did not ask for?gh pr diff N, read hunk by hunk against the ticket's acceptance criteria

The order matters. Shape first (--name-only, the counts), then content. A seven-file diff for a one-field ticket fails before you have read a line, and page 2 is exactly that case. Note also that gh pr diff has no --stat — the flag was tried and rejected as unknown flag: --stat on 2.100.0; the size numbers come from gh pr view --json.

A diff that passes: PR #4

Ticket #1 on the throwaway Instance: add review state to Card — four defaulted fields, validated, nothing reads or writes them yet. Shape first:

$ gh pr diff 4 --name-only
src/flashcards/domain/models.py
tests/domain/test_models.py

$ gh pr view 4 --json additions,deletions,changedFiles,files --jq '{additions, deletions, changedFiles, files: [.files[] | "\(.path) +\(.additions) -\(.deletions)"]}'
{"additions":63,"changedFiles":2,"deletions":0,"files":["src/flashcards/domain/models.py +16 -0","tests/domain/test_models.py +47 -0"]}

Apply the sentence test: "Adds four defaulted review-state fields to Card and validates them." The import serves it, the docstring serves it, the fields serve it, the three checks serve it. Nothing else is in the file's diff. The test file adds four tests that pin the defaults, a populated card, dataclasses.replace, and the three rejections — each one answering an acceptance criterion in the ticket. A reviewer who has read the ticket can check the whole PR against it without asking a question, which is the standard M07 set for tickets and this objective sets for diffs.

Reviewable is not the same as small

PR #5 on the same Instance touched five files after its parent merged (M16 page 2 explains why) and three after a rebase. The three-file version is reviewable; the five-file version was the same work with another PR's changes mixed in by the merge base, and a reviewer would have had to re-read #4's hunks to find #5's. Size is a symptom; the disease is anything in the diff that the one sentence does not cover.

Hands-on checklist

Do this on the PR you open for ticket A in Assignment A3, before you ask anyone to review it.

Self-check

1. Why does the page insist on --name-only and the size counts before reading the diff's content?

C. Shape is a cheap, decisive first test: seven files for a one-field ticket is a verdict on its own. A and B invent constraints; D describes a readable format, not a reason.

2. Which claim about PR #4 is the evidence that it has a single purpose?

B. The test is the sentence, and every hunk serving it. Additive-only (A) and file counts (C) are shape, not purpose; a green CI (D) says nothing about scope — the drive-by PR on page 2 was green too.

3. The page says a five-file PR #5 was "the same work" as the three-file version. What made the larger one less reviewable?

A. After a squash-merged parent, the child's merge base moved and #4's changes showed up again (M16 page 2). Nothing was added by the author (B); CI (C) and rendering (D) are not the issue.

The three reviewability tests, in order?
Single purpose (one sentence covers every hunk), bounded size (one sitting), no drive-bys (nothing the ticket did not ask for).
Two commands that show a diff's shape before its content?
gh pr diff N --name-only and gh pr view N --json additions,deletions,changedFiles.
Does gh pr diff have --stat?
No — "unknown flag: --stat" on 2.100.0. It has --name-only, --patch, --exclude, --web.
PR #4's shape?
2 files (model + its test file), +63 −0. Every hunk serves "adds four defaulted review-state fields to Card and validates them."
The ancillary source's size guidance?
Google eng-practices: "100 lines is usually a reasonable size for a CL, and 1000 lines is usually too large, but it's up to the judgment of your reviewer."
Why is "reviewable" not the same as "small"?
PR #5 grew to five files with another PR's merged hunks in it — same work, less reviewable. Size is a symptom; the test is the sentence.
Who is the first reviewer of a diff Claude Code wrote?
You. The mission puts the bottleneck at "reviewing what comes back."
Ask your teacher

Before opening your next PR, ask Claude Code: "list every file this branch changes against main, and for each one tell me which acceptance criterion in issue N required it." A file it cannot justify is a drive-by — ask it to move that change to a separate branch. Bring anything still unclear to the weekly meeting.
