The skill, as installed

From ~/.agents/skills/resolving-merge-conflicts/SKILL.md, read 2026-09-13. Its front matter: description: "Use when you need to resolve an in-progress git merge/rebase conflict." — no disable-model-invocation, so Claude Code may reach for it on its own when it sees a conflict, and you can type it. The body, verbatim:

resolving-merge-conflicts/SKILL.md — body
  1. See the current state of the merge/rebase. Check git history, and the conflicting files.
  2. Find the primary sources for each conflict. Understand deeply why each change was made, and what the original intent was. Read the commit messages, check the PRs, check original issues/tickets.
  3. Resolve each hunk. Preserve both intents where possible. Where incompatible, pick the one matching the merge's stated goal and note the trade-off. Do not invent new behaviour. Always resolve; never --abort.
  4. Discover the project's automated checks and run them — typically typecheck, then tests, then format. Fix anything the merge broke.
  5. Finish the merge/rebase. Stage everything and commit. If rebasing, continue the rebase process until all commits are rebased.

Two things to notice before the run. Step 2 is the one a human skips: it sends the agent to the commits, PRs, and tickets behind each side before it touches a line, which is what makes step 3's "preserve both intents" possible. And step 3's last sentence — "Always resolve; never --abort" — is a policy: the skill is invoked to finish the merge, not to decide whether to.

Step 2 — find the primary sources

$ git log -1 --format="%h %s%n%n%b" 3b9501a
3b9501a Reject a datetime in Card.due

A datetime passes the date annotation at runtime (it is a subclass) and
isoformat() would then write a timestamp the loader rejects. Guard it at
the model so the file format stays YYYY-MM-DD.

$ git log -1 --format="%h %s" 78e17a7
78e17a7 Tag field on Card (#7)
$ gh pr view 7 --json title,body --jq '"#7 \(.title)", .body' | head -12
#7 Tag field on Card
## Intent
Add a `tags` field to `Card` so review sessions (T10) and stats (T13) can be narrowed by topic. Replaces #6, which carried three unrelated changes; this PR is the ticket and nothing else.

## Scope
- `src/flashcards/domain/models.py`: `tags: tuple[str, ...] = ()`, rejection of empty and duplicate tags, `has_tag`.
- `tests/domain/test_models.py`: default, exact-match `has_tag`, both rejections.
- `CONTEXT.md`: a **Tag** entry (CLAUDE.md: a new domain term lands with the PR that introduces it).

$ gh issue view 3 --json body --jq .body | sed -n '/Acceptance/,/Out of scope/p'
## Acceptance criteria
- [ ] `Card` has `tags: tuple[str, ...] = ()`; a tuple, not a list, because `Card` is frozen and must stay hashable.
- [ ] `Card.__post_init__` rejects an empty-string tag and a duplicate tag with `ValueError`.
- [ ] `Card.has_tag(tag)` returns whether the card carries `tag`, exact match, case-sensitive.
…

Now each side has a stated intent that is not a guess. HEAD's docstring clause exists to document the YYYY-MM-DD file format the guard protects (commit body); main's tags docstring line exists because criterion 1 of #3 adds the field (ticket). Neither side's change is about the other's. That is the finding step 3 needs: the two intents are independent, so both survive.

Step 3 — resolve each hunk

Resolution: keep HEAD's two-line clause, then main's tags line — the docstring reads in field order. In the test file, keep HEAD's test, a blank pair, then main's three; either order would be correct and this one keeps each side's tests contiguous. Step 4 — the project's checks

The Seed's CLAUDE.md names them: "pytest; ruff check . && ruff format --check . — exactly what CI runs; mypy."

$ pytest
..................................                                       [100%]
34 passed in 0.17s
$ ruff check . && ruff format --check .
All checks passed!
15 files already formatted
$ mypy
Success: no issues found in 7 source files

Thirty-four: the branch's 30 before the merge plus #7's four (three tag tests and the parametrized pair count as four cases). A resolution that kept only one side would have run fewer.

Step 5 — finish the merge

$ git add src/flashcards/domain/models.py tests/domain/test_models.py
$ git status --short
M  CONTEXT.md
M  src/flashcards/domain/models.py
M  tests/domain/test_models.py
$ git commit --no-edit
[2-persist-review-state dd3293d] Merge remote-tracking branch 'origin/main' into 2-persist-review-state
$ git log --oneline --graph -5
*   dd3293d Merge remote-tracking branch 'origin/main' into 2-persist-review-state
|\
| * 78e17a7 Tag field on Card (#7)
* | 3b9501a Reject a datetime in Card.due
* | 37d4731 Persist review state in the deck file
|/
* 0b9a901 Add review state to Card (#4)
$ git push
   3b9501a..dd3293d  2-persist-review-state -> 2-persist-review-state

--no-edit keeps git's default merge message. The commit dd3293d has two parents — 3b9501a and 78e17a7 — and that two-parent commit is the artifact check_a3.py looks for: GET /repos/O/R/pulls/5/commits lists it with parents of length 2. A rebase-based resolution would leave no such commit, which is why the assignment asks for the merge route (or an explanation in the write-up).

Merge or rebase to resolve?

The skill handles both ("If rebasing, continue the rebase process"). The course asks for git merge origin/main on the stacked branch for two reasons: the resolution is one commit that the reviewer can read on its own, and it leaves the two-parent commit as evidence. A rebase re-applies each of the branch's commits onto main and may ask you to resolve the same hunk more than once — the merge-methods page's warning about squash-merged long-running branches, in practice. Either way, once the branch is squash-merged into main, the resolution commit disappears into the squash; only the PR's commit list remembers it.

Hands-on checklist

Item 5 of Assignment A3, from the conflict on page 1 to the merge.

Self-check

1. Why does the skill's step 2 send the agent to commit messages, PRs, and tickets before resolving anything?

C. The run showed it: the commit body explained the docstring clause, the ticket explained the tags line, and only then was "independent intents, keep both" a finding rather than a guess. A, B, and D invent mechanisms.

2. After the resolution, pytest reported 34 passed. What is that number evidence of?

A. Counting is a cheap check on "preserve both intents." Step 4 runs checks; it does not write tests (B). There was a two-parent merge commit (C). Nothing was duplicated (D) — the four are #7's tests.

3. Which artifact tells check_a3.py that a conflict was resolved on the stacked branch?

D. Two parents is structural and survives any message. There is no such event (A); the message is not parsed (B); file counts change for other reasons too (C — page 2 of M16 showed 3 → 5 → 3 with no conflict at all).

Ask your teacher

Run the skill on your own conflict and, when it finishes, ask Claude Code: "for each hunk you resolved, which side's line did you keep and which primary source told you why?" An answer that names commit messages and tickets is the skill working; an answer that says "the more complete version" is the skill skipped. Bring anything still unclear to the weekly meeting.
