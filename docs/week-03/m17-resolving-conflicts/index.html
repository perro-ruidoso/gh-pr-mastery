Where the Conflict Came From

Two tickets were unblocked by the same parent, worked at the same time, and both touched the class the parent had just reshaped. One merged first. The other became CONFLICTING. Before resolving anything, this page reads the conflict as evidence about the backlog.

The frontier after #1 merged

Once #1 (review state on Card) merged, two tickets had every blocker closed: #2 (persist the state — the stacked PR #5, retargeted and rebased on M16 page 2) and #3 (a tag field on Card). Week 2 called this the frontier: tickets a concurrent agent session could pick up. Both were picked up. Both, it turned out, needed to touch models.py:

  • #2, while persisting due, found that a datetime passes the date annotation at runtime and would write a timestamp the loader rejects. It added a guard in Card.__post_init__ and a sentence to the due docstring, plus a test — commit 3b9501a, "Reject a datetime in Card.due."
  • #3 added tags to Card: a docstring line right after due's, two checks in __post_init__, a has_tag method, and three tests at the end of the same test file — PR #7, squash-merged at 17:09:14.

Same class, same docstring, same __post_init__, same end of the same test file. Neither ticket was wrong to touch them — Card is the domain model; every ticket on this frontier reshapes it. GitHub's merge-conflicts page: "Merge conflicts often happen when people make different changes to the same line of the same file."

GitHub notices, slowly

$ gh pr view 5 --json mergeable,mergeStateStatus --jq '{mergeable, mergeStateStatus}'   # before #7 merges
{"mergeStateStatus":"CLEAN","mergeable":"MERGEABLE"}
$ gh pr merge 7 --squash
$ sleep 20
$ gh pr view 5 --json mergeable,mergeStateStatus --jq '{mergeable, mergeStateStatus}'   # after
{"mergeStateStatus":"UNKNOWN","mergeable":"UNKNOWN"}
$ gh pr view 5 --json mergeable,mergeStateStatus --jq '{mergeable, mergeStateStatus}'   # 35 s later
{"mergeStateStatus":"DIRTY","mergeable":"CONFLICTING"}

Twenty seconds after #7 merged, GitHub had not yet recomputed #5's mergeability and answered UNKNOWN; fifteen seconds after that, CONFLICTING / DIRTY. A script that reads mergeable immediately after a merge to main must treat UNKNOWN as "ask again," not as either answer. (Re-run on 2026-09-14, after PR #5 had merged, the same command printed UNKNOWN/UNKNOWN again and always will: GitHub does not compute mergeability for a merged PR. Same value, different reason — read state alongside it.) The docs on what the state means: "Merge conflicts block merging because Git cannot safely choose which version of the conflicting content to keep. You must resolve all merge conflicts before you can merge a pull request on GitHub. If your pull request has a merge conflict between the compare branch and base branch, the Merge pull request button is deactivated until the conflicts are resolved."

Reproducing it locally

The docs give two routes: "Simple line conflicts can often be resolved on GitHub … More complex conflicts must be resolved in a local clone and pushed back to the pull request branch." The course uses the local route always, because the skill on page 2 needs the repository's history and its checks, and because the web editor's own warning applies: "Resolving conflicts on GitHub merges the entire base branch into the head branch." Locally, the same merge is explicit:

Read the markers the way git-merge's manual describes them: "The area where a pair of conflicting changes happened is marked with markers <<<<<<<, =======, and >>>>>>>. The part before the ======= is typically your side, and the part afterwards is typically their side." Here "your side" is HEAD, the stacked branch; "their side" is origin/main. The docstring hunk is a real conflict — both sides replaced the same line after "has never been." The second hunk in the same file is not a conflict: the datetime guard (ours, + in the first column) and has_tag (theirs, + in the second) landed in different places and git merged them itself. The manual again: "non-overlapping ones … are incorporated in the final result verbatim." The test-file conflict is the classic one — both branches appended tests at the end of the file, and git cannot know which order was meant.

What the conflict says about the backlog

The objective asks you to explain what caused it, and "both touched models.py" is only half an answer. The other half is about edges. #2 and #3 had no edge between them, correctly: neither needs the other to start. But they share a surface — the domain model — and sharing a surface is not a dependency, it is a conflict risk, which a backlog cannot record and a stack cannot prevent. The honest explanation names the surface, says the edge was right to be absent, and says what would have avoided the collision: land the smaller model change first (#3 was three files) or, in one agent session, sequence the two tickets rather than parallelise them. That is the sentence Assignment A3's write-up asks for.

Hands-on checklist

Item 5 of Assignment A3, up to the point where the skill takes over on page 2.

Self-check

1. Twenty seconds after #7 merged, PR #5 reported mergeable: UNKNOWN. What should a script do with that value?

B. Fifteen seconds later the same query returned CONFLICTING / DIRTY. Neither guess (A, C) is safe; D is wrong about when the value appears.

2. In the models.py conflict output, the datetime guard and has_tag appear near each other with + in different columns and no markers. What does that mean?

D. git-merge: non-overlapping changes "are incorporated in the final result verbatim." The combined diff's two columns mark origin; only marker-bounded regions are conflicts. A, B, and C misread the format.

3. Should the backlog have recorded #3 as blocked by #2 to prevent this conflict?

A. M10's edge test: "could this ticket be started without that one?" #3 could. Recording a false edge to avoid a merge conflict would hide parallelism the sequencer exercise exists to find (B, C). Conflicts arise between any two branches that touch the same lines (D).

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

Which two tickets conflicted on the throwaway, and on what?
#2 (stacked PR #5, datetime guard) and #3 (tags, PR #7): the Card docstring line after due, and the end of tests/domain/test_models.py.
Values of mergeable seen over one minute after the sibling merged?
MERGEABLE → UNKNOWN (20 s) → CONFLICTING with mergeStateStatus: DIRTY (35 s). Ask again on UNKNOWN.
GitHub's definition of a merge conflict's effect?
"Merge conflicts block merging because Git cannot safely choose which version of the conflicting content to keep."
Which side is before =======?
"Typically your side" — HEAD, the branch you are on; after it, "their side" — what you merged in (origin/main).
git status --short code for a conflicting file?
UU — both modified. A file merged cleanly from the other side shows M, already staged.
Why did the datetime guard and has_tag not conflict?
They did not overlap; git incorporated non-overlapping changes "verbatim." Only marker-bounded regions are conflicts.
Should a shared file be recorded as a blocking edge?
No. An edge means "cannot start without"; a shared surface is a conflict risk, not a dependency.
Why resolve locally rather than in GitHub's editor?
The skill needs history and the project's checks; and the web editor "merges the entire base branch into the head branch" anyway.
Ask your teacher

Before resolving, ask Claude Code: "list every open ticket on my frontier and, for each pair, the files both are likely to touch." Then ask which pairs are conflict risks and which are dependencies, and make it defend the difference in M10's terms. Bring anything still unclear to the weekly meeting.
