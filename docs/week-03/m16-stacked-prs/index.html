Stacking on a Branch That Is Not Main

Ticket #2 is blocked by #1. If you wait for #1 to merge before starting #2, the edge costs you a day. If you branch #2 from #1's branch and open its PR against that branch, the edge is expressed in code, both PRs can be reviewed, and #2's diff shows only #2's work. That is a stacked PR.

M16 · Stacking Bloom: Apply Assessed by: A3 (checker)

Objective: Build a stacked PR on a dependent branch, set its base correctly, and retarget it after its parent merges.

The definition, and why the base is the whole trick

CONTEXT.md: a Stacked PR is "a pull request whose base is another open PR's head branch, expressing a work dependency in code. Needs retargeting when its parent merges." Recall M02: a PR is a request to merge a head ref into a base ref, and GitHub's Files-changed view is the three-dot diff from the merge base of those two refs (M03). If #2's branch starts at #1's tip and its PR's base is #1's branch, the merge base is #1's tip, and the diff is exactly what #2 added. Set the base to main instead and the diff is #1's work plus #2's — reviewable by nobody. The base is not a detail; it is what makes the second PR readable.

The Week 2 backlog's blocking edges are what tell you when a stack is warranted: an edge from #1 to #2 means #2 cannot start without #1, so #2's branch has to contain #1's commits, so #2's PR has to base on #1's branch until #1 merges. A ticket with no incoming edge branches from main like any other — #3 on the throwaway did, on M17 page 1, and that is where the conflict came from.

Building the stack

M13 page 1 already showed the branch: gh issue develop 2 --name 2-persist-review-state --base 1-add-review-state-… --checkout, which started the branch at #1's commit and wrote branch.2-persist-review-state.gh-merge-base into git config. After implementing #2 and pushing, the PR was opened with no --base flag:

$ git push -u origin HEAD
   58cab2d..aa8afb6  HEAD -> 2-persist-review-state
$ gh pr create --title "Persist review state in the deck file" --body-file pr2.md
https://github.com/perro-ruidoso/flashcards-w3probe/pull/5

$ gh pr view 5 --json number,baseRefName,headRefName,closingIssuesReferences,changedFiles,additions,deletions --jq '{number, base: .baseRefName, head: .headRefName, closes: [.closingIssuesReferences[].number], changedFiles, additions, deletions}'

$ gh pr diff 5 --name-only
src/flashcards/storage/json_store.py
tests/conftest.py
tests/storage/test_json_store.py

Three things to read off that output. The base is #1's branch, chosen by gh pr create from the config entry --base wrote — the manual: "If not provided, the value of gh-merge-base git branch config will be used." The diff is three files, all storage-side: models.py, which #1 changed, is not in it, because it is on both sides of the merge base. And closes is empty, twenty seconds after creation, with Closes #2 in the body — the M15 page 2 rule, seen from the stacked side: the keyword is ignored on a non-default base. The PR body says it is stacked

PR #5's Intent section says, in its second sentence: "Stacked on #4 (branch 1-add-review-state-…), which adds the fields this PR persists." The course repo's PR #14 did the same: "Stacked on #12 … Merge #12 first, then retarget this PR to main." A reviewer who lands on the child should be told where the parent is and what will happen to the base — GitHub's UI shows the base branch name, but not why.

Both PRs are reviewable at once

This is the payoff. #4 and #5 were open together; CI ran on both (each got lint and test green); a reviewer could read #4's two files and #5's three files as two separate units, in either order. The ancillary source for M14 calls this "stacking multiple changes on top of each other": "write one small CL, send it off for review, and then immediately start writing another CL based on the first CL." The Week 2 edge said #2 could not start without #1 — but "start" meant the code, not the review.

Hands-on checklist

Item 4 of Assignment A3; do it before merging A if you want the realistic order.

Self-check

1. PR #5's diff lists three storage files and not models.py, which #1 changed. Why?

B. The three-dot diff from M03: changes since the merge base of head and base. With base = #1's branch, #1's work is not "since." No flag hides files (A), GitHub has no parent-aware exclusion (C), and the branch still contains #1's commit (D — git log showed it).

2. gh pr create was run with no --base and produced a PR against #1's branch. Where did the base come from?

D. The manual's resolution order: --base, then the gh-merge-base config, then the default branch. The upstream (A) is the same-named remote branch, not the parent; GitHub infers nothing (B); the body is never parsed for a base (C).

3. A ticket has no incoming blocking edge. Should its branch be stacked on the branch of the ticket you happen to be working on?

A. The stack expresses a recorded work dependency; without one it is false structure, and page 2 shows the cost on retarget. Linear history (B) is a merge-method question (Week 5). Shared files (C) are a reason to expect a conflict, not to stack — M17. GitHub has no one-child limit (D).

Definition of a Stacked PR (CONTEXT.md)?
"A pull request whose base is another open PR's head branch, expressing a work dependency in code. Needs retargeting when its parent merges."
Why does the child's diff show only the child's work?
The base is the parent branch, so the merge base is the parent's tip; the parent's changes are on both sides.
Two commands that build a stack?
gh issue develop B --base <A-branch> --checkout, then gh pr create with no --base (it reads gh-merge-base).
PR #5's state at creation?
base = #1's branch, 3 files, +88 −6, closes: [] despite Closes #2 in the body.
When is a stack warranted?
When the tracker records B as blocked by A — B's branch must contain A's commits. No edge, no stack.
What can happen while both PRs are open?
CI runs on both; each is reviewed as its own unit. The edge blocks the code, not the review.
What should the child PR's body say?
That it is stacked, on which PR and branch, and what happens to the base when the parent merges.
Ask your teacher

Ask Claude Code to explain, with git merge-base on your own two branches, why PR B's diff excludes A's changes — and then to predict what the diff will contain after A is squash-merged and B is retargeted, before you read page 2. Bring anything still unclear to the weekly meeting.
