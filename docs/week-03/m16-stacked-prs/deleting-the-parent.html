What Deleting the Parent Does

GitHub's docs promise that deleting a merged head branch retargets any PR stacked on it. Two live probes, ten minutes apart, on the same repository: through gh pr merge --delete-branch the child PR was closed; through the repository's Automatically delete head branches setting it was retargeted. Which path deleted the branch decides what happens to the stack.

M16 · Stacking Bloom: Apply Assessed by: A3 (checker)

Objective: Build a stacked PR on a dependent branch, set its base correctly, and retarget it after its parent merges.

What the docs say

GitHub's merging page, in a note: "If you delete a head branch after its pull request has been merged, GitHub checks for any open pull requests in the same repository that specify the deleted branch as their base branch. GitHub automatically updates any such pull requests, changing their base branch to the merged pull request's base branch." The same page's CLI tab gives the example gh pr merge 523 --squash --body "my squash commit" --delete-branch — the flag the manual describes as "Delete the local and remote branch after merge." Read together, they suggest that --delete-branch on a parent is safe for its children. It is not, and the difference took two probes to see.

Probe 1: gh pr merge --delete-branch

Two throwaway branches with one-line README changes — probe-parent (PR #8, base main) and probe-child stacked on it (PR #9, base probe-parent):

$ gh pr view 9 --json baseRefName --jq .baseRefName
probe-parent
$ gh pr merge 8 --squash --delete-branch
$ sleep 10
$ gh pr view 9 --json baseRefName,state --jq '{base: .baseRefName, state}'
{"base":"probe-parent","state":"CLOSED"}

$ gh api repos/perro-ruidoso/flashcards-w3probe/issues/9/timeline --jq '.[] | "\(.created_at)  \(.event)  \(.actor.login // "")"'
null  committed
2026-09-13T17:13:34Z  base_ref_deleted  acatlin
2026-09-13T17:13:35Z  closed  acatlin
$ gh pr view 8 --json mergedAt --jq .mergedAt
2026-09-13T17:13:33Z

Merged at 17:13:33; the child's base branch deleted at 17:13:34 (base_ref_deleted); the child closed at 17:13:35, base still probe-parent, no base change event of any kind. The actor on both events is the user who ran the command, not GitHub. A stacked PR with an issue, a body, and a review on it would have been closed the same way — reopenable, and retargetable by hand afterwards, but closed.

Probe 2: the repository setting

Same shape, with Automatically delete head branches turned on (the docs: "On the 'General' settings page … Under 'Pull Requests', select or deselect Automatically delete head branches"; from the terminal it is the delete_branch_on_merge field) and a plain gh pr merge --squash with no flag:

$ gh api -X PATCH repos/perro-ruidoso/flashcards-w3probe -F delete_branch_on_merge=true --jq .delete_branch_on_merge
true
… probe2-parent → PR #10 (base main); probe2-child → PR #11 (base probe2-parent) …
$ gh pr merge 10 --squash
$ sleep 20
$ gh pr view 11 --json baseRefName,state --jq '{base: .baseRefName, state}'
{"base":"main","state":"OPEN"}

$ gh api repos/perro-ruidoso/flashcards-w3probe/issues/11/timeline --jq '.[] | "\(.created_at)  \(.event)  \(.actor.login // "")"'
null  committed
null  committed
2026-09-13T17:15:53Z  automatic_base_change_succeeded  acatlin
$ gh pr view 10 --json mergedAt --jq .mergedAt
2026-09-13T17:15:51Z
$ gh api graphql -f query='{ repository(owner:"perro-ruidoso", name:"flashcards-w3probe") { pullRequest(number:11) { timelineItems(itemTypes:[AUTOMATIC_BASE_CHANGE_SUCCEEDED_EVENT], first:10) { nodes { ... on AutomaticBaseChangeSucceededEvent { createdAt oldBase newBase } } } } } }' --jq '.data.repository.pullRequest.timelineItems.nodes[]' 
{"createdAt":"2026-09-13T17:15:53Z","newBase":"main","oldBase":"probe2-parent"}

Merged at 17:15:51; the child retargeted to main at 17:15:53 by an automatic_base_change_succeeded event, still open. This is the behaviour the docs describe — and it is triggered by GitHub's own deletion of the branch after the merge, not by a client deleting the ref. gh pr merge --delete-branch deletes through the API after the merge completes, and GitHub treats that as any other branch deletion: the child's base is gone, so the child is closed.

The rule

Never pass --delete-branch when merging a PR that another open PR is stacked on. Retarget the child first (page 2), then delete the parent branch if you want to. The automatic-deletion setting is safe for stacks — and the retargeted child still carries the parent's commits, so the rebase on page 2 is still needed before review. check_a3.py accepts either a BaseRefChangedEvent or an AutomaticBaseChangeSucceededEvent as the retarget; a child that was closed and reopened will show the manual event when you retarget it.

What the probes cost, and what they did not test

Four PRs and four branches on the throwaway, restored afterwards (delete_branch_on_merge back to false, #11 closed). Not tested: deleting the branch from the web UI's Delete branch button on a merged PR, or with git push origin --delete. The docs' sentence is worded for the first; the second is presumably the API path. If you try either, read the child's timeline afterwards and add the row.

Hands-on checklist

No assignment item depends on this page, but the rule does. Verify it once so you never learn it on a real stack.

Self-check

1. A parent PR is merged with gh pr merge --squash --delete-branch. What happens to the open child stacked on it?

C. Probe 1: 17:13:33 merged, 17:13:34 base_ref_deleted, 17:13:35 closed. The docs' retarget (A) is what probe 2 produced, through the repository setting. Nothing is refused (D) or restored (B).

2. Under which condition did the child PR get an automatic_base_change_succeeded event?

A. Probe 2 changed exactly one thing — delete_branch_on_merge=true and no --delete-branch flag — and the child was retargeted two seconds after the merge. Both probes used squash (B); the probe PRs had no keywords (C); timing (D) was similar in both.

3. You have retargeted the child by hand and want the parent branch gone. What is the safe order?

B. Once the child's base is main, the parent branch is not referenced by any open PR and deleting it affects nothing. A is the order that closes the child. The diff is computed from main after the retarget (C). D works but delays the cleanup for no reason.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

What the docs promise when a merged head branch is deleted?
GitHub "automatically updates any such pull requests, changing their base branch to the merged pull request's base branch."
What gh pr merge --delete-branch on a parent actually did to the child?
Closed it: base_ref_deleted 17:13:34, closed 17:13:35, base unchanged. No retarget.
What the Automatically delete head branches setting did to the child?
Retargeted it: automatic_base_change_succeeded 17:15:53, oldBase probe2-parent → newBase main, still open.
The rule for stacks?
Never --delete-branch a parent with an open child. Retarget the child first, then delete.
Three ways a child's base can change, and their events?
By hand → BaseRefChangedEvent; GitHub's auto-deletion → AutomaticBaseChangeSucceededEvent; API deletion → no change, base_ref_deleted + closed.
Field that turns the setting on from the terminal?
gh api -X PATCH repos/O/R -F delete_branch_on_merge=true.
After an automatic retarget, is the rebase still needed?
Yes — the child still carries the parent's commits, so its diff includes the squash-merged work until you rebase.
Ask your teacher

Show Claude Code the two probe transcripts and the docs' sentence, and ask it to explain the discrepancy. Then ask it what it would have said before seeing the probes — most agents will confidently describe the docs' behaviour for the --delete-branch case.
