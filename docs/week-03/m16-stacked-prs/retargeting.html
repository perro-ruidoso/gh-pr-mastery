Retarget, Then Look Again

The parent merges. The child's base still names a branch that is now behind main. One command changes the base; then three things happen at once — the closing link appears, the diff grows, and the timeline records the change — and one of them needs fixing before review.

M16 · Stacking Bloom: Apply Assessed by: A3 (checker)

Objective: Build a stacked PR on a dependent branch, set its base correctly, and retarget it after its parent merges.

Before: the parent merges, the child does not notice

PR #4 was squash-merged at 17:02:47 (without --delete-branch — page 3 is about why). Five seconds later, the child:

$ gh pr view 5 --json baseRefName,closingIssuesReferences,changedFiles --jq '{base: .baseRefName, closes: [.closingIssuesReferences[].number], changedFiles}'
{"base":"1-add-review-state-to-card-repetitions-ease-factor-interval-due-date","closes":[],"changedFiles":3}

Nothing changed. GitHub's base-branch page states it: "When you open a pull request, GitHub sets the base to the commit that branch references. If the branch is updated in the future, GitHub does not update the base branch's commit." The parent branch still exists, still points at 58cab2d, and #5 is still a request to merge into it. Left alone, merging #5 would put #2's work onto a branch nobody will ever merge again.

The retarget

The docs describe the web flow — "Next to the pull request title, click Edit title … In the base branch drop-down menu, select the base branch … click Change base" — with a warning worth reading first: "When you change the base branch of your pull request, some commits may be removed from the timeline. Review comments may also become outdated because the line of code that the comment referenced may no longer be part of the changes in the pull request." From the terminal, gh pr edit --base — "Change the base branch for this pull request":

$ gh pr edit 5 --base main
https://github.com/perro-ruidoso/flashcards-w3probe/pull/5

…fifteen seconds later:
$ gh pr view 5 --json baseRefName,closingIssuesReferences,changedFiles,additions,deletions,mergeable --jq '{base: .baseRefName, closes: [.closingIssuesReferences[].number], changedFiles, additions, deletions, mergeable}'
{"additions":151,"base":"main","changedFiles":5,"closes":[2],"deletions":6,"mergeable":"MERGEABLE"}

$ gh pr diff 5 --name-only
src/flashcards/domain/models.py
src/flashcards/storage/json_store.py
tests/conftest.py
tests/domain/test_models.py
tests/storage/test_json_store.py

Three things happened.

  1. The link appeared. closes went from [] to [2]; issue #2's timeline gained a connected event at 17:03:13, one second after the base change. The keyword had been in the body for three minutes; it took effect when condition one (M15 page 2) was met.
  2. The diff grew — from 3 files and +88 to 5 files and +151. The two new files are models.py and tests/domain/test_models.py: PR #4's work, which is already on main.
  3. The timeline recorded it. The event is what check_a3.py reads:
$ gh api graphql -f query='{ repository(owner:"perro-ruidoso", name:"flashcards-w3probe") { pullRequest(number:5) { timelineItems(itemTypes:[BASE_REF_CHANGED_EVENT], first:10) { nodes { ... on BaseRefChangedEvent { createdAt previousRefName currentRefName } } } } } }' --jq '.data.repository.pullRequest.timelineItems.nodes[]' 
{"createdAt":"2026-09-13T17:03:12Z","currentRefName":"main","previousRefName":"1-add-review-state-to-card-repetitions-ease-factor-interval-due-date"}

The REST timeline shows the same moment as base_ref_changed — the event-types reference: "The base reference branch of the pull request changed" — but without the branch names; GraphQL's BaseRefChangedEvent carries previousRefName and currentRefName, which is what lets a checker confirm the base went from a feature branch to main and not the other way.

Why the diff grew: the squash

PR #4 was squash-merged. GitHub's merge-methods page: "the pull request's commits are squashed into a single commit … merged into the default branch." That single commit, 0b9a901, has the same content as #1's branch commit 58cab2d but is a different commit. #5's branch contains 58cab2d; main contains 0b9a901; their merge base is the template's initial commit. The three-dot diff from there includes #1's changes. The same page says so under "Squashing and merging a long-running branch": "If you keep working on the same head branch after a squash merge, later pull requests can include commits that were already squashed into the base branch. This can make merge conflicts more likely and can force you to resolve the same conflicts more than once."

It was still MERGEABLE — git can merge identical changes made on both sides. The git-merge manual's conflict section lists exactly this among the hunks that resolve cleanly: lines "cleanly resolved because both sides changed the same way." But a reviewer of #5 would now have to read #4's hunks again to find #5's. The fix is a rebase:

$ git fetch origin main
$ git log --oneline origin/main..HEAD
aa8afb6 Persist review state in the deck file
58cab2d Add review state to Card
$ git merge-base origin/main HEAD
e474711

$ git rebase origin/main
warning: skipped previously applied commit 58cab2d
hint: use --reapply-cherry-picks to include skipped commits
Successfully rebased and updated refs/heads/2-persist-review-state.
$ git log --oneline origin/main..HEAD
37d4731 Persist review state in the deck file
$ git merge-base origin/main HEAD
0b9a901

$ git push --force-with-lease
 + aa8afb6...37d4731 2-persist-review-state -> 2-persist-review-state (forced update)

$ gh pr view 5 --json baseRefName,closingIssuesReferences,changedFiles,additions,deletions,commits --jq '{base: .baseRefName, closes: [.closingIssuesReferences[].number], changedFiles, additions, deletions, commits: [.commits[].oid[0:7]]}'
{"additions":88,"base":"main","changedFiles":3,"closes":[2],"commits":["37d4731"],"deletions":6}

Git noticed on its own that 58cab2d's patch was already upstream — "skipped previously applied commit" — and replayed only #2's commit onto main. The merge base moved from e474711 to 0b9a901, the diff is back to three files and +88, the link is intact, and the PR now has one commit. --force-with-lease rather than --force: it refuses if someone else pushed to the branch since your last fetch.

The order is: retarget, check the link, rebase, force-push

Retargeting first means the PR keeps its number, its review history, and its CI runs. Rebasing first and pushing to a PR whose base is still the parent branch gives a diff of everything since the parent branch diverged from main — worse, not better. And never rebase a branch someone else has checked out without telling them; the force-push rewrites the commits they have.

Hands-on checklist

Item 4 of Assignment A3, after A has merged.

Self-check

1. After gh pr edit 5 --base main, the diff grew from 3 files to 5 and was still MERGEABLE. What is the correct reading?

C. The merge base went from #1's tip to the initial commit (git merge-base printed e474711), so #1's changes are "since" again; git resolves "both sides changed the same way" without conflict. Nothing failed (A), nothing foreign arrived (B), GitHub adds no context files (D).

2. git rebase origin/main printed "skipped previously applied commit 58cab2d." What did git do and why is it right?

B. git log origin/main..HEAD afterwards showed only #2's commit (as 37d4731), and the PR diff returned to three files. The force-push is needed because the commit was rewritten, not because of a conflict (C). A and D misread the message.

3. Which sequence of the course repo's #12 → #14 timestamps shows the retarget happened after the parent merged and before the child did?

D. Parent's mergedAt, child's BaseRefChangedEvent, child's MergedEvent — the same three facts check_a3.py orders. B invents a trigger (page 3 shows the only automatic retarget, and it is branch deletion, not issue closure); A and C reason from things that do not imply the order.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

Does GitHub update a stacked PR when its parent merges?
No. "If the branch is updated in the future, GitHub does not update the base branch's commit." PR #5 was unchanged five seconds after #4 merged.
The retarget command?
gh pr edit N --base main — "Change the base branch for this pull request."
Three things that changed on PR #5 after the retarget?
closes [] → [2] (connected 17:03:13); diff 3 → 5 files; a BaseRefChangedEvent at 17:03:12 with previous/current ref names.
Why did the diff grow?
The parent was squash-merged: a new commit with #1's content. The merge base fell back to the initial commit, so #1's changes were "since" again.
Why was it still MERGEABLE?
git-merge: hunks "cleanly resolved because both sides changed the same way."
The fix, and what git printed?
git rebase origin/main → "skipped previously applied commit 58cab2d"; then git push --force-with-lease. Diff back to 3 files.
Course repo #12 → #14: merge, retarget, rebase, merge, close?
15:40:01 · 15:40:05 · 15:42:45 (force-push 32ac8c2 → 3af3c05) · 15:43:30 · 15:43:31.
Which timeline event has the branch names, REST or GraphQL?
GraphQL's BaseRefChangedEvent (previousRefName, currentRefName); REST's base_ref_changed has only the time.
