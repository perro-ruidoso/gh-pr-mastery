Six Skills, Six Situations

wayfinder

~/.agents/skills/wayfinder/SKILL.md · disable-model-invocation: true · on-ramp · in the plugin (whose copy says "decision tickets" for the installed "investigation tickets", renamed 2026-07-13)

description: "Plan a huge chunk of work — more than one agent session can hold — as a shared map of investigation tickets on your issue tracker, and resolve them one at a time until the way to the destination is clear."

The body opens: "A loose idea has arrived — too big for one agent session, and wrapped in fog: the way from here to the destination isn't visible yet." Its first rule is "Plan, don't do": "each ticket resolves a decision, and the map is done when the way is clear — nothing left to decide before someone goes and does the thing." The map is "a single issue on this repo's issue tracker, labelled wayfinder:map," its tickets are child issues with wayfinder:<type> labels (research, prototype, grilling, task), and blocking "uses the tracker's native dependency relationship" — the same Week 2 issue dependencies, used to draw a frontier of decisions instead of tasks. "Never resolve more than one ticket per session."

For: "we should add a mobile client" — nobody can say what it needs, what it excludes, or whether the API can serve it; you want a map of the decisions, on the tracker, that several sessions can work through. Not for: a feature you can already describe in a conversation — that is grill-with-docs then to-spec; ask-matt: "Where /grill-with-docs sharpens an idea you can hold in one session, wayfinder is for the idea you can't."

request-refactor-plan

~/.agents/skills/request-refactor-plan/SKILL.md · model-invocable · removed upstream 2026-08-05 (replaced, per its changeset, by /to-spec and /improve-codebase-architecture) · still installed on the course machine · not in the plugin

description: "Create a detailed refactor plan with tiny commits via user interview, then file it as a GitHub issue. Use when user wants to plan a refactor, create a refactoring RFC, or break a refactor into safe incremental steps."

Eight steps, of which the agent "may skip steps if you don't consider them necessary": a long description of the problem; explore the repo "to verify their assertions"; other options; a detailed interview; exact scope — "what you plan to change and what you plan not to change"; test coverage of the area; then "Break the implementation into a plan of tiny commits. Remember Martin Fowler's advice to 'make each refactoring step as small as possible, so that you can always see the program working.'" Step 8 files a GitHub issue with a fixed template — Problem Statement, Solution, Commits, Decision Document, Testing Decisions, Out of Scope, Further Notes — with the instruction "Do NOT include specific file paths or code snippets. They may end up being outdated very quickly."

For: the M14 drive-by, done properly — the format_deck → render_deck rename, if it is worth doing at all, becomes an issue with a plan of tiny commits that each leave the suite green. Not for: a behaviour change; a refactor by this skill's definition keeps behaviour and moves structure. Note that its issue template is the to-spec shape with a Commits section in place of User Stories — and that the upstream author deleted the skill as unused, naming /to-spec plus /improve-codebase-architecture as what does the job now. If you installed the plugin you do not have it; if you rely on the old copy, keep it.

grill-me

~/.agents/skills/grill-me/SKILL.md · disable-model-invocation: true · standalone · in the plugin

description: "A relentless interview to sharpen a plan or design."

Its entire body is one line: "Run a /grilling session." (Since 2026-08-15 the upstream line reads "Call the Skill tool with “grilling”." — same shape, same delegate.)

So the substance is in grilling, the model-invoked primitive it delegates to — description "Grill the user relentlessly about a plan or design. Use when the user wants to stress-test a plan before building, or uses any 'grill' trigger phrases." Its installed body: "Interview me relentlessly about every aspect of this plan until we reach a shared understanding. Walk down each branch of the design tree, resolving dependencies between decisions one-by-one. For each question, provide your recommended answer. Ask the questions one at a time, waiting for feedback on each question before continuing. Asking multiple questions at once is bewildering." (Upstream rewrote grilling between 2026-07-13 and 2026-08-20 — the description now reads "Grill the user relentlessly about a plan, decision, or idea", and the body works the design tree in numbered rounds with a recommended answer under each question; the one-at-a-time rule became one-round-at-a-time. A plugin install runs that version.) ask-matt places grill-me off the main flow: "the same relentless interview as /grill-with-docs, but for when you have no codebase. Stateless: it saves nothing locally, builds no CONTEXT.md."

For: stress-testing your A3 plan — which two tickets, why that edge, what ticket C will collide on — before you touch a branch; or any design with no repository behind it. Not for: a design that lives in a repo and should update CONTEXT.md and ADRs as it goes — that is grill-with-docs, "the one that leaves a paper trail."

tdd

~/.agents/skills/tdd/SKILL.md (+ tests.md, mocking.md) · model-invocable · driven by implement

description: "Test-driven development. Use when the user wants to build features or fix bugs test-first, mentions "red-green-refactor", or wants integration tests."

"TDD is the red → green loop. This skill is the reference that makes that loop produce tests worth keeping." Its one non-obvious rule is about seams: "A seam is the public boundary you test at … Test only at pre-agreed seams. Before writing any test, write down the seams under test and confirm them with the user. No test is written at an unconfirmed seam." Three anti-patterns are named — implementation-coupled, tautological, and horizontal slicing ("writing all tests first, then all implementation … Work in vertical slices instead — one test → one implementation → repeat, each test a tracer bullet"). And "Refactoring is not part of the loop. It belongs to the review stage (see the code-review skill)." It reads CONTEXT.md first "so test names and interface vocabulary match the project's domain language."

For: implementing ticket A: the seam is Card's constructor; one failing test per acceptance criterion, then the code that passes it — which is how PR #4's four tests came to map one-to-one onto #1's criteria. Not for: a refactor with no behaviour change (no red to go green from), or writing the whole test file first (its own anti-pattern).

handoff

~/.agents/skills/handoff/SKILL.md · disable-model-invocation: true · argument-hint: "What will the next session be used for?" · crossing sessions · in the plugin

description: "Compact the current conversation into a handoff document for another agent to pick up."

The body: "Write a handoff document summarising the current conversation so a fresh agent can continue the work. Save to the temporary directory of the user's OS - not the current workspace. Include a 'suggested skills' section … Do not duplicate content already captured in other artifacts (specs, plans, ADRs, issues, commits, diffs). Reference them by path or URL instead. Redact any sensitive information." And on the argument: "If the user passed arguments, treat them as a description of what the next session will focus on and tailor the doc accordingly." ask-matt on when: "when a thread is full or you need to branch off … You don't continue in place — you open a new session and reference that file." Against the built-in: "/handoff forks; /compact continues."

For: the A3 conflict resolution is half-done and has to continue somewhere this session cannot follow — a colleague's machine, a different directory, a different harness — with the reasoning intact: /handoff finish resolving the conflict on PR #5. Not for: a pause between phases in the same conversation, where losing the verbatim history is fine — that is /compact. The two routers differ on the case in between: the installed ask-matt (2026-07-09) says a nearly full window is a /handoff case ("/handoff forks; /compact continues"); the upstream one (2026-08-05) makes /compact "the default" at a phase boundary and calls /handoff "Narrow: only for a new harness, a new directory, a colleague, or forking a side task mid-phase." The description has not changed; the recommendation around it has, so ground your answer in the description. (A sibling, claude-handoff, is installed too and instead launches a background agent with the summary; it is in upstream's in-progress bucket.)

git-guardrails-claude-code

~/.agents/skills/git-guardrails-claude-code/SKILL.md (+ scripts/block-dangerous-git.sh) · model-invocable · skills/misc/ upstream, not in ask-matt, not in the plugin — add it alone with npx skills@latest add mattpocock/skills and pick it

description: "Set up Claude Code hooks to block dangerous git commands (push, reset --hard, clean, branch -D, etc.) before they execute. Use when user wants to prevent destructive git operations, add git safety hooks, or block git push/reset in Claude Code."

"Sets up a PreToolUse hook that intercepts and blocks dangerous git commands before Claude executes them." What gets blocked, from the file: "git push (all variants including --force) · git reset --hard · git clean -f / git clean -fd · git branch -D · git checkout . / git restore .." Five steps: ask the scope (project .claude/settings.json or global ~/.claude/settings.json); copy the bundled script; add the hook to settings — "If the settings file already exists, merge the hook into existing hooks.PreToolUse array — don't overwrite other settings"; ask about customisation; verify with echo '{"tool_input":{"command":"git push origin main"}}' | <path-to-script>, which "Should exit with code 2 and print a BLOCKED message to stderr." The script itself reads the tool input with jq, so jq must be on the PATH.

For: a shared repository — the Upstream Repo in Weeks 5–6 — where you want the agent to prepare commits but never push, and never run reset --hard against a branch a peer has checked out. Note that M16 page 2's git push --force-with-lease would be blocked too; with guardrails on, the rebase's push is yours to run. Not for: a throwaway Instance where the whole point is letting the agent run the loop end to end; and not a substitute for branch protection (Week 5, M26), which GitHub enforces and a hook only advises.

The six on the map

Two on-ramps or standalone entries (wayfinder, grill-me), one discipline inside the main flow (tdd), one bridge between sessions (handoff), and two off the map entirely — request-refactor-plan, deleted upstream, and git-guardrails-claude-code, kept in misc — which are also the two the plugin does not install. Knowing which is which is most of the objective; ask-matt will tell you the rest.

Self-check

1. A feature is too large for one session and nobody can yet say what decisions it involves. Which skill, and what does it produce?

C. "Plan, don't do": wayfinder's tickets "resolve a decision," and it merges onto the main flow at to-spec once the fog is gone. to-tickets (A) needs a spec you cannot yet write; B is for structure-only changes; D bridges sessions but plans nothing.

2. What is the one instruction in the course machine's installed grill-me file?

A. The body is that single line (the plugin's copy says the same thing as "Call the Skill tool with “grilling”."). B and D are sentences from the installed grilling, which it delegates to; C describes grill-with-docs — grill-me is the stateless one.

3. With git-guardrails-claude-code installed, which M16 step changes hands?

D. The file's list: "git push (all variants including --force)." The hook matches git commands, not gh (A, C); creating a branch is not on the list (B).

4. Mid-task, the work has to continue in a different directory — a prototype checkout — with the reasoning intact. Which, and why not the other?

B. Both routers agree on this case: the installed ask-matt ("/handoff forks; /compact continues") and the upstream one ("/handoff … only for a new harness, a new directory, a colleague"). A reverses them; /compact is built in, not a skill (C); handoff is user-invoked (D).
