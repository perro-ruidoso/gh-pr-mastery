Naming That Links Twice

GitHub links a branch to an issue by a stored relation; Linear links a pull request to an issue by reading the branch name. A branch that satisfies both carries two identifiers — the GitHub number and the Linear ID — and --name is where you put them.

M13 · Branching Bloom: Apply Assessed by: A3 (checker)

Objective: Create a branch bound to an issue with gh issue develop, and follow a branch-naming convention that auto-links in both GitHub and Linear.

Two systems, two linking rules

GitHub — links by relation

The link is created by the act of creating the branch from the issue (gh issue develop or the sidebar button), then carried by the PR. The branch's name plays no part: --name anything-at-all is linked just the same. The number in the default name is for humans, for CLAUDE.md's rule, and for the checker.

Linear — links by name

"Include issue ID in the branch name." And in the FAQ: "If your branch name includes a Linear issue ID, Linear will automatically link the pull request to that issue. Even if you manually unlink it, the connection can return when you push new commits or when the PR is merged." The ID is the KEY-n you saw in Week 2 — not the GitHub number.

Those are different mechanisms with different keys. Your Instance has both, because Week 2 wired Issues Sync: every GitHub issue created since then has a synced twin in Linear with its own identifier (FLA-7, say, for GitHub #7). A branch named only with the GitHub number links on GitHub and is invisible to Linear; a branch named only with the Linear ID links in Linear and — if you created it with gh issue develop — still links on GitHub, but the number is gone from the name and the CLAUDE.md rule is broken.

The convention

Put both in, GitHub's number first so the branch sorts with its issue:

$ gh issue develop 7 --name 7-fla-7-persist-review-state --checkout

Read it as <github-number>-<linear-id>-<slug>. Linear's own Copy git branch name action produces a branch name in whatever format the workspace's Branch format setting selects — the docs say: "Select the branch format you want to use when copying the branch name using Cmd + Shift + . from a Linear issue and pasting it into your branch name." Copy that, prepend the GitHub number, and hand the result to --name. The checker only reads the leading number; the Linear ID is for Linear.

Titles and magic words are a second channel

Linear also links from the PR itself: "Include the Linear issue ID (e.g. ID-123) in the title when creating pull requests," or "use a magic word + issue ID in the PR description or title (for example, Fixes ENG-123 …)". Its closing words overlap GitHub's — "close, closes, closed, closing, fix, fixes, fixed, fixing, resolve, resolves, resolved, resolving, complete, completes, completed, completing, implement, implements, implemented, implementing, linear issue" — but the reference differs: GitHub wants Closes #7, Linear wants Closes FLA-7. A PR body for a synced issue can carry both lines, and M15 page 2 is about what the GitHub one does. Linear's non-closing words ("ref, refs, references, part of, contributes to, toward, towards") move the issue through statuses without closing it; GitHub has no such distinction.

One thing squash-merging does to Linear

Linear's FAQ: "If you have already merged multiple PRs into a single branch and you want to merge that branch into a new branch, we will not auto-detect any Linear issues that were linked in the previous PRs. You will need to link each issue anew." A stack of PRs where each is merged into its parent branch, and then the parent into main, loses Linear's links at the last step. The course's stacking method — retarget each child to main and merge it there (M16 page 2) — avoids the case entirely.

Hands-on checklist

Self-check

1. A branch is created with gh issue develop 7 --name persist-review-state. What is linked where?

C. GitHub's link is the stored relation, name-independent. Linear reads the name and finds no KEY-n. Sync copies issue properties (title, description, status, …), not the Development link (A).

2. Which PR body line closes the GitHub issue on merge and moves the synced Linear issue to its merged status?

A. GitHub's syntax is KEYWORD #ISSUE-NUMBER; Linear's is a magic word plus ID-123. Neither documents resolving the other's reference (B, C). The branch name links in Linear, but closing on merge is the keyword's job on GitHub (D).

3. The Linear docs warn about merging "multiple PRs into a single branch" and then that branch onward. Which course practice sidesteps it?

D. The warned case is PR → parent branch → main. The M16 method merges every PR into main directly, retargeting the child first. Squashing (A) does not help — the FAQ is in the "squash merging" question. Stacking itself is fine (C).
