A Branch Bound to an Issue

A branch created with gh issue develop is not just named after its issue — GitHub records the relation, shows it in the issue's Development section, and hands it to the pull request you open from it. One command replaces three habits.

M13 · Branching Bloom: Apply Assessed by: A3 (checker)

Objective: Create a branch bound to an issue with gh issue develop, and follow a branch-naming convention that auto-links in both GitHub and Linear.

M13 pages 1A Branch Bound to an Issue 2Naming That Links Twice

What GitHub means by a linked branch

GitHub's page on creating a branch for an issue puts the whole feature in three sentences: "Branches connected to an issue are shown under the 'Development' section in the sidebar of an issue. When you create a pull request for one of these branches, it is automatically linked to the issue. The connection with that branch is removed and only the pull request is shown in the 'Development' section." Two more facts from the same page matter for this week: "You can link multiple branches for an issue," and "By default, the new branch is created in the current repository, and from the default branch."

The page describes clicking Create a branch in the sidebar. gh issue develop is the same operation from the terminal — the manual's one-line summary is "Manage linked branches for an issue." Everything below was run on a throwaway Instance created from the template that afternoon, gh 2.100.0, 2026-09-13.

The first branch

The Instance had three freshly filed tickets: #1 (review state on Card), #2 (persist it — blocked by #1), and #3 (a tag field — blocked by #1). Before anything, the issue had no linked branch:

$ gh issue develop --list 1
(no output, exit 0)

$ gh issue develop 1 --checkout
github.com/perro-ruidoso/flashcards-w3probe/tree/1-add-review-state-to-card-repetitions-ease-factor-interval-due-date
From https://github.com/perro-ruidoso/flashcards-w3probe
 * [new branch]      1-add-review-state-to-card-repetitions-ease-factor-interval-due-date -> origin/1-add-review-state-to-card-repetitions-ease-factor-interval-due-date

$ git branch --show-current
1-add-review-state-to-card-repetitions-ease-factor-interval-due-date
$ git log --oneline -1
e474711 Initial commit

$ gh issue develop --list 1
1-add-review-state-to-card-repetitions-ease-factor-interval-due-date	https://github.com/perro-ruidoso/flashcards-w3probe/tree/1-add-review-state-to-card-repetitions-ease-factor-interval-due-date

Read what happened. The branch was created on GitHub first (the URL is printed before anything local happens), from the default branch (git log shows only the template's initial commit), then fetched and checked out because of --checkout. The default name is the issue number followed by the whole title, slugified — 68 characters here. And --list now returns the branch, which means the relation is stored on GitHub's side, not inferred from the name. The same relation is readable through GraphQL, which is how a checker or a script sees it:

$ gh api graphql -f query='{ repository(owner:"perro-ruidoso", name:"flashcards-w3probe") { issue(number:1) { linkedBranches(first:10) { nodes { ref { name } } } } } }' --jq '.data.repository.issue.linkedBranches.nodes[].ref.name' 
1-add-review-state-to-card-repetitions-ease-factor-interval-due-date

Re-run on 2026-09-14, after PR #4 had been opened from the branch and merged, the same query returns an empty nodes list — the relation had moved to the pull request, as the section below shows happening live. Run it before you open the PR if you want to see the branch.

--name and --base

Two flags change the defaults, and both were used for the second ticket. --name replaces the slugified title; --base — "Name of the remote branch you want to make your new branch from" — creates the branch from something other than the default branch. The manual adds a sentence that M16 depends on: "The new branch will be configured as the base branch for pull requests created using gh pr create."

$ gh issue develop 2 --name 2-persist-review-state --base 1-add-review-state-to-card-repetitions-ease-factor-interval-due-date --checkout
github.com/perro-ruidoso/flashcards-w3probe/tree/2-persist-review-state
From https://github.com/perro-ruidoso/flashcards-w3probe
 * [new branch]      2-persist-review-state -> origin/2-persist-review-state
$ git log --oneline -2
58cab2d Add review state to Card
e474711 Initial commit
$ git config --get branch.2-persist-review-state.gh-merge-base
1-add-review-state-to-card-repetitions-ease-factor-interval-due-date

The new branch starts at #1's commit, not at main, and gh wrote a git config entry — branch.<name>.gh-merge-base — naming the parent. The gh pr create manual documents exactly this lookup: "The base branch for the created PR can be specified using the --base flag. If not provided, the value of gh-merge-base git branch config will be used. If not configured, the repository's default branch will be used." That is why, on M16 page 1, gh pr create opens the second PR against the first branch with no flag at all.

The moment the branch stops being listed

The docs said the branch connection "is removed and only the pull request is shown" once a PR exists. Observed, seconds after gh pr create on the first branch:

$ gh pr create --title "Add review state to Card" --body-file pr1.md
https://github.com/perro-ruidoso/flashcards-w3probe/pull/4
$ gh issue develop --list 1
(no output)

So --list is a view of branches without a PR yet. Once you have opened the PR, the place to read the relation is the PR (gh pr view --json closingIssuesReferences) or the issue (gh issue view --json closedByPullRequestsReferences); M15 page 2 shows both. A grader cannot use linkedBranches to check that you used gh issue develop — by the time the work is merged, the link has moved to the PR. What survives is the name, which is why the convention on page 2 matters and why check_a3.py reads headRefName.

More than one branch per issue

"You can link multiple branches for an issue." On M14 page 2 the first branch for #3 produced a PR that was closed as a drive-by, and a second gh issue develop 3 --name 3-tag-field-on-card-clean created the branch the clean PR came from. Both branches were linked to #3; both PRs reference it; only the merged one appears in closedByPullRequestsReferences.

Self-check

1. After gh pr create on a branch made with gh issue develop, gh issue develop --list prints nothing. What happened?

B. GitHub's docs: "The connection with that branch is removed and only the pull request is shown in the 'Development' section." The branch still exists (A); no flag changes the view (C); nothing is cached (D) — the relation genuinely moved.

2. gh issue develop 2 --base 1-add-review-state… --checkout was run. Which pair of facts is true afterwards?

D. git log showed #1's commit at the tip, and git config --get branch.2-persist-review-state.gh-merge-base printed #1's branch name. --base says nothing to the issue tracker (B) — the blocking edge was recorded separately in Week 2.

3. Why does check_a3.py read a merged PR's headRefName rather than the issue's linkedBranches to confirm you branched from the issue?

A. The page showed --list going empty the moment PR #4 existed. The checker already uses GraphQL elsewhere (B is not the reason); GitHub never renames branches (C); the cross-repository case (D) is real but not why.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

What does gh issue develop N do, in GitHub's terms?
Creates a branch linked to issue N (shown in the issue's Development section), from the default branch unless --base says otherwise.
Default branch name from gh issue develop?
<number>-<title slugified> — 68 characters for #1. --name replaces it.
Two effects of gh issue develop N --base B?
The branch starts at B's tip, and branch.<name>.gh-merge-base is set to B so gh pr create targets B by default.
When does a branch stop appearing in gh issue develop --list?
As soon as a PR is opened from it — "the connection with that branch is removed and only the pull request is shown."
Where does gh pr create look for its base when no --base is given?
The gh-merge-base git branch config; if unset, the repository's default branch.
Can one issue have several linked branches?
Yes — "You can link multiple branches for an issue." #3 had two on the throwaway: the drive-by branch and the clean one.
Which flag checks the new branch out locally?
--checkout (or -c); --worktree <path> checks it out into a worktree instead.
Ask your teacher

Ask Claude Code, inside your Instance: "create a branch for issue N with gh issue develop, then show me three different ways to confirm the branch is linked to the issue, and tell me which of them will stop working once I open a PR." If it reaches for the branch name as proof, ask it what the name proves and what the Development section proves. Bring anything still unclear to the weekly meeting.
