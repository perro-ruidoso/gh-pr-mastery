What is there to read

perro-ruidoso/gh-pr-mastery is being built using the workflow this course teaches: work is filed as an issue, built on a branch, opened as a pull request, and merged, with blocking relations recorded on the issues rather than only described in prose. That was done deliberately so you would have a real example to read in Week 1 — including the parts that went sideways.

Be honest about how much history is there. The course is being written as you take it, so the repository's history is short and growing, and it is not uniformly dogfooded — the first commit is a squashed import of everything that existed before the repo had version control at all. That is itself worth reading: a single enormous initial commit tells you nothing about how the work was done, which is exactly why the commits after it are structured differently. Do not describe process the artifacts do not show.

Where the blocking relations live

A blocking relation is stored on the issue, not on the pull request. The REST endpoint reads it on any gh version; from gh 2.94.0 the same relation is also a --json blockedBy field on gh issue view (Week 2 uses both):

$ gh api repos/perro-ruidoso/gh-pr-mastery/issues/2/dependencies/blocked_by --jq '.[] | "#\(.number) [\(.state)] \(.title)"' 
#1 [closed] Org-qualify course-repo references now that the repo has an address

Issue #2 was recorded as blocked by #1. Run the same command for every other issue and, as of 2026-09-13, exactly one more edge comes back — #13 is blocked by #11 (the Week 2 pages depended on the Week 1 rebuild) — and the rest return an empty list. The empty list is a finding too, and worth stating precisely: "no blocking relation is recorded for #4, #7, or #9", not "they had no dependencies."

Dependencies are not sub-issues

That endpoint is GitHub's issue dependencies feature, which is not the same thing as a sub-issue. A sub-issue is a hierarchy — one parent, many children, up to eight levels — so it cannot express a ticket blocked by two others. A dependency is a graph: an issue may be blocked by many and block many. The Seed Repo's backlog has five tickets with two blockers each, which is the concrete reason the two mechanisms are not interchangeable (Week 2, M11). Naming which mechanism recorded the relation, and how you checked, is worth more than naming the blocker.

Your assignment target

Pick one merged pull request in perro-ruidoso/gh-pr-mastery and write roughly 300 words answering: what did it change, what was it blocked by, and how can you tell? Every claim must name the artifact that supports it — a field in --json output, a linked issue number, a timestamp, a review thread. Put it in a1-writeup.md at the root of your Instance; the full brief is assignments/a1.md.

Some things you might notice: which issues have blocking edges declared; whether a PR's base was main or another feature branch (one of them was not, and its timeline says when that changed); whether any issue was closed by hand rather than by a merge; how long the gap was between a PR opening and its first review; what reviewDecision says on a repository with, so far, one maintainer.

Hands-on checklist

Self-check

1. Where is a blocking relation between two issues stored, and how do you read it?

C. Issue dependencies are a property of the issue and are reached through the REST endpoint — or, from gh 2.94.0, through gh issue view N --json blockedBy, which reads the same relation. A "Blocked by" line in a body is prose — GitHub does not act on it. The PR's closing references bind the PR to the issue it closes, which is a different relation.

2. Why can a sub-issue not express "ticket T04 is blocked by both T02 and T03"?

B. One parent, many children — a tree, not a graph. Two blockers is a join, and a tree has no joins. (The real limits are up to 100 sub-issues per parent and eight levels of nesting; the CLI supports them fine; and closing a parent does not close its children.)

3. The course repo's first commit is a squashed import of 31 files. What does it tell you about how that work was done?

D. One commit is one observation: the files arrived together. It does not show whether there were issues, drafts, reviews, or weeks of work behind it — the squash removed that information. The honest sentence is "the initial commit demonstrates nothing about process," which is also why the commits after it are structured to demonstrate something.

4. You query dependencies/blocked_by for issue #7 and get an empty list. Which write-up sentence is defensible?

A. The endpoint tells you what was recorded. B and C claim facts about the work itself that the artifact cannot show; D asserts a motive. Same rule as the review-comments case on the previous page: report the absence, not a story about it.

Issue Dependency vs Sub-Issue — graph or hierarchy?
Dependency = graph (blocked by many, blocking many). Sub-issue = hierarchy (one parent, up to eight levels). Only the graph can express a two-blocker join.
