A repository records how its work was done. Learn to read that record and you can audit any team's process — including your own — from the outside, without asking anyone.

Objective: Read the course repo's own issue graph and PR history as an exhibit and describe the workflow that produced it.

Why this page exists

Everything else this week taught you a mechanism. This one teaches you to infer process from artifacts — and it is the skill that makes the other five compound. A merged pull request is not just a change that landed; it is a record of what someone decided, in what order, with what checks, and who agreed.

You need this for three reasons. You will join codebases whose conventions nobody has written down. You will be graded, in this course, on the evidence your repository leaves rather than on your account of what you did. And from Week 2 onward you will be directing an agent whose work you can only supervise through exactly these traces.

A worked example

Here is a real, complete story from the cli/cli repository, reconstructed entirely from the command line. Start with a closed issue:

$ gh issue view 14404 -R cli/cli --json number,title,state,labels,createdAt,closedAt --jq '{number,title,state,labels:[.labels[].name],createdAt,closedAt}' 
{
  "number": 14404,
  "title": "`gh pr merge NNN --delete-branch` fails to delete branch when repo owner
            from `remote.origin.url` case mismatches github's canonical owner",
  "state": "CLOSED",
  "labels": ["bug", "priority-3", "gh-pr"],
  "createdAt": "2026-09-09T03:10:49Z",
  "closedAt": "2026-09-11T15:55:42Z"
}

Three labels doing three different jobs: bug is a kind, priority-3 is a rank, gh-pr is an area of the codebase. Opened on the 9th, closed on the 11th. Now the pull request that closed it:

$ gh pr view 14429 -R cli/cli --json number,title,state,baseRefName,headRefName,isCrossRepository,additions,deletions,changedFiles,mergedAt,closingIssuesReferences 
{
  "number": 14429,
  "title": "Fix remote branch deletion for owner case mismatch",
  "state": "MERGED",
  "baseRefName": "trunk",
  "headRefName": "williammartin-validate-issue-14404",
  "isCrossRepository": false,
  "additions": 63,
  "deletions": 4,
  "changedFiles": 3,
  "mergedAt": "2026-09-11T15:55:40Z",
  "closingIssuesReferences": [{"number": 14404, "url": "https://github.com/cli/cli/issues/14404", …}]
}

Output lightly abridged: closingIssuesReferences also carries each issue's id and repository, elided here.

What the evidence says

ObservationInference
closingIssuesReferences: [14404]The PR body used a linking keyword. The issue and the change are formally bound, not just mentioned in prose.
Issue closedAt is 15:55:42; PR mergedAt is 15:55:40Two seconds apart. Nobody closed that issue by hand — merging closed it. This is the automation you will build in Week 3 and Week 6.
headRefName contains 14404The branch was named after the issue it serves. The link is legible before you open anything.
isCrossRepository: falseA maintainer working on a branch in the repo itself, not an outside contributor from a fork. Different trust model, different CI behaviour (Week 5).
63 added, 4 removed, 3 filesOne bug, one fix, bounded. A reviewer can hold this entire change in their head — which is the point of Week 3's M14.
Two days from open to mergeNot a rush, not a stall. Worth comparing against the repo's median before drawing conclusions.

Observation, then inference — in that order

Every row in the table has two columns for a reason. The left column is something a command printed; the right column is what you conclude from it. Keeping them apart is the whole discipline of this objective, and it is what the A1 rubric grades. The next page turns the two columns into a repeatable method with four questions.

Self-check

1. A PR merged at 15:55:40 and its linked issue closed at 15:55:42. What does the two-second gap tell you?

B. Two seconds is machine time, and closingIssuesReferences on the PR confirms the formal link. A human closing an issue deliberately leaves a much larger and more variable gap. (D is ruled out by the order of the timestamps.)

2. Which claim is fully supported by "isCrossRepository": false?

D. That is exactly and only what the field means. Membership, review, and contribution policy are separate questions answered by other fields — author, reviewDecision, and the repository's settings. Over-reading a single field is the most common failure in this kind of analysis.

3. An issue carries the labels bug, priority-3, and gh-pr. What is each one doing?

C. Three independent axes on one issue — which is how a small label set stays filterable. None of them is a triage state in the M05 sense; a repo can use kind/rank/area labels and a state vocabulary side by side, and reading which axis a label belongs to is part of reading the exhibit.

4. The head branch is named williammartin-validate-issue-14404. What is the defensible inference?

A. The name contains the issue number; that is all the artifact shows. How the branch was created (B) is not recoverable from its name alone, the author's role (C) needs the author field and the org's membership, and D is a claim about other PRs you have not looked at. State what the artifact supports and stop.

What skill does M06 teach, in four words?
Infer process from artifacts — read what a repository records and say what workflow produced it, no interviews needed.
Which gh pr view field proves a PR is formally bound to an issue, not just mentioning it?
closingIssuesReferences — populated only when the PR body uses a linking keyword (Week 3).
PR mergedAt 15:55:40, issue closedAt 15:55:42. What closed the issue?
The merge, via a linking keyword. A two-second gap is machine time; a human leaves a larger, variable gap.
bug, priority-3, gh-pr — what three jobs are these labels doing?
Kind, rank, area. Three independent axes on one issue.
What does isCrossRepository: false tell you — and what does it not tell you?
Tells you: the head branch lives in the base repo, not a fork. Does not tell you: who the author is, whether it was reviewed, or the repo's contribution policy.
63 additions, 4 deletions, 3 files. What is the inference, and what is the caveat?
A bounded change a reviewer can hold in their head. Caveat: compare with the repo's median before calling it small or large.
The two-column discipline: what goes left, what goes right?
Left: an observation — something a command printed. Right: the inference you draw from it. Never let the right column outrun the left.
Ask your teacher

Try the worked example on a different pair: ask Claude Code to "find a merged PR in cli/cli whose closingIssuesReferences is non-empty, then show me the issue's closedAt and the PR's mergedAt side by side." Check whether the gap is seconds or hours, and say what each would mean. Bring anything still unclear to the weekly meeting.
