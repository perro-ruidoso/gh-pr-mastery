Filter and Diff

Reshape JSON with --jq, pull one value out of it, read a pull request's diff without a browser — and turn two of those into questions the web UI cannot answer quickly.

Filtering: --jq

gh has jq built in via -q/--jq, so you can reshape output without installing anything. It only applies when --json is present, because it filters the JSON gh is about to print:

$ gh issue list -R cli/cli --limit 3 --json number,title,labels --jq '.[] | {number, title, labels: [.labels[].name]}' 
{"labels":["needs-triage"],"number":14432,"title":"docs: improve README wording for quick start"}
{"labels":["more-info-needed","needs-triage"],"number":14420,"title":"gh 2.100.0 fails HTTPS requests with an instant connection reset"}
{"labels":["enhancement"],"number":14413,"title":"Feature request: allow selecting fields for human-readable list output"}

Read the expression left to right. .[] walks the array; the | passes each element on; {number, title, labels: [...]} builds a smaller object, flattening each label to its name. Notice the labels themselves: needs-triage, more-info-needed. A real project runs a triage vocabulary very like the one you will configure in M05 and use in Week 6.

Extracting a single value is the building block of every script you will write here:

$ gh pr list -R cli/cli --limit 1 --json number --jq '.[0].number' 
14398

A bare scalar, no quotes, no braces — exactly what a shell variable or a checker wants.

Diffing: what actually changed

$ gh pr diff 14398 -R cli/cli --name-only 
pkg/cmd/issue/view/view.go

Drop --name-only for the patch itself, or pass --patch to get it in patch format you can apply. gh pr diff shows the pull request's diff — which, per M03, is the three-dot comparison against the merge base, not a tip-to-tip diff. The CLI and the website agree because they are asking the same question of the same pull request.

Putting it together

Two questions you could not answer quickly in the web UI:

# Which open PRs target a base branch other than the default? 
$ gh pr list -R cli/cli --limit 50 \
    --json number,baseRefName,title \
    --jq '.[] | select(.baseRefName != "trunk")'
# How big is each open PR, largest first? 
$ gh pr list -R cli/cli --limit 20 \
    --json number,title,additions,deletions \
    --jq 'sort_by(-(.additions + .deletions))
          | .[] | "\(.number)\t\(.additions + .deletions)\t\(.title)"'

The second is worth running on any repository you join. Pull request size predicts review quality better than almost anything else, and a list sorted by size tells you where review is failing before anyone admits it.

# And the one M02 left you needing: which open PRs come from forks? 
$ gh pr list -R cli/cli --limit 50 \
    --json number,isCrossRepository,headRepositoryOwner \
    --jq '.[] | select(.isCrossRepository) | "\(.number)\t\(.headRepositoryOwner.login)"'
Give your agent the command, not the screenshot

When you want Claude to reason about a pull request, the useful move is to tell it which gh command to run, or paste the --json output. Pasting a screenshot or a URL forces it to guess at structure it could have read exactly. This becomes a habit in Week 4, when /code-review needs a precise scope.

Hands-on checklist

Item 3 is the one most worth doing on a repository you actually care about.

Self-check

1. gh pr diff shows a pull request's changes. Which comparison is it showing?

D. The CLI and the web UI are asking the same question of the same pull request, so they agree. That is exactly why the CLI is trustworthy as a review surface — and why you can hand its output to an agent without worrying that it differs from what a human reviewer sees.

2. Why does this course build its assignment checkers out of --json output rather than screenshots or self-reports?

C. The artifacts you produce — branch names, linked issues, passing checks, a closed issue after merge — are the evidence that the workflow happened. --json turns that evidence into something a script can assert on, which is why most of A1 is graded automatically and only the written analysis needs a human.

3. gh pr list -R cli/cli --limit 1 --json number --jq '.[0].number' prints 14398. What did each part do?

B. list with --json always returns an array, even for one item; .[0] indexes it and .number reads the field, leaving a bare scalar. --jq never talks to GitHub — it reshapes the JSON gh already fetched.

4. You want an agent to reason about PR #42 accurately. Which input gives it the most to work with?

A. Structured fields, or the command that produces them, give the agent exact data with no guessing at layout. A screenshot or URL forces it to infer structure it could have read directly, and your summary substitutes your reading for the evidence. This is the habit Week 4's review work depends on.

What does --jq do, and what must accompany it?
Filters the JSON output with a jq expression, using jq built into gh. It needs --json, because it operates on the fields you asked for.
Read this jq aloud: .[] | select(.baseRefName != "trunk")
"For each element of the array, keep the ones whose baseRefName is not trunk."
jq expression to pull the first PR's number as a bare scalar from a list?
.[0].number — index the array, read the field. list always returns an array, even for one item.
Command to see only the file names a PR touches?
gh pr diff N -R O/R --name-only. Drop the flag for the full diff; --patch gives patch format.
Which comparison does gh pr diff show?
The same three-dot, merge-base comparison the PR's Files changed tab shows. CLI and web agree because they ask the same question.
Why is a PR-size list sorted largest-first worth running on any repo you join?
PR size predicts review quality better than almost anything else; the sorted list shows where review is failing before anyone admits it.
jq to keep only fork PRs from a gh pr list --json result?
.[] | select(.isCrossRepository) — then read .headRepositoryOwner.login for who owns the fork.
Screenshot, URL, or --json output: which do you hand an agent, and why?
--json output (or the command). Exact structure, no guessing — the same evidence a checker would read.
Ask your teacher

jq syntax is the most common place to get stuck this week. Paste any expression that does not work into Claude Code with the error and the first few lines of the raw --json output, and ask it to fix the expression and explain each pipe stage. Bring anything still unclear to the weekly meeting.
