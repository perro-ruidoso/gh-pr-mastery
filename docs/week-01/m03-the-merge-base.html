The Merge Base, and Why Your Diff Looks Like That

One idea — the merge base — explains why a pull request shows what it shows, why it stays stable when main moves, and why your local git diff sometimes accuses you of deleting a colleague's work.

M03 · Diffs Bloom: Understand Assessed by: Quiz 1

Objective: Distinguish two-dot from three-dot diffs and explain why a PR's Files-changed view is computed from the merge base.

The situation that creates the confusion

You branch off main and add a line to one file. While you work, a colleague merges a change to a completely different file. Now two branches have diverged from a shared ancestor:

$ git log --all --oneline --graph 
* 12ccbf6 Add my line to shared.txt          <- your branch: feature
| * 8c7a482 Someone else edits untouched.txt <- main moved on
|/
* 9c332a8 Initial commit                    <- the shared ancestor

That bottom commit — the most recent commit both branches have in common — is the merge base. Git will tell you which one it is:

$ git merge-base main feature 
9c332a8037d289c6588c65b802bdae0797dda779

Two ways to compare, and they disagree

Now ask "what did I change?" two different ways. First with two dots:

$ git diff main..feature --stat 
 shared.txt    | 1 +
 untouched.txt | 2 +-
 2 files changed, 2 insertions(+), 1 deletion(-)

Two files. But you only touched one. Look at what it claims you did to the other:

$ git diff main..feature 
diff --git a/untouched.txt b/untouched.txt
--- a/untouched.txt
+++ b/untouched.txt
@@ -1 +1 @@
-CHANGED BY SOMEONE ELSE
+original

It reads as though you deleted your colleague's work and restored the old text. You did not. Now the same question with three dots:

$ git diff main...feature --stat 
 shared.txt | 1 +
 1 file changed, 1 insertion(+)

One file, one line. That is what you actually did — and that is what GitHub shows in a pull request.

Why they differ

GitHub's documentation states the rule directly. A three-dot comparison shows the difference between "the most recent common commit of both branches (merge base) and the most recent version of the topic branch." A two-dot comparison shows the difference between "the most recent state of the base branch (for example, main) and the most recent version of the topic branch."

Two dots — main..feature

Compares the tip of main to the tip of your branch.

Answers: "what would I have to do to turn main into my branch?"

Includes, in reverse, every change on main that your branch lacks. Moves every time main moves.

Three dots — main...feature

Compares the merge base to the tip of your branch.

Answers: "what did my branch introduce?"

Ignores everything that happened on main after you branched. Stable while main moves.

Two dots measure from the tip of the base. Three dots measure from the merge base. A pull request always uses three.

What GitHub shows you

The Files changed tab shows "what would change if the pull request merged" — computed as a three-dot diff, so it focuses on "what a pull request introduces." GitHub's docs spell out the consequence: a three-dot view "remains consistent even when the base branch updates," while a two-dot view "changes whenever the base branch updates, potentially obscuring the topic branch's actual contributions."

This is a genuinely good design choice. If pull requests used two-dot diffs, every merge into main would visibly churn every open PR, and reviewers would spend their attention on other people's changes.

Then why do I sometimes see unrelated files in a PR?

Three-dot diffing removes the most common cause, so when it still happens the reason is almost always one of: you merged main into your branch and resolved a conflict (those resolutions are your changes, and they belong to your branch), you rebased onto a moved base, or the head branch was created from something other than the base. Diagnosis starts the same way every time — find the merge base and look at what sits between it and your tip.

Why an agentic coder needs this specifically

You will routinely ask Claude to "review the changes on this branch." What it compares determines what it reports:

  • Point it at a two-dot range and it will dutifully review your colleague's changes in reverse, and may report them as regressions. You then waste a cycle arguing with a correct answer to the wrong question.
  • Point it at main...HEAD and it reviews what you introduced — the same scope a human reviewer sees on the PR.

This is why /code-review in Week 4 accepts a ref range such as main...my-feature, and why getting the dots right is a prerequisite for trusting agentic review at all. Wrong scope produces confident, well-written, irrelevant findings.

A habit worth forming today

When you want "what does my branch add," type three dots. When you genuinely want "how do these two tips differ" — comparing two releases, say — type two. If you are unsure which you want, you want three.

Self-check

1. git diff main..feature lists a file you never opened, showing its lines being reverted. What happened?

C. Two dots compare the tip of main with the tip of your branch. Your branch simply does not contain the colleague's newer commit, so relative to main's tip that content is "missing" — and the diff renders it as a deletion. Use three dots and it disappears, because three dots measure from the merge base, before their change existed.

2. What exactly is the merge base of two branches?

B. The merge base is their most recent common ancestor — git merge-base reports it. (D is a tempting trap: the merge base is not frozen at PR-open time; it is recomputed, and it moves if you merge the base into your branch.)

3. Ten commits land on main while your PR sits open, none touching your files. What happens to the PR's Files changed tab?

A. GitHub's docs say the three-dot view "remains consistent even when the base branch updates," whereas a two-dot view "changes whenever the base branch updates, potentially obscuring the topic branch's actual contributions." (B and C are what you would get from a two-dot view. D confuses the diff with a merge requirement — a ruleset can demand the branch be up to date, but that is a separate gate, covered in Week 5.)

4. You ask Claude to review "the changes on this branch" and it reports bugs in code a teammate wrote last week. What is the most likely cause?

D. Wrong scope, not wrong model. A two-dot range folds the base branch's newer commits into the diff, so the reviewer sees changes that are not yours and reasons about them correctly but uselessly. Pass main...HEAD — the same scope the PR shows a human. (B is worth keeping in mind as a secondary possibility, but if it were true you would want it filed as its own issue, not smuggled into your PR's review.)
