GitHub Pull Requests for Agentic Coders Week 1

Week 1 — The Machine You Work In

Before you can run work through pull requests, you need an accurate model of what a pull request is — and a repository, a terminal, and an agent configured to work in it.

Most people who have used GitHub for a year still hold a fuzzy model of the pull request: something like "a request to merge my branch." That model is close enough to open a PR and wrong enough to produce the three most common confusions in this course — why does my PR show a file I never touched?, why did my PR change when someone else merged?, and what exactly am I comparing against? This week replaces the fuzzy model with a precise one, then gets your tooling into a state where the rest of the course can be hands-on.

Suggested order

Do M01 first — it gives you a real repository to point the next objectives at. M02 and M03 are the conceptual core of the whole course; take them slowly, and do the M03 experiment. M04 and M05 are tooling. M06 asks you to turn the week's model on a real artifact and write up what you see. Every page ends with a self-check and a flashcard deck — do the flashcards again a few days later; that second pass is what makes them stick.

Learning pages

Each objective has an entry page (index.html) and, where the objective is dense, one or two supporting pages. Every page ends with a self-check, a flashcard deck, and a where-to-learn-more list; the pager at the bottom of each page walks the whole week in order.

  • M01Apply2 pages
    Your Instance and Your Toolchain

    Which of the three repositories is yours, joining the org properly, and gh scopes.

    Create Your Instance — template versus fork, the one command, and why --public.

  • M02Understand2 pages
    Two Refs and a Conversation

    Base and head, reading them off a real PR, and the five tabs everything else hangs from.

    Heads, Forks, and Drafts — head in someone else's repository, the two development models, and draft state.

  • M03Understand2 pages
    The Merge Base

    Three dots versus two, with a four-minute experiment you can reproduce.

  • M04Apply2 pages

    gh pr list, gh pr view --json, discovering field names, and the defaults that silently shape a count.

    Filter and Diff — --jq, gh pr diff, and three questions the web UI cannot answer quickly.

  • M05Apply2 pages

    What a skill is, the setup run, and Decision A: where issues live.

    Labels and Domain Docs — the five-label vocabulary, making the labels real, domain docs, and what to commit.

  • M06Analyze3 pages
    Reading the Exhibit

    A worked example from cli/cli: two commands, one two-second gap, and an observation/inference table.

    The Method — four questions that work on any repository. Your Target — this course's own repository, and the A1 write-up.

Assignment A1

Due before the Week 2 meeting. The full brief is in assignments/a1.md; in short:

  1. Instance created from the template, named flashcards-<your-github-handle>, public, in the course org.
  2. gh authenticated with the required scopes; a gh pr view --json command run against a real PR and its output pasted into your write-up.
  3. /setup-matt-pocock-skills run and its three output files committed.
  4. A short written analysis (roughly 300 words) of one pull request in the course repository: what it changed, what it was blocked by, and how you can tell.

Most of A1 is graded by a script that reads your repository's actual state — see the checker in checkers/check_a1.py. The written analysis is graded by a human against a rubric. Nothing is graded on whether you typed the code yourself.

Assigned sources

  • GitHub Docs: Pull requests (reference)
  • GitHub Docs: Branches (reference) — three-dot and two-dot comparisons — the important one
  • GitHub Docs: Creating a repository from a template
  • GitHub CLI manual — skim gh pr and gh issue

Time estimate: 3.5–4.5 hours including the assignment.
