What a skill is, and why it needs configuring

A skill is a packaged set of instructions Claude Code loads when a task matches it. This course uses a family of engineering skills — /to-spec, /to-tickets, /implement, /code-review, /qa, /triage — that form the workflow spine of Weeks 2 through 6. (One caveat, found 2026-09-14: upstream retired qa on 2026-08-05, folding its job into /triage and /to-tickets, and the plugin never shipped it — so the Week 4 pages will name whichever of those the instructor decides on; the course machine still has the older installed copy.)

Several of them read from and write to your issue tracker. But a skill cannot guess whether "file this ticket" means gh issue create, a markdown file in a scratch folder, or something else entirely. So they all read a small set of configuration files, and /setup-matt-pocock-skills is the one-time run that writes them. Its own description: "Configure this repo for the engineering skills — set up its issue tracker, triage label vocabulary, and domain doc layout. Run once before first use of the other engineering skills."

Run it once, in your Instance

This is a setup skill, not a working one. Run it today in flashcards-<your-handle>, commit what it writes, and then forget about it — the other skills pick the files up automatically. You will edit them by hand if your conventions change; the skill says re-running "is only necessary if they want to switch issue trackers or restart from scratch."

The run

Open Claude Code in your Instance and invoke it:

$ cd flashcards-<your-handle>
$ claude
> /setup-matt-pocock-skills

It is, in its own words, "a prompt-driven skill, not a deterministic script." It explores first — git remote -v, whether CLAUDE.md or AGENTS.md exists and already has an ## Agent skills section, CONTEXT.md, any docs/adr/, any prior docs/agents/ output — then walks you through three decisions one at a time. Read each one; do not just accept defaults you have not understood.

Decision A — Where do issues live?

The skill offers four options: GitHub (via the gh CLI), GitLab (via the glab CLI), local markdown (files under .scratch/, "good for solo projects or repos without a remote"), or other — Jira, Linear, anything else — which you describe in a paragraph of prose. Its default posture is to propose GitHub when a remote points at GitHub.

Choose GitHub. Your remote points at GitHub, and this course's entire premise is that GitHub Issues is the source of truth for work. That choice writes a file telling every skill exactly how to operate:

Extract from docs/agents/issue-tracker.md
  • Create an issue: gh issue create --title "..." --body "..."
  • List issues: gh issue list --state open --json number,title,body,labels,comments
  • Apply / remove labels: gh issue edit <number> --add-label "..."

Those are the same commands you learned in M04. That is not a coincidence — you and your agent drive GitHub through one interface, which is why reading that interface fluently was worth a lesson.

Why not Linear, given Week 2?

You will connect Linear at the end of Week 2 — but as the project-management layer above GitHub, not as the tracker the skills write to. These skills support GitHub, GitLab, and local markdown natively; Linear falls under "other," where you would have to describe the whole workflow in prose and maintain it yourself. Keeping GitHub as the source of truth keeps the tooling first-class and lets Linear do what it is genuinely better at. Week 6's M35 asks you to defend that choice — or argue against it.

The follow-up question: PRs as a request surface

Because you picked GitHub, the skill asks one more thing: should /triage pull external pull requests into the same queue as issues? Its explainer: "Open-source repos often receive feature requests as pull requests, not just issues — a PR is an issue with attached code." The default is no.

Answer no for your Instance. Nobody else contributes to it. You will flip this to yes in Week 6, on the shared upstream repository, where classmates' incoming PRs are exactly the queue you are triaging. Note now how it works, because it is a neat piece of filtering — the skill keeps only PRs whose authorAssociation is CONTRIBUTOR, FIRST_TIME_CONTRIBUTOR, or NONE, dropping OWNER, MEMBER, and COLLABORATOR, so a maintainer's own in-flight work is left alone.

Decisions B and C — the label vocabulary and the domain docs — are on the next page, along with what the skill writes and how to commit it.

Hands-on checklist

The first half of the run. A1's checker verifies the resulting docs/agents/issue-tracker.md exists and says GitHub, PRs-as-request-surface no.

Self-check

1. Why do the engineering skills need an issue-tracker.md at all?

C. The skills are tracker-agnostic by design; the config file is what binds an abstract instruction ("publish to the issue tracker") to concrete commands in your repository. Credentials live in your gh token, not in the repo.

2. You answer "no" to PRs as a request surface in your Instance. When would "yes" be right?

B. The flag exists for repos where a PR is effectively an issue with code attached — the open-source case. It filters on authorAssociation so that collaborators' own in-flight PRs are left alone. You will turn it on for the shared upstream repo in Week 6, and it has nothing to do with visibility or collaborator count.

3. Your Instance has a CLAUDE.md and no AGENTS.md. Where does the skill put its ## Agent skills block?

A. The skill's rule: if CLAUDE.md exists, edit it; else if AGENTS.md exists, edit that; if neither, ask. It "never create[s] AGENTS.md when CLAUDE.md already exists (or vice versa)," and an existing block is updated in place. The template ships a CLAUDE.md, so that is where yours goes.

4. Which authorAssociation values does the PRs-as-request-surface filter keep?

D. The point is to triage external requests while leaving maintainers' own in-flight PRs alone, so the filter keeps the associations that mean "not on the team" and drops OWNER, MEMBER, and COLLABORATOR. You will see the field in Week 6's maintainer rotation.

Ask your teacher

The skill itself is your teacher here — its explainers are written for someone who does not know the terms. If an explainer still does not land, ask Claude Code, before answering the prompt: "Before I choose, show me what each option would write to docs/agents/issue-tracker.md." Bring anything still unclear to the weekly meeting.
