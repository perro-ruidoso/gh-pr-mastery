Step 3 — Create your Instance from the template

flashcards-seed is a template repository, not an ordinary one. Creating from a template is not the same as forking, and the difference is worth understanding now because you will do both in this course — template today, fork in Week 6.

From a template

Per GitHub's docs, a repository created from a template "starts with a single commit" — none of the template's history comes with it.

Your commits do appear in your contributions graph.

No ongoing relationship to the original. It is your repository.

From a fork

A fork "includes the entire commit history of the parent repository."

Commits to a fork do not appear in your contributions graph.

Stays linked to the parent — which is what makes cross-repo pull requests possible (Week 6).

Template is right here: you want a clean history that is yours, because from Week 3 onward your history is the thing being read and graded. Create it from the terminal:

$ gh repo create perro-ruidoso/flashcards-<your-handle> \
    --template perro-ruidoso/flashcards-seed \
    --public \
    --clone

Three flags, three jobs. --template makes "the new repository based on a template repository"; --public sets visibility (the alternatives are --private and --internal); and --clone drops a local copy in the current directory, so you can go straight in:

$ cd flashcards-<your-handle>
$ git log --oneline
a1b2c3d (HEAD -> main, origin/main) Initial commit

One commit. That is the template behaviour, confirmed from your own terminal rather than taken on faith.

Yes, --public is required

Not a typo and not laziness. Merge queue — which Week 5 depends on — is available in any public repository owned by an organization, but for a private repository it requires GitHub Enterprise Cloud. A private Instance would put that objective out of reach. Public repositories also get unlimited free Actions minutes, so the CI you configure in Week 5 costs nothing to run over and over. Keep nothing personal in this repo. The full reasoning is in adr/0003.

What a template does not copy

GitHub's page says a template copies "the same directory structure and files." It says nothing about labels, and the course verified by experiment that labels are not copied: every new repository — template-derived or not — arrives with GitHub's current default label set (bug, documentation, wontfix, and seven more). Remember this when M05 asks you to create labels: one of the five you need is already there.

Step 4 — Confirm the app runs

The Instance is a small Python CLI. Set it up and run its tests once, so that when CI fails in Week 5 you know it is CI's fault and not your machine's:

$ python -m venv .venv
$ source .venv/bin/activate      # Windows: .venv\Scripts\activate
$ pip install -e ".[dev]"
$ pytest -q

Then open Claude Code in the repository — claude — and ask it to describe the project. It will read the CLAUDE.md and CONTEXT.md that ship with the template. Those files are why an agent can be useful here on its first turn instead of its tenth.

Self-check

1. You create a repository from a template and run git log. How much history do you expect?

C. GitHub's documentation is explicit: a repository created from a template "starts with a single commit," whereas a fork "includes the entire commit history of the parent repository." That is the central difference between the two, along with the contributions graph.

2. Why does this course insist your Instance be public?

B. Merge queue is available in any public repository owned by an organization, but for a private repository it requires GitHub Enterprise Cloud — so M29 would be unreachable on a private Instance. Public repositories also run Actions for free. (C is false — gh reads private repos fine; D is false — Actions runs on private repos, it just consumes metered minutes.)

3. When would a fork be the right choice instead of a template copy?

B. A fork stays linked to its parent, and that link is what a cross-repository pull request rides on — which is exactly what Week 6's fork drill needs. A and C are properties of the template path, and D depends on visibility, not on how the repository was created.

4. Immediately after creating your Instance, gh label list shows ten labels you never made. Where did they come from?

D. Verified by experiment when the template was built: a label deleted from the template still appeared on a fresh Instance, so the set comes from GitHub's defaults, not from the template. (There is no org-wide label push on this org, and --clone only affects your local copy.) They also take a few seconds to appear — an immediate gh label list can come back empty.

How much history does a repository created from a template start with?
A single commit. None of the template's history comes across — GitHub Docs: "starts with a single commit."
How much history does a fork start with?
All of it — a fork "includes the entire commit history of the parent repository."
Template copy vs fork: which one puts your commits in your contributions graph?
The template copy. Commits to a fork do not appear in your contributions graph.

Why must the Instance be public? Name the one gate that forces it.
Merge queue (Week 5, M29): available in any public repo owned by an org, but private repos need GitHub Enterprise Cloud. Free Actions minutes are the bonus.
Does a template copy the template's labels?
No. Every new repository gets GitHub's default label set (including wontfix) whether or not it came from a template — verified by experiment on 2026-09-12.

Template in Week 1 (your Instance). Fork in Week 6 (contributing to the Upstream Repo from outside).
