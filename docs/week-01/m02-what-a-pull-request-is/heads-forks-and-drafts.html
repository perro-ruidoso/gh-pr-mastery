Heads, Forks, and Drafts

The head branch can live in someone else's repository. Draft is a state, not a folder. And a pull request is a GitHub idea, not a git one.

M02 · The PR model Bloom: Understand Assessed by: Quiz 1

Objective: Explain a pull request as a request to merge one ref into another, naming base and head, and identify both for any open PR.

head can live somewhere else entirely

Listing open PRs on cli/cli shows something the single-PR view on the previous page hid:

$ gh pr list -R cli/cli --limit 3 
14373  docs: Add step to install working version on Ubuntu Pro  acoulton:patch-1                    OPEN   2026-09-07T10:43:26Z
14355  Remove obsolete Git test seams                           williammartin-clean-git-test-seams  DRAFT  2026-09-04T15:50:28Z
14351  Improve git client tests                                 williammartin-improve-git-tests     DRAFT  2026-09-04T15:36:50Z

Look at the third column (captured 2026-09-13; the open list moves daily, the shape does not). One of these heads is written owner:branch — acoulton:patch-1 — and two are bare branch names. That is the difference between a cross-repository pull request, whose head branch lives in a contributor's fork, and a same-repository one, whose head branch lives in cli/cli itself. In --json output the same fact is the boolean isCrossRepository.

The base repository still owns the pull request. GitHub's documentation explains how: "When you open a pull request, GitHub creates temporary Git references that point to the pull request's head branch and, when possible, to a simulated merge result." Those refs are how CI, reviews, and the merge button can operate on code that lives in somebody else's copy — and, the docs add, they are "most relevant when you are building automation, debugging CI behavior, or fetching pull request state locally." You will meet them again in Week 5.

Two development models

GitHub names the two ways a project can use pull requests, and this course uses both — on purpose, in different weeks:

Shared repository model

Contributors have write access. They push branches to the repository itself and open same-repo PRs. Head and base live together.

Weeks 1–5: your Instance, and the Upstream Repo in write-access mode.

Fork and pull model

Anyone with read access forks the "upstream" repository, works in the fork, and opens a cross-repository PR back. Head lives in the fork.

Week 6: one deliberate drill, so you feel what an outside contributor feels.

This distinction returns, and it bites

In Week 5 you will learn that a pull request from a fork cannot read the base repository's Actions secrets — so agentic review in CI cannot run on it. That limit is a direct consequence of what you just read: the head branch is untrusted code from outside the repository. Same-repo PR, secrets available. Fork PR, no secrets. Remember where you first saw the distinction; the reasoning is written up in adr/0004.

Draft is a state, not a folder

PR 14355 above is DRAFT. GitHub's docs describe two states — draft and ready for review — and draft means two concrete things:

  • It cannot be merged, regardless of approvals or green checks.
  • Code owners are not automatically requested for review (Week 5's CODEOWNERS routing simply does not fire).

Drafts let you "share work-in-progress without formally requesting reviews," and "you can convert a pull request to a draft at any time." Marking a draft ready "will request reviews from any code owners." For an agentic workflow this is more useful than it looks: opening a draft PR the moment the branch exists gives you a stable URL, a running CI signal, and a place to accumulate notes while the agent works — without putting a reviewer on the hook.

Self-check

1. In gh pr list, one PR's head shows as acoulton:patch-1 and another as clean-git-test-seams. What does the difference tell you?

C. The owner:branch form marks a cross-repository pull request whose head lives in a contributor's fork. A bare branch name means the head branch is in the base repository itself. Draft state, approvals, and the base branch are all shown elsewhere.

2. Which statement about draft pull requests is correct?

D. Those are exactly the two behaviours GitHub's docs attach to draft state. CI still runs (that is much of the point of opening a draft early), and a draft on a public repository is as visible as any other PR.

3. Week 6 has you fork the Upstream Repo and open a PR from the fork. Which development model is that, in GitHub's terms?

B. Fork and pull: fork the upstream, work in the fork, open a cross-repository PR back. Weeks 1–5 use the shared repository model, where contributors push branches to the repository itself. C and D are not development models — stacking is a base-branch choice (Week 3) and draft is a PR state.

4. A PR's head branch lives in a contributor's fork, yet CI on the base repository builds it. What makes that possible?

A. "GitHub creates temporary Git references that point to the pull request's head branch and, when possible, to a simulated merge result." Nothing is merged and nothing is pushed twice. Those refs are also why a fork PR's code is treated as untrusted — it is external code checked out inside the base repository's automation — which is the reason secrets are withheld from it (Week 5).

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

In gh pr list, what does a head written owner:branch mean?
A cross-repository PR — the head branch lives in owner's fork, not in the base repository. A bare branch name means same-repo.
Which --json field says whether a PR's head is in a fork?
isCrossRepository — true for a fork PR, false when head and base share a repository.
How can the base repository run CI on code that lives in a fork?
GitHub creates temporary Git references in the base repo pointing at the head branch and, when possible, a simulated merge result.
Name GitHub's two collaborative development models, and the weeks this course uses each.
Shared repository model (Weeks 1–5: push branches directly) and fork and pull model (Week 6: one deliberate drill).
State the two concrete consequences of draft state.
The PR cannot be merged, and code owners are not automatically requested for review. CI still runs.
Why can agentic review in CI not run on a PR from a fork?
Secrets are withheld from workflows triggered by a fork PR — the head is untrusted external code. Same-repo PR: secrets available. Fork PR: none. (Week 5, adr/0004.)
Is a pull request a git concept?
No. Git has branches and merges; the pull request is a GitHub construct owned, numbered, and stored by the base repository.
Name the two ways a pull request can end.
Merged, or closed without merging.
