Two Refs and a Conversation

A pull request is a proposal to merge one specific ref into one specific other ref. Everything else — reviews, checks, labels, merge buttons — hangs off that.

M02 · The PR model Bloom: Understand Assessed by: Quiz 1

Objective: Explain a pull request as a request to merge one ref into another, naming base and head, and identify both for any open PR.

The definition, and the part people skip

GitHub's own words: "Pull requests are proposals to merge code changes into a project." The documentation calls a pull request "GitHub's key collaboration feature, letting you discuss and review changes before merging them."

That is accurate but incomplete in a way that causes real confusion. A pull request is a proposal to merge one specific ref into one specific other ref, and it names both:

Where it would go base

The branch you are asking to change. Often main — but very often not, and in Week 3 you will deliberately point a PR at another PR's branch.

What you are offering head

The branch holding your work. It does not have to live in the same repository as the base — that is what makes fork contributions possible.

A pull request is not a bundle of changes. It is a live comparison between two moving refs. Push to the head branch and the PR updates itself; nobody re-uploads anything. This is why a PR can "change" while you are asleep, and why M03 exists.

Reading base and head off a real pull request

Here is an actual pull request in the cli/cli repository — the GitHub CLI's own codebase — read from the terminal on 2026-09-13:

$ gh pr view 14398 -R cli/cli --json number,title,state,isDraft,baseRefName,headRefName,changedFiles 
{
  "baseRefName": "trunk",
  "changedFiles": 1,
  "headRefName": "issue-12195",
  "isDraft": false,
  "number": 14398,
  "state": "CLOSED",
  "title": "Check for merged state when viewing a PR via the issues command"
}

This PR was open when the course first captured it on 2026-09-12 and was closed, unmerged, the next morning (closedAt 2026-09-13T06:06:03Z, mergedAt null). Closing it changed state and nothing else: the two refs it names are still recorded, which is why the sentence below still reads the same. Run the command yourself and the only field that may have moved again is state.

Read it as a sentence: pull request 14398 proposes merging issue-12195 into trunk. That sentence — head into base — is the whole objective. If you can produce it for any PR from its baseRefName and headRefName, you have M02.

The base is not always main

Note "baseRefName": "trunk". The cli/cli project's default branch is called trunk, not main. Every habit you build that assumes the word "main" will eventually break on a real repository — and on your own stacked pull requests in Week 3, where the base is another feature branch on purpose. Read the base; never assume it.

The conversation around the two refs

GitHub organises everything that accumulates around the comparison into tabs, and the documentation names them:

TabWhat it showsWhere it returns in this course
Conversation"the description, timeline, comments, and reviews"Week 4 — review mechanics and writing comments a peer can act on
Commits"how the pull request branch changed over time"Week 3 — the shape of a reviewable diff
Checks"automated tests, builds, and other validations"Week 5 — CI and required status checks
Files changed"the diff that reviewers use to understand the proposed changes"M03, next — and every review you ever do
Findings"automated code review results, such as code scanning alerts"Week 4 — separating findings from defects

Separately from the tabs, the merge status "highlights blockers, missing approvals, and other requirements before merging." It sits in the header and the merge box. In Week 5 you will be the one configuring what appears there.

The habit to form this week

Whenever you open a pull request — yours, a classmate's, a stranger's — say the sentence first: "This proposes merging head into base." Only then read the title. It takes two seconds and it is the check that catches a PR pointed at the wrong branch before anyone reviews the wrong diff.

Self-check

1. A pull request says its base is release-2.4 and its head is fix/token-refresh. What is being proposed?

B. Head is what you are offering; base is where it would go. The default branch is irrelevant — a PR names its own base, and here that base is a release branch rather than main.

2. You open a PR, then push three more commits to your branch. What must you do to update the pull request?

A. A pull request is a live comparison between two refs, not an uploaded snapshot. Pushing to the head branch updates the PR by definition. (Re-requesting review is a social act — it tells a human to look again — and does not change what the PR contains.)

3. A reviewer wants "the diff that reviewers use to understand the proposed changes." Which tab is that, in GitHub's own description?

D. Files changed is the diff. Conversation holds the description, timeline, comments, and reviews; Commits shows how the branch changed over time (each commit's diff, not the whole proposal); Checks shows automated validations. Knowing which tab answers which question is what lets you read a PR quickly.

4. gh pr view 14398 -R cli/cli --json baseRefName prints "trunk". What should you conclude?

C. A PR names its own base, and cli/cli happens to call its default branch trunk. Reading baseRefName rather than assuming it is the whole point of the exercise. (B has the fields backwards; D invents a rule that does not exist.)

Flashcards

Define base.
The branch the pull request is asking to change — where the work would go. Often main, but not necessarily.
Define head.
The branch holding the proposed work — what you are offering. It may live in a different repository from the base.
Given baseRefName and headRefName, say the pull request as a sentence.
"This PR proposes merging head into base." Head first, base second.
Is a pull request a snapshot of your changes?
No — it is a live comparison between two moving refs. Pushing to the head branch updates the PR by itself.
What is cli/cli's default branch called, and why does the course keep pointing at it?
trunk. It breaks the "base is always main" habit before Week 3's stacked PRs break it for you.
Name the five tabs of a pull request page.
Conversation, Commits, Checks, Files changed, Findings.
Which tab shows "the diff that reviewers use", and which shows "how the pull request branch changed over time"?
Files changed shows the diff. Commits shows the branch's history.
Which gh command reads base and head for PR N in repo O/R?
gh pr view N -R O/R --json baseRefName,headRefName
