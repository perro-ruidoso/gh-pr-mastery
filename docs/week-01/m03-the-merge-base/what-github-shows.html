What GitHub Shows You

The Files changed tab is a three-dot diff. That single design decision is why your PR stays stable while main moves — and why the scope you hand an agent decides whether its review is worth reading.

M03 · Diffs Bloom: Understand Assessed by: Quiz 1

Objective: Distinguish two-dot from three-dot diffs and explain why a PR's Files-changed view is computed from the merge base.

The Files changed tab

GitHub's reference page says the Files changed tab "shows what would change if the pull request merged." On the branches page it explains how: "Because the three-dot comparison uses the merge base, it focuses on 'what a pull request introduces.'" Then it contrasts the alternative directly:

"When you use a two-dot comparison, the diff changes when the base branch is updated, even if you haven't made any changes to the topic branch. A two-dot comparison also focuses on the base branch, which can make the changes introduced by the topic branch harder to understand. In contrast, a three-dot comparison keeps showing the changes introduced by the topic branch since the branches diverged."

This is a genuinely good design choice. If pull requests used two-dot diffs, every merge into main would visibly churn every open PR, and reviewers would spend their attention on other people's changes.

Compare pages are not PR pages

GitHub's reference page carries a caution worth memorising: "Compare pages and pull request pages can calculate changed files from different merge bases. As a result, the same branches can sometimes show different diffs in each place." This "usually matters when the base branch has changed since the pull request was created" — the PR page "focus[es] on what the pull request introduced, while compare pages reflect the current comparison between two refs." If a classmate's /compare/ link disagrees with the PR, neither is lying; they are answering different questions.

Then why do I sometimes see unrelated files in a PR?

Three-dot diffing removes the most common cause, so when it still happens the reason is almost always one of:

  • You merged main into your branch and resolved a conflict. Those resolutions are your changes, and they belong to your branch.
  • You rebased onto a moved base and the rebase carried something unexpected.
  • The head branch was created from something other than the base — a stale local main, or a different branch entirely.

Diagnosis starts the same way every time — find the merge base and look at what sits between it and your tip: git merge-base main HEAD, then git log --oneline <that-sha>..HEAD.

Why an agentic coder needs this specifically

You will routinely ask Claude to "review the changes on this branch." What it compares determines what it reports:

  • Point it at a two-dot range and it will dutifully review your colleague's changes in reverse, and may report them as regressions. You then waste a cycle arguing with a correct answer to the wrong question.
  • Point it at main...HEAD and it reviews what you introduced — the same scope a human reviewer sees on the PR.

This is why the /code-review skill you will run in Week 4 pins a "fixed point" and then captures the diff as git diff <fixed-point>...HEAD — its own instructions say "three-dot, so the comparison is against the merge-base." The skill's authors made the choice for you; knowing why is what lets you notice when a different tool, or a hand-typed prompt, gets it wrong. Wrong scope produces confident, well-written, irrelevant findings.

The check before you ask for a review

Before handing a branch to an agent — or a human — run git diff main...HEAD --stat and read the file list. If a file is there that you did not mean to touch, you have found the problem before the reviewer did. Week 3's M14 turns this into a formal judgement about whether a diff is reviewable at all.

Hands-on checklist

Self-check

1. Ten commits land on main while your PR sits open, none touching your files. What happens to the PR's Files changed tab?

A. GitHub's docs: "a three-dot comparison keeps showing the changes introduced by the topic branch since the branches diverged," whereas with two-dot "the diff changes when the base branch is updated, even if you haven't made any changes to the topic branch." (B and C are what you would get from a two-dot view. D confuses the diff with a merge requirement — a ruleset can demand the branch be up to date, but that is a separate gate, covered in Week 5.)

2. You ask Claude to review "the changes on this branch" and it reports bugs in code a teammate wrote last week. What is the most likely cause?

D. Wrong scope, not wrong model. A two-dot range folds the base branch's newer commits into the diff, so the reviewer sees changes that are not yours and reasons about them correctly but uselessly. Pass main...HEAD — the same scope the PR shows a human. (B is worth keeping in mind as a secondary possibility, but if it were true you would want it filed as its own issue, not smuggled into your PR's review.)

3. A /compare/main...feature page and the PR for feature show different file lists. Why can that happen?

C. GitHub's own caution, almost verbatim. It "usually matters when the base branch has changed since the pull request was created." Neither page is stale or lying — they are answering different questions, which is exactly why you should know which one you are looking at.

4. Your PR shows a conflict-resolution change in a file you never edited by hand. Is that file legitimately part of your PR?

B. A merge commit on your branch, and whatever you did to resolve the conflict inside it, sits between the merge base and your tip — so the three-dot diff includes it, correctly. This is one of the three legitimate reasons an "unrelated" file appears; the diagnosis is always the same: find the merge base and read what lies between it and HEAD.
