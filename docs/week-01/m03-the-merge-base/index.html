The Merge Base

One idea explains why a pull request shows what it shows and why your local git diff sometimes accuses you of deleting a colleague's work. Two dots versus three.

M03 · Diffs Bloom: Understand Assessed by: Quiz 1

Objective: Distinguish two-dot from three-dot diffs and explain why a PR's Files-changed view is computed from the merge base.

M03 pages 1The Merge Base 2What GitHub Shows You

The situation that creates the confusion

You branch off main and add a line to one file. While you work, a colleague merges a change to a completely different file. Now two branches have diverged from a shared ancestor:

$ git log --all --oneline --graph 
* 12ccbf6 Add my line to shared.txt          <- your branch: feature
| * 8c7a482 Someone else edits untouched.txt <- main moved on
|/
* 9c332a8 Initial commit                    <- the shared ancestor

That bottom commit — the most recent commit both branches have in common — is the merge base. Git will tell you which one it is:

$ git merge-base main feature 
9c332a8037d289c6588c65b802bdae0797dda779

Two ways to compare, and they disagree

Now ask "what did I change?" two different ways. First with two dots:

$ git diff main..feature --stat 
 shared.txt    | 1 +
 untouched.txt | 2 +-
 2 files changed, 2 insertions(+), 1 deletion(-)

Two files. But you only touched one. Look at what it claims you did to the other:

$ git diff main..feature 
diff --git a/untouched.txt b/untouched.txt
--- a/untouched.txt
+++ b/untouched.txt
@@ -1 +1 @@
-CHANGED BY SOMEONE ELSE
+original

It reads as though you deleted your colleague's work and restored the old text. You did not. Now the same question with three dots:

$ git diff main...feature --stat 
 shared.txt | 1 +
 1 file changed, 1 insertion(+)

One file, one line. That is what you actually did — and that is what GitHub shows in a pull request.

Why they differ

GitHub's documentation states the rule in a two-row table. A three-dot comparison, git diff A...B, compares "the most recent common commit of both branches (merge base) and the most recent version of the topic branch." A two-dot comparison, git diff A..B, compares "the most recent state of the base branch (for example, main) and the most recent version of the topic branch." And the sentence above the table: "Pull requests on GitHub show a three-dot diff."

Two dots — main..feature

Compares the tip of main to the tip of your branch.

Answers: "what would I have to do to turn main into my branch?"

Includes, in reverse, every change on main that your branch lacks. Moves every time main moves.

Three dots — main...feature

Compares the merge base to the tip of your branch.

Answers: "what did my branch introduce?"

Ignores everything that happened on main after you branched. Stable while main moves.

Two dots measure from the tip of the base. Three dots measure from the merge base. A pull request always uses three.
When the two agree

GitHub's docs add a useful corollary: "When you merge the base branch, the diffs shown by two-dot and three-dot comparisons are the same." Merging main into your branch moves the merge base up to main's tip, so there is nothing left for the two-dot view to show in reverse. That is why "merge main into your branch" makes the phantom changes vanish — and why the docs recommend doing it often.

A habit worth forming today

When you want "what does my branch add," type three dots. When you genuinely want "how do these two tips differ" — comparing two releases, say — type two. If you are unsure which you want, you want three.

The next page takes this into the Files changed tab, explains the cases where unrelated files still show up, and says why it decides whether you can trust an agent's review.

Hands-on checklist

Reproduce the divergence above in your own Instance. It takes four minutes and you will never forget the result.

Self-check

1. git diff main..feature lists a file you never opened, showing its lines being reverted. What happened?

C. Two dots compare the tip of main with the tip of your branch. Your branch simply does not contain the colleague's newer commit, so relative to main's tip that content is "missing" — and the diff renders it as a deletion. Use three dots and it disappears, because three dots measure from the merge base, before their change existed.

2. What exactly is the merge base of two branches?

B. The merge base is their most recent common ancestor — git merge-base reports it. (D is a tempting trap: the merge base is not frozen at PR-open time; it is recomputed, and it moves if you merge the base into your branch.)

3. You merge main into your feature branch. How do main..feature and main...feature now compare?

A. Straight from the docs: "When you merge the base branch, the diffs shown by two-dot and three-dot comparisons are the same." After the merge, the most recent common commit of both branches is main's tip, so tip-to-tip and merge-base-to-tip measure from the same point. A rebase also works, but it is not the only way.

4. Which comparison does a pull request's Files changed tab use?

D. "Pull requests on GitHub show a three-dot diff." There is no author choice and no dependence on where the head lives. This is what makes the Files changed tab answer "what did this branch introduce?" rather than "how do these two tips differ?"

Define the merge base of two branches.
Their most recent common ancestor — the newest commit that is in both branches' histories.
Command that prints the merge base of main and feature?
git merge-base main feature
What does git diff main..feature (two dots) compare?
The tip of main against the tip of feature. It answers "how do these two tips differ?" and moves whenever main moves.
What does git diff main...feature (three dots) compare?
The merge base against the tip of feature. It answers "what did this branch introduce?" and is stable while main moves.
Which comparison does a GitHub pull request show?
Three-dot. GitHub Docs: "Pull requests on GitHub show a three-dot diff."
Two-dot shows a colleague's file with their lines removed. Did you delete anything?
No. Their commit is on main's tip but not on your branch, so tip-to-tip renders it as a deletion. Three-dot measures from before it existed.
When do two-dot and three-dot show the same diff?
After you merge the base branch into your topic branch — the merge base becomes the base's tip. GitHub Docs: "the diffs shown by two-dot and three-dot comparisons are the same."
Unsure which you want — two dots or three?
You want three. Two is only for genuinely comparing two tips, such as two releases.

If the two-dot result still looks wrong to you, that is the right instinct — ask Claude Code, in the repository where you ran the experiment: "Explain, commit by commit, why git diff main..feature shows untouched.txt and main...feature does not."
