GitHub Pull Requests for Agentic Coders Week 1 · Objective M04

Reading Work From the Terminal

The web UI is for humans reading one thing. The CLI is for asking precise questions, piping the answers, and handing them to an agent.

M04 · Tooling Bloom: Apply Assessed by: A1 (checker)

Objective: Inspect issues and PRs from the terminal with gh issue/pr list, view, and diff, including --json field selection.

Why not just use the website?

Use the website — it is excellent. But three things only the CLI gives you, and all three matter in this course:

  • Precision. "Which open PRs target a base other than main?" is one command, not twenty clicks.
  • Structure. --json returns data you can filter, count, and assert on. Every assignment checker in this course is built from it.
  • Agent parity. When Claude works with GitHub, it uses these same commands. Knowing what they return means you can read what your agent did, and tell it exactly what to run.
Try these against a real repository

Every command on this page uses -R cli/cli — the GitHub CLI's own public repository — so you can run them right now, before your Instance has any interesting history. Your numbers will differ from the outputs shown; the shapes will not.

Listing: what is in flight?

$ gh pr list -R cli/cli --limit 3 
14398  Check for merged state when viewing a PR via the issues command  timmattison:issue-12195   OPEN   2026-09-08T18:25:17Z
14373  docs: Add step to install working version on Ubuntu Pro          acoulton:patch-1          OPEN   2026-09-07T10:43:26Z
14355  Remove obsolete Git test seams                                   williammartin-clean-git-test-seams  DRAFT  2026-09-04T15:50:28Z

Number, title, head ref, state, age. Note the third column again — owner:branch means a fork, as M02 covered.

Viewing: the fields that matter

Plain gh pr view 14398 -R cli/cli prints a readable summary. Add --json and you choose exactly what you get:

$ gh pr view 14398 -R cli/cli --json number,title,state,isDraft,baseRefName,headRefName,additions,deletions,changedFiles 
{
  "additions": 2,
  "baseRefName": "trunk",
  "changedFiles": 1,
  "deletions": 0,
  "headRefName": "issue-12195",
  "isDraft": false,
  "number": 14398,
  "state": "OPEN",
  "title": "Check for merged state when viewing a PR via the issues command"
}

Two lines added, one file touched. That is a reviewable diff — a judgement you will make formally in Week 3.

Discovering the field names

You do not need to memorise them. Ask for a field that does not exist and gh lists the real ones:

$ gh pr view 14398 -R cli/cli --json nope 
Unknown JSON field: "nope"
Available fields:
  additions
  assignees
  author
  autoMergeRequest
  baseRefName
  baseRefOid
  …and about two dozen more
A trick worth keeping

Deliberately asking for a bogus field is the fastest way to see what a gh command can return. It works for gh issue view, gh pr list, and gh run list too.

Filtering: --jq

gh has jq built in via -q/--jq, so you can reshape output without installing anything:

$ gh issue list -R cli/cli --limit 3 --json number,title,labels --jq '.[] | {number, title, labels: [.labels[].name]}' 
{"labels":["needs-triage"],"number":14432,"title":"docs: improve README wording for quick start"}
{"labels":["more-info-needed","needs-triage"],"number":14420,"title":"gh 2.100.0 fails HTTPS requests with an instant connection reset"}
{"labels":["enhancement"],"number":14413,"title":"Feature request: allow selecting fields for human-readable list output"}

Notice the labels: needs-triage, more-info-needed. A real project runs a triage vocabulary very like the one you will configure in M05 and use in Week 6.

Extracting a single value is the building block of every script you will write here:

$ gh pr list -R cli/cli --limit 1 --json number --jq '.[0].number' 
14398

Diffing: what actually changed

$ gh pr diff 14398 -R cli/cli --name-only 
pkg/cmd/issue/view/view.go

Drop --name-only for the patch itself. gh pr diff shows the pull request's diff — which, per M03, is the three-dot comparison against the merge base, not a tip-to-tip diff. The CLI and the website agree because they are asking the same question.

Putting it together

Two questions you could not answer quickly in the web UI:

# Which open PRs target a base branch other than the default? 
$ gh pr list -R cli/cli --limit 50 \
    --json number,baseRefName,title \
    --jq '.[] | select(.baseRefName != "trunk")'
# How big is each open PR, largest first? 
$ gh pr list -R cli/cli --limit 20 \
    --json number,title,additions,deletions \
    --jq 'sort_by(-(.additions + .deletions))
          | .[] | "\(.number)\t\(.additions + .deletions)\t\(.title)"'

The second is worth running on any repository you join. Pull request size predicts review quality better than almost anything else, and a list sorted by size tells you where review is failing before anyone admits it.

Give your agent the command, not the screenshot

When you want Claude to reason about a pull request, the useful move is to tell it which gh command to run, or paste the --json output. Pasting a screenshot or a URL forces it to guess at structure it could have read exactly. This becomes a habit in Week 4, when /code-review needs a precise scope.

Hands-on checklist

A1's checker looks for evidence of items 2 and 5 in your write-up.

Self-check

1. You cannot remember what fields gh pr view --json accepts. Fastest way to find out, without leaving the terminal?

B. gh pr view N --json nope prints Unknown JSON field: "nope" followed by every valid field. (A prints a human summary but not the field names; C works but is enormous overkill; D is simply false.)

2. gh pr diff shows a pull request's changes. Which comparison is it showing?

D. The CLI and the web UI are asking the same question of the same pull request, so they agree. That is exactly why the CLI is trustworthy as a review surface — and why you can hand its output to an agent without worrying that it differs from what a human reviewer sees.

3. Why does this course build its assignment checkers out of --json output rather than screenshots or self-reports?

C. The artifacts you produce — branch names, linked issues, passing checks, a closed issue after merge — are the evidence that the workflow happened. --json turns that evidence into something a script can assert on, which is why most of A1 is graded automatically and only the written analysis needs a human.
