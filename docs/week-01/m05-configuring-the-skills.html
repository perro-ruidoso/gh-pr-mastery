GitHub Pull Requests for Agentic Coders Week 1 · Objective M05

Teaching Your Repo to the Skills

Three decisions, written to three files, that every engineering skill you use for the next five weeks will read before it does anything.

M05 · Agent config Bloom: Apply Assessed by: A1 (checker)

Objective: Configure an Instance for the engineering skills with /setup-matt-pocock-skills: issue tracker, triage label vocabulary, and domain docs.

What a skill is, and why it needs configuring

A skill is a packaged set of instructions Claude Code loads when a task matches it. This course uses a family of engineering skills — /to-spec, /to-tickets, /implement, /code-review, /qa, /triage — that form the workflow spine of Weeks 2 through 6.

Several of them read from and write to your issue tracker. But a skill cannot guess whether "file this ticket" means gh issue create, a markdown file in a scratch folder, or something else entirely. So they all read a small set of configuration files, and /setup-matt-pocock-skills is the one-time run that writes them.

Run it once, in your Instance

This is a setup skill, not a working one. Run it today in flashcards-<your-handle>, commit what it writes, and then forget about it — the other skills pick the files up automatically. You will edit them by hand if your conventions change, rather than re-running.

The run

Open Claude Code in your Instance and invoke it:

$ cd flashcards-<your-handle>
$ claude
> /setup-matt-pocock-skills

It explores the repo first — git remotes, existing CLAUDE.md, any CONTEXT.md or ADR directories — then walks you through three decisions one at a time. Read each one; do not just accept defaults you have not understood.

Decision A — Where do issues live?

The skill offers GitHub, GitLab, local markdown files, or "other" (Jira, Linear, and anything else) described in your own prose.

Choose GitHub. Your remote points at GitHub, and this course's entire premise is that GitHub Issues is the source of truth for work. That choice writes a file telling every skill exactly how to operate:

Extract from docs/agents/issue-tracker.md
  • Create an issue: gh issue create --title "..." --body "..."
  • List issues: gh issue list --state open --json number,title,body,labels,comments
  • Apply / remove labels: gh issue edit <number> --add-label "..."

Those are the same commands you learned in M04. That is not a coincidence — you and your agent drive GitHub through one interface, which is why reading that interface fluently was worth a lesson.

Why not Linear, given Week 2?

You will connect Linear at the end of Week 2 — but as the project-management layer above GitHub, not as the tracker the skills write to. These skills support GitHub, GitLab, and local markdown natively; Linear falls under "other," where you would have to describe the whole workflow in prose and maintain it yourself. Keeping GitHub as the source of truth keeps the tooling first-class and lets Linear do what it is genuinely better at. Week 6's M35 asks you to defend that choice — or argue against it.

The follow-up question: PRs as a request surface

Because you picked GitHub, the skill asks one more thing: should /triage pull external pull requests into the same queue as issues? The default is no.

Answer no for your Instance. Nobody else contributes to it. You will flip this to yes in Week 6, on the shared upstream repository, where classmates' incoming PRs are exactly the queue you are triaging. Note now how it works, because it is a neat piece of filtering — the skill keeps only PRs whose authorAssociation is CONTRIBUTOR, FIRST_TIME_CONTRIBUTOR, or NONE, dropping OWNER, MEMBER, and COLLABORATOR, so a maintainer's own in-flight work is left alone.

Decision B — The triage label vocabulary

Skills speak in terms of five canonical roles. This file maps each role to the label string your repository actually uses:

RoleMeaning
needs-triageMaintainer needs to evaluate this issue
needs-infoWaiting on the reporter for more information
ready-for-agentFully specified — an agent can pick it up with no human context
ready-for-humanRequires human implementation
wontfixWill not be actioned

Accept the defaults. The mapping exists so that a repo already using, say, bug:triage can point the skills at its own vocabulary instead of growing a duplicate set of labels — but your Instance starts clean, so the canonical strings are correct.

ready-for-agent is the one to watch

Of the five, that label carries the most weight in this course. It asserts something strong: this issue is specified well enough that a fresh session, with no memory of the conversation that produced it, can execute it. Week 2 is largely about earning the right to apply it, and the gap between an issue you understand and an issue that label describes is where most agentic work quietly fails.

Decision C — Domain docs

Some skills read a CONTEXT.md for the project's domain language, and docs/adr/ for past architectural decisions. The skill asks whether this repo has one context or several.

Choose single-context. Your Instance is one small application; a CONTEXT.md already ships with the template, defining what a deck, a card, an interval, and an ease factor mean in this codebase. Multi-context is for monorepos with genuinely separate frontend and backend vocabularies.

What you end up with

Before it writes anything, the skill shows you a draft and lets you edit. Then it produces:

  • docs/agents/issue-tracker.md — how to create, read, label, and close work
  • docs/agents/triage-labels.md — the five roles mapped to your label strings
  • docs/agents/domain.md — where CONTEXT.md and ADRs live, and the rules for reading them
  • An ## Agent skills section added to your existing CLAUDE.md, summarising all three and pointing at the files

Commit all of it. These files are part of the repository's contract with every future agent session, which makes them exactly as reviewable as code — and in Week 4 you will review a change to one.

One number space, two kinds of thing

Worth internalising before Week 2: GitHub shares a single number space between issues and pull requests, so a bare #42 may be either one. If you are scripting, resolve it explicitly — try gh pr view 42 and fall back to gh issue view 42. This trips up more automation than any other GitHub quirk.

Hands-on checklist

A1's checker verifies that the three files exist and are committed.

Self-check

1. Why do the engineering skills need an issue-tracker.md at all?

C. The skills are tracker-agnostic by design; the config file is what binds an abstract instruction ("publish to the issue tracker") to concrete commands in your repository. Credentials live in your gh token, not in the repo.

2. You answer "no" to PRs as a request surface in your Instance. When would "yes" be right?

B. The flag exists for repos where a PR is effectively an issue with code attached — the open-source case. It filters on authorAssociation so that collaborators' own in-flight PRs are left alone. You will turn it on for the shared upstream repo in Week 6, and it has nothing to do with visibility or collaborator count.

3. What is the strongest claim the ready-for-agent label makes?

D. That is the bar — "fully specified, AFK-ready." Size correlates but is not the claim, and it does not forbid a human from picking the work up. Week 2 exists largely to teach you how to write an issue that genuinely earns the label.

4. A script does gh issue view 42 and errors, though you can see #42 in the repository. Most likely cause?

A. GitHub numbers issues and pull requests from one sequence, so any bare reference is ambiguous. Resolve by trying gh pr view and falling back to gh issue view. (B is false — view reads closed issues fine. C and D are possible in general but would fail differently, and you said you can see it in this repo.)
