GitHub Pull Requests for Agentic Coders Week 1 · Objective M02

What a Pull Request Actually Is

Two refs and a conversation. Everything else — reviews, checks, labels, merge buttons — hangs off that.

M02 · The PR model Bloom: Understand Assessed by: Quiz 1

Objective: Explain a pull request as a request to merge one ref into another, naming base and head, and identify both for any open PR.

The definition, and the part people skip

GitHub's own words: "Pull requests are proposals to merge code changes into a project." The documentation calls them "GitHub's key collaboration feature, letting you discuss and review changes before merging them."

That is accurate but incomplete in a way that causes real confusion. A pull request is a proposal to merge one specific ref into one specific other ref, and it names both:

Where it would go base

The branch you are asking to change. Often main — but very often not, and in Week 3 you will deliberately point a PR at another PR's branch.

What you are offering head

The branch holding your work. It does not have to live in the same repository as the base — that is what makes fork contributions possible.

A pull request is not a bundle of changes. It is a live comparison between two moving refs. Push to the head branch and the PR updates itself; nobody re-uploads anything. This is why a PR can "change" while you are asleep, and why M03 exists.

Reading base and head off a real pull request

Here is an actual open pull request in the cli/cli repository — the GitHub CLI's own codebase — read from the terminal:

$ gh pr view 14398 -R cli/cli --json number,title,state,isDraft,baseRefName,headRefName,changedFiles 
{
  "baseRefName": "trunk",
  "changedFiles": 1,
  "headRefName": "issue-12195",
  "isDraft": false,
  "number": 14398,
  "state": "OPEN",
  "title": "Check for merged state when viewing a PR via the issues command"
}

Read it as a sentence: pull request 14398 proposes merging issue-12195 into trunk.

The base is not always main

Note "baseRefName": "trunk". The cli/cli project's default branch is called trunk, not main. Every habit you build that assumes the word "main" will eventually break on a real repository — and on your own stacked pull requests in Week 3, where the base is another feature branch on purpose. Read the base; never assume it.

head can live somewhere else entirely

Listing open PRs on the same repository shows something the single-PR view hides:

$ gh pr list -R cli/cli --limit 3 
14398  Check for merged state when viewing a PR via the issues command  timmattison:issue-12195  OPEN   2026-09-08T18:25:17Z
14373  docs: Add step to install working version on Ubuntu Pro          acoulton:patch-1        OPEN   2026-09-07T10:43:26Z
14355  Remove obsolete Git test seams                                   williammartin-clean-git-test-seams  DRAFT  2026-09-04T15:50:28Z

Look at the third column. Two of these heads are written owner:branch — timmattison:issue-12195 — and one is a bare branch name. That is the difference between a cross-repository pull request, whose head branch lives in a contributor's fork, and a same-repository one, whose head branch lives in cli/cli itself.

The base repository still owns the pull request. GitHub creates temporary git references in the base repository that point at the head branch, which is how CI, reviews, and the merge button can operate on code that lives in somebody else's copy.

This distinction returns, and it bites

In Week 5 you will learn that a pull request from a fork cannot read the base repository's Actions secrets — so agentic review in CI cannot run on it. That limit is a direct consequence of what you just read: the head branch is untrusted code from outside the repository. Same-repo PR, secrets available. Fork PR, no secrets. Remember where you first saw the distinction.

Draft is a state, not a folder

PR 14355 above is DRAFT. GitHub's docs describe two states — draft and ready for review — and draft means two concrete things:

  • It cannot be merged, regardless of approvals or green checks.
  • Code owners are not automatically requested for review (Week 5's CODEOWNERS routing simply does not fire).

Drafts let you "share work-in-progress without formally requesting reviews," and you can flip between draft and ready at any time. For an agentic workflow this is more useful than it looks: opening a draft PR the moment the branch exists gives you a stable URL, a running CI signal, and a place to accumulate notes while the agent works — without putting a reviewer on the hook.

Self-check

1. A pull request says its base is release-2.4 and its head is fix/token-refresh. What is being proposed?

B. Head is what you are offering; base is where it would go. The default branch is irrelevant — a PR names its own base, and here that base is a release branch rather than main.

2. In gh pr list, one PR's head shows as acoulton:patch-1 and another as clean-git-test-seams. What does the difference tell you?

C. The owner:branch form marks a cross-repository pull request whose head lives in a contributor's fork. A bare branch name means the head branch is in the base repository itself. Draft state, approvals, and the base branch are all shown elsewhere.

3. You open a PR, then push three more commits to your branch. What must you do to update the pull request?

A. A pull request is a live comparison between two refs, not an uploaded snapshot. Pushing to the head branch updates the PR by definition. (Re-requesting review is a social act — it tells a human to look again — and does not change what the PR contains.)

4. Which statement about draft pull requests is correct?

D. Those are exactly the two behaviours GitHub's docs attach to draft state. CI still runs (that is much of the point of opening a draft early), and a draft on a public repository is as visible as any other PR.
