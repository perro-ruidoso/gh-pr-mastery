Tracer Bullets and Blocking Edges

A decomposition is two decisions: how to cut the work, and what has to land before what. Cut vertically and the second decision becomes a graph you can hand to concurrent agents. Cut horizontally and it becomes a queue.

M10 · Decomposition Bloom: Create Assessed by: A2 (rubric)

Objective: Decompose a spec into 6–10 tracer-bullet tickets with declared blocking edges using /to-tickets.

M10 pages 1Tracer Bullets and Blocking Edges 2Reading the Seed Backlog

Vertical, not horizontal

/to-tickets defines the unit of work it produces with four rules, quoted in full because A2's rubric is these four lines:

  • "Each slice cuts a narrow but COMPLETE path through every layer (schema, API, UI, tests) — vertical, NOT a horizontal slice of one layer"
  • "A completed slice is demoable or verifiable on its own"
  • "Each slice is sized to fit in a single fresh context window"
  • "Any prefactoring should be done first"

In the Seed Repo, "every layer" means domain/, storage/, and cli/ — the three-layer layout was chosen (seed/SPEC.md §4) so that "a tracer-bullet ticket should have to touch all three, and a horizontal ticket should feel wrong." A horizontal decomposition of the review loop would be: (1) all the domain code, (2) all the storage code, (3) all the CLI code. Nothing is demoable until (3), the three tickets form a strict chain, and no two agents can work at once. The vertical decomposition — the one the Seed backlog actually uses — is on page 2.

"Tracer bullet"

CONTEXT.md's definition: "A ticket that crosses every layer of the app and emits observable feedback, rather than completing one layer horizontally." The metaphor is a round you can see the path of: you learn where the whole system is aimed from the first shot, not the last. The Seed Repo's flashcards list command is the tracer bullet that shipped in the template — a real, thin path through all three layers — and every backlog ticket extends it.

Blocking edges

The skill's instruction is short: "Give each ticket its blocking edges — the other tickets that must complete before it can start. A ticket with no blockers can start immediately." Two things about this are worth more than they look.

First, an edge is a claim. "B is blocked by A" says that B cannot be started — not finished, started — without A having landed. The skill asks you to check exactly this: "Are the blocking edges correct — does each ticket only depend on tickets that genuinely gate it?" Over-declaring edges is the common failure, and it is costly: every unnecessary edge removes a ticket from the set that could run in parallel.

Second, the set of edges is a graph, not a list. Once a ticket can have two blockers — and in any real backlog some will — the shape has forks and joins, and reading it as a numbered list misleads. That is the entire content of M11, where the edges become GitHub issue dependencies and get drawn.

The process

  1. Gather context. "If the user passes a reference (a spec path, an issue number or URL) as an argument, fetch it and read its full body and comments." Pass your M09 spec's number: /to-tickets #n.
  2. Explore the codebase, respecting the glossary and ADRs — and "look for opportunities to prefactor the code to make the implementation easier. 'Make the change easy, then make the easy change.'"
  3. Draft vertical slices with the four rules above, each with its blocking edges.
  4. Quiz the user. The skill presents a numbered list — Title, Blocked by, What it delivers — and asks three questions: "Does the granularity feel right?", "Are the blocking edges correct?", "Should any tickets be merged or split further?" It says "iterate until the user approves the breakdown." This is the review step; treat it as seriously as M09's seam question.
  5. Publish. On a real tracker it publishes "one issue per ticket in dependency order (blockers first) so each ticket's blocking edges can reference real identifiers," and applies ready-for-agent — "the tickets are agent-grabbable by construction." It also says: "Do NOT close or modify any parent issue."
Read the publish step's wording closely

The skill says to "use the platform's native blocking / sub-issue relationship where it has one." Those are two different GitHub features with two different shapes, and M11 shows — by experiment — that a sub-issue cannot express a ticket with two blockers. When the skill publishes, check which relation it used: gh issue view N --json blockedBy,parent. The right answer is both — parent is the spec, blockedBy is the edges — and if the edges arrived only as prose in the body, M11 tells you how to record them.

Six to ten

The objective says 6–10 tickets, and the bounds are there for reasons. Fewer than six for a feature the size of the review loop means slices too wide for "a single fresh context window" — an agent that cannot hold the whole ticket will improvise. More than ten usually means horizontal slicing crept in, or tickets that are one acceptance criterion each. The Seed backlog's fifteen cover the whole application (review loop, tags, stats, CSV); the review loop alone is its first six. If your decomposition of the same scope has three tickets or fourteen, something is off, and the quiz step is where to fix it.

Wide refactors are the exception

The skill carves out one case where vertical slicing is wrong: a wide refactor, "one mechanical change — rename a column, retype a shared symbol — whose blast radius fans across the whole codebase, so a single edit breaks thousands of call sites at once and no vertical slice can land green." For those it prescribes expand–contract: "First expand: add the new form beside the old so nothing breaks. Then migrate the call sites over in batches … each batch its own ticket blocked by the expand … Finally contract: delete the old form once no caller remains, in a ticket blocked by every migrate batch." You will not need it in a 21-file Instance; you will need it the first time you rename something in a real codebase, and the graph it produces — one fan-out, one fan-in — is worth recognising.

Hands-on checklist

A2's rubric grades the decomposition on the four slice rules and on whether every edge is genuine. check_a2.py counts tickets (6–10, type Task, ready-for-agent) and edges; the judgement is the human grader's.

Self-check

1. Which decomposition of "add a review loop" is vertical in the skill's sense?

B. That is the Seed backlog's T01–T04: each lands green with its own test and extends the running program. A is the horizontal cut the three-layer layout was designed to make "feel wrong"; C slices by activity, which is also horizontal; D fails "sized to fit in a single fresh context window."

2. What does "B is blocked by A" assert?

D. "The other tickets that must complete before it can start." Preference (A) and conflict risk (B) are not gates; C describes a sub-issue, a different feature. Over-declaring edges costs parallelism, which is why the skill's quiz asks whether each ticket depends "only … on tickets that genuinely gate it."

3. Why does the skill publish tickets "in dependency order (blockers first)"?

A. The skill's own reason: "so each ticket's blocking edges can reference real identifiers." Numbers are not an ordering (B) — page 2 shows why reading them as one misleads — GitHub accepts any edge (C), and the skill explicitly does not touch the parent (D).

4. Your decomposition of the review loop has fourteen tickets. What is the most likely diagnosis?

C. The whole Seed application is fifteen tickets; its review loop is six. Fourteen for the loop alone means slices that are not vertical or not complete. The quiz step exists for exactly this ("Should any tickets be merged or split further?"). More tickets do not mean more parallelism (D) if they form chains.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

The four vertical-slice rules?
Complete path through every layer · demoable or verifiable alone · fits one fresh context window · prefactoring first.
A tracer bullet, per CONTEXT.md?
"A ticket that crosses every layer of the app and emits observable feedback, rather than completing one layer horizontally."
What does a blocking edge assert?
The blocked ticket cannot be started until the blocker lands. Not "should be done after"; not "touches the same files".
Why is over-declaring edges costly?
Every unnecessary edge removes a ticket from the set that could run in parallel across agent sessions.
The three questions the skill asks at the quiz step?
Granularity right? Edges correct — only genuine gates? Merge or split anything?
Why publish blockers first?
"So each ticket's blocking edges can reference real identifiers." The number is an artifact of order, not a plan.
Wide refactor: the exception and its pattern?
One mechanical change with a codebase-wide blast radius. Expand → migrate in batches (each blocked by expand) → contract (blocked by every batch).
Why 6–10 tickets for the review loop?
Fewer: slices too wide for one context window. More: horizontal or one-criterion slices. The Seed's whole app is 15; its review loop is 6.
Ask your teacher

At the quiz step, before approving, ask Claude Code: "For each edge, tell me what would go wrong if an agent started the blocked ticket today, with the blocker unmerged." An edge whose answer is "nothing, really" should be deleted. Then ask it which tickets could be handed to three concurrent sessions right now. Bring anything still unclear to the weekly meeting.
