Reading the Seed Backlog

Fifteen tickets, nineteen edges, five waves. The Seed Repo's backlog is a worked decomposition of the whole flashcards application, and everything on this page was read back from what GitHub stores — not from the spec that designed it.

The fifteen tickets

One command lists every open issue with the issues that block it. The blockedBy field arrived in gh 2.94.0; on the Seed Repo it returns this (issue numbers, not the spec's T-numbers — the tickets were filed in dependency order, so the two do not line up, and that is deliberate):

$ gh issue list -R perro-ruidoso/flashcards-seed --limit 30 --json number,title,blockedBy --jq 'sort_by(.number)[] | "#\(.number)\t\(.title)\tblocked by: \([.blockedBy.nodes[].number] | map("#\(.)") | join(", "))"'

#2   Persist review state in the deck file                                   blocked by: #1
#3   SM-2 scheduler: next interval and ease update                           blocked by: #1
#4   Tag field on Card                                                       blocked by: #1
#5   `review` command: one card, prompt, grade, schedule                     blocked by: #3, #2
#6   Due-date filtering: select only cards due today                         blocked by: #3
#7   Tag persistence in the deck file                                        blocked by: #2, #4
#8   Session stats aggregation                                               blocked by: #2
#9   `review --limit N`                                                      blocked by: #6, #5
#10  `add` command with `--tags`                                             blocked by: #7
#11  `stats` command                                                         blocked by: #8
#12  CSV import, including a tags column                                     blocked by: #7
#13  `review --tag <tag>`                                                    blocked by: #9, #10
#14  `stats --by-tag`                                                        blocked by: #7, #11
#15  `export --format json|csv`                                              blocked by: #12

Columns aligned for display; gh separates them with tabs.

Read the layers off the titles: Card and scheduler and filtering and aggregation are domain; persist, deck file, CSV are storage; anything in backticks is a cli command. Now notice that the vertical slices are not single tickets but short chains: #1 → #2 → #5 is one tracer bullet (state, saved, used by a command) broken into three tickets so each lands green on its own and so #3 can proceed in parallel with #2.

Waves: what the graph is for

A wave is the set of tickets whose blockers have all landed. Derive them with Kahn's algorithm — repeatedly take every ticket with no remaining blockers, remove them, repeat — and you get the schedule for concurrent agent sessions. The course repo ships a small script that does this from gh issue list --json:

$ python seed/tools/waves_from_github.py --repo perro-ruidoso/flashcards-seed 
15 issues, 19 blocking edges, 5 joins (2+ blockers): #5, #7, #9, #13, #14
wave 1  #1
wave 2  #2  #3  #4
wave 3  #5  #6  #7  #8
wave 4  #9  #10  #11  #12
wave 5  #13  #14  #15
5 waves, max parallel width 4

Three readings of that output:

  • Width 4 at waves 3 and 4. Four tickets could each go to a fresh Claude Code session at the same time. That number — not the ticket count — is what a decomposition buys you, and it is why over-declared edges are expensive: each one narrows a wave.
  • Depth 5. The longest chain (#1 → #2 → #7 → #10 → #13, or #1 → #2 → #8 → #11 → #14) is five tickets, so fifteen tickets take a minimum of five sequential rounds no matter how many agents you have. Cutting a wide-but-shallow graph is the skill.
  • Five joins. The tickets with two blockers are where a list view lies to you. seed/SPEC.md §6 picks the clearest, in its own T-numbering: T13 (stats --by-tag, issue #14) sits next to T12 (stats, #11), "but its other parent is six tickets away in a different layer" — T08, tag persistence, issue #7, in storage. Read top to bottom, you would start #14 as soon as #11 landed and discover the missing storage work halfway through.
The answer key was machine-checked, twice

seed/SPEC.md §6 gives the waves above as the answer key for a Week 5 exercise and says "the waves above were machine-checked, not eyeballed." The first check ran a topological sort on the spec's table before any issue was filed. The one on this page is the second, independent check: it reads the edges GitHub actually stores. The two agree — 5 waves, width 4, joins at T04, T06, T08, T10, T13 — which is the evidence that the filing script recorded what the spec meant. Doing the check twice from two sources is not paranoia; it is what M06 called observation before inference.

What to copy, and what not to

Your A2 decomposition covers the review loop only — the Seed backlog's first six tickets (#1, #2, #3, #5, #6, #9) — and it is produced by /to-tickets from your own spec, so it will not match number for number. What it should share: a single root, short vertical chains rather than layer-wide tickets, at least one join, and a width greater than one somewhere. What it should not share: the tag, stats, and CSV tickets, which your spec's Out of Scope hands to the neighbouring backlog. If your decomposition reproduces the Seed's six exactly, that is fine; if it finds a better cut, that is better — the rubric grades the four slice rules, not conformity.

Hands-on checklist

Self-check

1. The Seed backlog has 15 tickets and its widest wave is 4. What does the 4 tell you that the 15 does not?

C. Width is parallelism. Only one ticket (#1) has no blockers (B is false); the wave of four is reached after waves 1 and 2 land. Size (A) and layer count (D) are unrelated to it.

2. Why does seed/SPEC.md single out #14 (stats --by-tag) as the clearest example of why a linear reading misleads?

A. Reading the list in number order, #14 looks ready as soon as #11 lands. The graph shows the storage parent. Five tickets have two parents (B is false), GitHub accepts any edge direction (C), and wave 5 has three tickets (D).

3. The page says the waves were "machine-checked, twice." What did the second check add?

D. The first check validated the spec; the second validated what was actually recorded. Agreement between two sources is evidence; one source checked twice is not. The numbers do not match the T-numbers (C), by design.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

The Seed backlog in four numbers?
15 tickets, 19 edges, 5 waves, max width 4.
What is a wave?
The set of tickets whose blockers have all landed — derived by Kahn's algorithm; each wave can go to concurrent agent sessions.
Width vs depth — what does each bound?
Width bounds parallelism (how many agents at once). Depth bounds the minimum number of sequential rounds.
The five joins (two blockers) by issue number?
#5, #7, #9, #13, #14 — T04, T08, T06, T10, T13 in the spec's numbering.
Why do the Seed's issue numbers not match its T-numbers?
Tickets were filed in dependency order, blockers first, so edges could reference real numbers. Numbers are an artifact of filing order.
Which command reads the whole graph back in one call?
gh issue list --json number,title,blockedBy (gh ≥ 2.94.0), then .blockedBy.nodes[].number in --jq.
Why check the waves from GitHub as well as from the spec?
Two independent sources agreeing is evidence the filing recorded what the spec meant; one source checked twice is not.
Ask your teacher

Ask Claude Code: "Read the Seed backlog's edges with gh issue list --json number,blockedBy and propose one edge to remove that would widen a wave without letting an agent start a ticket it cannot finish." If it cannot find one, ask it to justify #8's dependency on #2 — is stats aggregation really blocked by persistence, or only by #1? That question has a defensible answer either way, and arguing it is the objective. Bring anything still unclear to the weekly meeting.
