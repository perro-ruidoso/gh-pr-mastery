Reading the Graph Back

Recording an edge is half the objective. The other half is reading every edge back, checking the graph is one an agent can actually work, and drawing it where the next reader will look — in the issue itself.

M11 · Work dependencies Bloom: Apply Assessed by: A2 (checker)

Objective: Record work dependencies as GitHub issue dependencies via the gh CLI, distinguish them from sub-issues and say why a sub-issue cannot express a two-parent join, and render the resulting graph as a Mermaid diagram.

Three surfaces, one relation

The same stored edge is readable three ways. Knowing all three means you are never stuck when one of them is missing — an older gh, a script in another language, a colleague who only uses the browser.

1. gh issue view --json

The fields blockedBy, blocking, parent, subIssues, and subIssuesSummary all arrived in 2.94.0. Each relation field is an object with nodes and totalCount — so the --jq path is .blockedBy.nodes[], not .blockedBy[]:

$ gh issue view 2 --json blocking --jq '[.blocking.nodes[].number]' 
[4,3]

Same edge as page 1's blockedBy on #3 and #4, read from the other end. The plain (non-JSON) gh issue view prints the same data as blocked-by: and blocking: header lines, alongside parent: and sub-issues:.

2. The REST API

Four routes, quoted from the reference page:

GET    /repos/{owner}/{repo}/issues/{issue_number}/dependencies/blocked_by
POST   /repos/{owner}/{repo}/issues/{issue_number}/dependencies/blocked_by
DELETE /repos/{owner}/{repo}/issues/{issue_number}/dependencies/blocked_by/{issue_id}
GET    /repos/{owner}/{repo}/issues/{issue_number}/dependencies/blocking
$ gh api repos/perro-ruidoso/flashcards-seed/issues/14/dependencies/blocked_by --jq '.[] | "#\(.number) [\(.state)] \(.title) (id \(.id))"' 
#11 [open] `stats` command  (id 5434030684)
#7 [open] Tag persistence in the deck file  (id 5434030220)
issue_id is the database id, not the number

The POST body's one required parameter is issue_id — "The id of the issue that blocks the current issue" — and it is the database id, the ten-digit integer gh api repos/O/R/issues/N --jq .id returns, not the #14 you see in the UI and not the GraphQL node_id. The sub-issue endpoint's sub_issue_id works the same way. This is the single most common way to get a 422 from these endpoints, and it is why the gh flags — which take numbers and resolve the id for you — are worth the upgrade. When you do go through REST, resolve first:

$ gh api repos/perro-ruidoso/flashcards-<handle>/issues/5 --jq '{number, id, node_id}'
{"id":5440629998,"node_id":"I_kwDOUZEMts8AAAABREls7g","number":5}

3. The web UI

The issue sidebar shows "Blocked by" and "Blocking" lists, and a parent issue shows its sub-issues with a progress bar (that is what subIssuesSummary's percentCompleted feeds). It is the surface the rest of your team will read. It cannot show you the whole graph at once, which is why the last section of this page exists.

What GitHub does not check for you

A dependency graph an agent can work has to be a DAG — no cycles. GitHub does not enforce that. On the throwaway Instance, with #5 (transitively) blocked by #2, this was accepted without complaint:

$ gh issue edit 2 -R perro-ruidoso/flashcards-w2probe --add-blocked-by 5
https://github.com/perro-ruidoso/flashcards-w2probe/issues/2
$ gh issue view 2 -R perro-ruidoso/flashcards-w2probe --json blockedBy --jq '[.blockedBy.nodes[].number]'
[5]

#2 is now blocked by #5, which is blocked by #3 and #4, which are blocked by #2. Nothing in the backlog can ever start. The only relation GitHub refused was the degenerate one:

$ gh issue edit 5 -R perro-ruidoso/flashcards-w2probe --add-blocked-by 5
GraphQL: … Validation failed: Target issue cannot be the same as the source issue (addBlockedBy)

So the check is yours. The course script from M10 runs Kahn's algorithm, which cannot finish on a cycle, and says so:

$ python seed/tools/waves_from_github.py --repo perro-ruidoso/flashcards-w2probe
cycle among [2, 3, 4, 5]

$ gh issue edit 2 -R perro-ruidoso/flashcards-w2probe --remove-blocked-by 5
$ python seed/tools/waves_from_github.py --repo perro-ruidoso/flashcards-w2probe
4 issues, 4 blocking edges, 1 joins (2+ blockers): #5
wave 1  #2
wave 2  #3  #4
wave 3  #5
3 waves, max parallel width 2
Always pass -R when the repo is not your working directory

The first attempt to remove that edge was run from the course repo's directory without -R, and gh resolved 2 and 5 against that repository — where #5 is a pull request — and failed with "Could not resolve to an Issue with the number of 5." Harmless there; in a repo where both numbers were issues it would have edited the wrong graph without a word. The transcripts above carry -R for that reason.

Drawing it where the next reader looks

GitHub renders Mermaid in issue bodies natively: "To create a Mermaid diagram, add Mermaid syntax inside a fenced code block with the mermaid language identifier," and it works "in GitHub Issues, GitHub Discussions, pull requests, wikis, and Markdown files." The script prints the graph in that syntax:

$ python seed/tools/waves_from_github.py --repo perro-ruidoso/flashcards-<handle> --mermaid 
graph LR
  I2["#2 Add review state to Card: repetitions, ease factor, interval, due date"]
  I3["#3 Persist review state in the deck file"]
  I4["#4 SM-2 scheduler: next interval and ease update"]
  I5["#5 review command: one card, prompt, grade, schedule"]
  I2 --> I3
  I2 --> I4
  I4 --> I5
  I3 --> I5

Paste that into the spec issue's body, under a ## Dependency graph heading, inside a ```mermaid fence — the spec is the parent of every ticket, so it is where someone looking for the shape of the work will look. Rendered, it is the same picture as this:

graph LR
  I2["#2 review state on Card"]
  I3["#3 persist review state"]
  I4["#4 SM-2 scheduler"]
  I5["#5 review command"]
  I2 --> I3
  I2 --> I4
  I4 --> I5
  I3 --> I5
The throwaway Instance's four tickets, read back from GitHub after the cycle was removed. One root, one join at #5, width 2.

Note that the script skips issues that have sub-issues — the spec itself — so the parent does not appear as a spurious wave-1 node with no blockers. Pass --include-parents if you want it, or --label ready-for-agent to narrow the set another way.

Hands-on checklist

check_a2.py runs the same Kahn pass over your Instance's blockedBy data (no cycle, ≥ 1 join) and looks for a mermaid fence in the spec issue's body.

Self-check

1. gh api -X POST …/issues/9/dependencies/blocked_by -F issue_id=6 returns 422. The most likely cause?

B. "issue_id: The id of the issue that blocks the current issue" — the ten-digit database id from gh api repos/O/R/issues/6 --jq .id. Closed issues can block (A), no extra scope is needed (C), and the blocked-by route is exactly the one to POST to (D).

2. You record #2 as blocked by #5 while #5 is already (transitively) blocked by #2. What happens?

D. Verified on 2026-09-13: the edge was accepted, and waves_from_github.py reported "cycle among [2, 3, 4, 5]." The only relation GitHub refused was an issue blocking itself.

3. Where should the Mermaid graph of a decomposition live, and why?

C. The spec is where someone looking for the shape of the work arrives, via any ticket's parent. Per ticket (A) is fifteen copies to keep in sync; the README (B) outlives the decomposition; and Mermaid renders in issues (D is false).

4. Why does waves_from_github.py skip issues that have sub-issues by default?

A. On the throwaway Instance the spec (#1) appeared in wave 1 beside the real root until the script learned to skip parents. The other options invent API and algorithm limits that do not exist.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

The --jq path for blockers in gh issue view --json blockedBy?
.blockedBy.nodes[].number — the field is an object with nodes and totalCount.
The four REST routes for dependencies?
GET/POST …/dependencies/blocked_by, DELETE …/dependencies/blocked_by/{issue_id}, GET …/dependencies/blocking.
Which id does the REST POST body want?
The database id (gh api …/issues/N --jq .id, ten digits) — not the number, not the node_id.
Does GitHub reject a dependency cycle?
No (verified 2026-09-13). It rejects only an issue blocking itself. Cycle detection is your job — waves_from_github.py.
Where does Mermaid render on GitHub?
"GitHub Issues, GitHub Discussions, pull requests, wikis, and Markdown files" — a fenced block with the mermaid language identifier.
Where should the decomposition's graph be pasted, and why?
The spec issue's body — every ticket's parent points there.
Why pass -R to gh issue edit?
Without it, numbers resolve against the working directory's repo — possibly editing the wrong graph without a word.
Ask your teacher

Ask Claude Code to "write a one-line gh api --paginate pipeline that prints every blocked-by edge in this repository as blocker → blocked, without using the 2.94 --json fields." It will need the REST route and one call per issue; compare its result with waves_from_github.py --mermaid. If they differ, one of them is wrong, and finding out which is the exercise. Bring anything still unclear to the weekly meeting.
