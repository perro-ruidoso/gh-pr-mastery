Two Features, Two Shapes

GitHub has two ways to relate one issue to another, and they are not interchangeable. A sub-issue is a hierarchy: one parent. A dependency is a graph: any number of blockers. The Seed backlog has five tickets that only one of them can express.

M11 · Work dependencies Bloom: Apply Assessed by: A2 (checker)

Objective: Record work dependencies as GitHub issue dependencies via the gh CLI, distinguish them from sub-issues and say why a sub-issue cannot express a two-parent join, and render the resulting graph as a Mermaid diagram.

The two features, in GitHub's words

Sub-issues — a hierarchy

"You can add sub-issues to an issue to break down larger pieces of work into tasks." "Your sub-issues can themselves contain sub-issues, allowing you to create full hierarchies of issues that visualize entire projects or pieces of work and show the relationships between your issues."

Limits: "up to 100 sub-issues per parent issue and … up to eight levels of nested sub-issues." An issue has at most one parent.

Good for: decomposition. The spec is the parent; its tickets are the children.

Issue dependencies — a graph

"Issue dependencies let you define issues that are blocked by, or blocking, other work." Blocked by: "your issue depends on another issue being completed." Blocking: "your issue is preventing another issue from being completed."

An issue may be blocked by many issues and block many.

Good for: sequencing. This is where a Work Dependency lives.

CONTEXT.md gives each its own term — Sub-Issue and Issue Dependency — precisely because they were once conflated in this course's own documents, and the conflation was caught by trying to file the Seed backlog. The /to-tickets skill's publish step still says "native blocking / sub-issue relationship" in one breath. After this page you will know which half of that sentence applies to which relation.

The gh flags

Since gh 2.94.0 both features are first-class on gh issue create and gh issue edit. Every relation for a new ticket can be set in the command that files it:

$ gh issue create --title "Persist review state in the deck file" --body-file t02.md \
    --label ready-for-agent --label layer:storage --type Task \
    --parent 1 \
    --blocked-by 2
https://github.com/perro-ruidoso/flashcards-<handle>/issues/3

$ gh issue create --title "review command: one card, prompt, grade, schedule" --body-file t04.md \
    --label ready-for-agent --label layer:cli --type Task \
    --parent 1 \
    --blocked-by 3,4
https://github.com/perro-ruidoso/flashcards-<handle>/issues/5

--parent 1 makes the ticket a sub-issue of the spec (#1). --blocked-by 3,4 records two dependency edges. Both are visible in one view:

$ gh issue view 5 --json number,title,parent,blockedBy --jq '{number, title, parent: .parent.number, blockedBy: [.blockedBy.nodes[].number]}' 
{"blockedBy":[4,3],"number":5,"parent":1,"title":"review command: one card, prompt, grade, schedule"}

For existing issues the edit flags are symmetrical: --add-blocked-by / --remove-blocked-by, --add-blocking / --remove-blocking, --parent / --remove-parent, --add-sub-issue / --remove-sub-issue. Note that --blocked-by and --add-blocking are the same edge seen from either end: "#5 is blocked by #3" and "#3 is blocking #5" are one fact.

Before 2.94.0 this was gh api only

The Seed backlog's 19 edges were filed on 2026-09-12 with gh 2.92.0, which had no dependency flags, through the REST endpoint POST /repos/O/R/issues/N/dependencies/blocked_by with a payload of {"issue_id": <database id>}. Page 2 still teaches that route: it is what the flags call underneath, it is what you use from any language, and its error messages are more honest than the CLI's — as the experiment below shows.

The experiment: can a sub-issue have two parents?

Ticket #5 (the review command) is blocked by both #3 (persistence) and #4 (scheduler). Suppose you tried to express that with sub-issues instead — make #5 a child of #3, then also a child of #4. Run on a throwaway Instance, 2026-09-13:

$ gh issue edit 3 --add-sub-issue 5
https://github.com/perro-ruidoso/flashcards-w2probe/issues/3
$ gh issue view 5 --json parent --jq .parent.number
3

$ gh issue edit 4 --add-sub-issue 5
https://github.com/perro-ruidoso/flashcards-w2probe/issues/4
$ gh issue view 5 --json parent --jq .parent.number
4
$ gh issue view 3 --json subIssues --jq '[.subIssues.nodes[].number]'
[]
$ gh issue view 4 --json subIssues --jq '[.subIssues.nodes[].number]'
[5]

Both commands "succeeded." But the second one did not add a parent — it moved the only parent from #3 to #4, and #3's sub-issue list is now empty. The CLI silently replaced the relation. The REST API, asked to do the same thing without permission to replace, says so out loud:

$ gh api -X POST repos/perro-ruidoso/flashcards-w2probe/issues/3/sub_issues -F sub_issue_id=5440629998
{"message":"An error occurred while adding the sub-issue to the parent issue. Sub issue may only have one parent",
 "documentation_url":"https://docs.github.com/rest/issues/sub-issues#add-sub-issue","status":"422"}

"Sub issue may only have one parent." That sentence is the whole objective. The REST endpoint documents an optional replace_parent flag — "when true, instructs the operation to replace the sub-issues current parent issue" — and gh's source hard-codes the GraphQL equivalent, replaceParent: true, for --add-sub-issue (api/queries_issue.go in cli/cli, read 2026-09-13), which is why the CLI moved the parent instead of failing. Either way, at no point did #5 have two parents, because the data model has no place to put a second one.

What this means for a backlog

Five of the Seed's fifteen tickets have two blockers (#5, #7, #9, #13, #14). A backlog that recorded its "dependencies" as sub-issues would have to drop one blocker from each of those five, and an agent working the frontier would start each of them one ticket too early. The failure is silent: nothing errors, the graph is just wrong. So the rule is mechanical — decomposition is --parent; sequencing is --blocked-by — and the course convention uses both at once: every ticket is a sub-issue of its spec and is blocked by its predecessors.

Restoring the hierarchy

After the experiment, #5's parent was put back where it belongs:

$ gh issue edit 5 --parent 1
$ gh issue view 1 --json subIssues --jq '[.subIssues.nodes[].number]'
[2,3,4,5]

The spec has its four children again, and the blockedBy edges were never touched — the two relations are stored separately, which is the other half of "two features."

Hands-on checklist

check_a2.py verifies every ticket has the spec as its parent, at least six blockedBy edges exist across the tickets, at least one ticket has two blockers, and the graph has no cycle.

Self-check

1. Ticket #5 is blocked by #3 and #4. Why can sub-issues not record this?

C. The experiment showed it: --add-sub-issue from a second parent moved the relation, and the REST API said "Sub issue may only have one parent." Depth (A), types (B), and state (D) are not the constraint; cardinality is.

2. Which pair of flags does the course convention use on every ticket, and for what?

A. Decomposition is a hierarchy (one spec, many tickets), so --parent; sequencing is a graph (a ticket may need several predecessors), so --blocked-by. B inverts them, C misuses both, and D leaves the edges as prose that no query can read.

3. gh issue edit 4 --add-sub-issue 5 printed a URL and exited 0, yet #5 did not gain a second parent. What is the lesson?

D. The CLI replaced the parent, which is what the REST replace_parent option does. Neither a bug (A) nor a lag (B) nor a no-op (C) — the state changed, just not into a shape that exists. M06's discipline again: observe, then infer.

4. "#3 is blocking #5" and "#5 is blocked by #3" — how many facts is that?

B. After --blocked-by 3 on #5, gh issue view 3 --json blocking lists #5 with no further command. The REST API exposes both directions (dependencies/blocked_by and dependencies/blocking) of the same stored relation.

Sub-issue vs issue dependency — the shape of each?
Sub-issue: a hierarchy, at most one parent, up to eight levels, 100 children. Dependency: a graph, any number of blockers and blocked.
What each is for, in the course convention?
Sub-issue = decomposition (spec → tickets). Dependency = sequencing (ticket → the tickets it needs first).
Why can a sub-issue not express a two-parent join?
"Sub issue may only have one parent" (REST 422). A second parent replaces the first; there is nowhere to store two.
The two gh issue create flags a course ticket always carries for relations?
--parent <spec> and --blocked-by a,b.
What did gh issue edit 4 --add-sub-issue 5 do to #5, which already had parent #3?
Moved its parent to #4 and exited 0 — gh sends replaceParent: true. The REST API without replace_parent refuses with a 422 instead.
Which Seed tickets would lose a blocker if edges were stored as sub-issues?
The five joins: #5, #7, #9, #13, #14. Each would silently drop one of its two blockers.
"A is blocking B" and "B is blocked by A" — how many stored facts?
One. Either flag records it; both directions are readable (blocking, blockedBy).
Which gh version introduced these flags, and what did you use before?
2.94.0 (2026-06-10). Before: gh api against the REST dependency and sub-issue endpoints.
