Criteria That Can Fail

An acceptance criterion is a sentence that a wrong implementation makes false. If you cannot describe the wrong implementation, you have not written a criterion — you have written a wish.

M07 · Issues Bloom: Create Assessed by: A2 (rubric)

Objective: Write an issue body a fresh agent session can execute without asking a question: context, acceptance criteria, and explicit out-of-scope.

The falsifiability test

For each line under Acceptance criteria, ask: what would an implementation look like that makes this line false? If the answer is specific — "one that returns 2 for round(2.5)", "one that raises on an empty deck" — the criterion is doing its job. If the answer is "a bad one", rewrite it.

Here are four criteria from the Seed Repo's backlog, each paired with the wrong implementation it rules out. The right-hand column is the whole reason the left-hand column is phrased the way it is.

Criterion (from the backlog)The wrong implementation it catches
"Intervals follow I(1)=1, I(2)=6, I(n)=I(n-1)*EF, rounded half-up with a floor of 1 day; bare round() is wrong and docs/adr/0001 says why" (#3)Python's round(), which is banker's rounding: round(2.5) == 2. Off by one day, only on exact halves — the kind of bug tests miss unless one is written for it.
"today is obtained once, in cli/, and passed down — no layer below reads the clock" (#5)A date.today() call inside the scheduler. The command works; the tests become time-dependent and flaky.
"a deck file written before this change still loads - missing fields fall back to the T01 defaults" (#2)A loader that KeyErrors on any deck saved before review state existed. Every existing user's data becomes unreadable.
"A card with two tags is counted under both, and the totals row says so rather than silently exceeding the deck size" (#14)A totals row that sums per-tag counts — 12 cards reported for a 10-card deck, with no explanation.
Name the test, not just the behaviour

Every Seed Repo ticket ends its criteria with a line like "tests/storage/test_json_store.py covers the round trip, the old-file fallback, and a malformed date." That line does two things. It tells the agent where "done" is checked, so the diff arrives with the test in it rather than with a promise to add one. And it gives the Week 4 reviewer a concrete thing to look for — if the malformed-date case is missing from the test, that is a finding, not a matter of taste. /to-tickets advises against file paths because "they go stale fast"; a test path is the exception this course makes, because the test is part of the deliverable.

Rewriting weak criteria

The same three moves fix most weak criteria: name the input, name the observable output, and name where it is checked.

Before

"The review command works end to end."

"Handles invalid input."

"Well tested."

After

"flashcards review --deck <path> shows one card's front, waits, reveals the back, and reads a grade of 0–5."

"An invalid grade re-prompts rather than crashing."

"tests/cli/test_main.py drives the command with scripted stdin and a fixed today, and asserts the saved deck."

The right-hand column is ticket #5, verbatim. Notice that "re-prompts rather than crashing" chooses one of two reasonable behaviours (the other being "exits with an error"). An agent left to decide would pick one; the reviewer would then argue about it in the PR. Deciding in the ticket moves the argument to where it is cheap.

Out of scope is a fence, not a disclaimer

A weak Out-of-scope section says "everything else." A useful one names the two or three things an implementer would plausibly do while working this ticket, and assigns each to where it belongs. From #5 again:

"Choosing which card — T05 does due-filtering, and until then the command takes the first card. Limits (T06) and tags (T10)."

That sentence also makes a decision ("takes the first card") so the ticket is completable before its neighbours exist. Out of scope is where you say what the stub behaviour is, not merely what is deferred.

Context is state, not story

Two sentences: what is true now, and why it must change. Ticket #14 adds a third that earns its place — "note that its two parents sit six tickets apart, in different layers" — because that fact changes how the agent should read the Blocked-by list. A Context paragraph that recounts the discussion ("we considered three designs…") is conversation residue; if a design decision matters, it belongs in an ADR the ticket cites, as #3 cites docs/adr/0001.

Hands-on checklist

This is the A2 rubric's M07 item, done once by hand before /to-tickets does it for you in M10 — so you can judge the skill's output.

Self-check

1. Which of these is an acceptance criterion in the sense this page means?

B. It names an input and an observable output: 5 × 2.5 = 12.5, which rounds half-up to 13. An implementation using bare round() returns 12 and makes the sentence false — that is the planted bug from seed/SPEC.md §7. A, C, and D cannot be false: "cleanly", "correctly", "thoroughly" have no failing case.

2. Why does this course name a test file path in acceptance criteria when /to-tickets warns that file paths "go stale fast"?

D. A named test tells the agent to ship the test in the diff and tells the Week 4 reviewer where to look for the missing case. It is a deliberate exception to the skill's rule, made because the test is not implementation detail — it is the evidence of completion.

3. Ticket #5 says "until then the command takes the first card." What job is that sentence doing?

A. It sits under Out of scope and makes the fence usable: the implementer knows what to do at the boundary without doing the neighbour's work. It is not a dependency (B) — #5 is blocked by #2 and #3, not by T05 — and it is not a bug (D); it is a decided interim behaviour.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

The falsifiability test for a criterion?
Can you describe the wrong implementation that makes it false? If not, it is a wish, not a criterion.
Three moves that fix most weak criteria?
Name the input, name the observable output, name where it is checked (the test).
Why is "bare round() is wrong" written into ticket #3?
Python rounds half to even — round(2.5) == 2. The criterion rules out the one wrong implementation a naive test would miss.
What does a good Out-of-scope section contain besides deferrals?
The stub behaviour at the boundary — e.g. "until then the command takes the first card" — so the ticket is completable alone.
Where does design reasoning go if not in Context?
In an ADR the ticket cites (ticket #3 cites docs/adr/0001). Context is state and reason, two sentences.
"An invalid grade re-prompts rather than crashing" — why decide this in the ticket?
Two behaviours are reasonable; deciding in the ticket moves the argument from the PR (expensive) to the spec (cheap).
Ask your teacher

Give Claude Code your hand-written T05 ticket and ask it to "implement this wrongly in three different ways that would each pass a lazy test, and say which acceptance criterion catches each one." If a wrong implementation passes every criterion, the ticket needs another line. Bring anything still unclear to the weekly meeting.
