The Ticket as a Contract

An issue body is the only thing a fresh agent session knows. If the session has to ask you a question, the issue failed — and the failure is yours, not the agent's.

M07 · Issues Bloom: Create Assessed by: A2 (rubric)

Objective: Write an issue body a fresh agent session can execute without asking a question: context, acceptance criteria, and explicit out-of-scope.

What "fresh session" changes

GitHub's own description of issues is deliberately loose: they "are quick to create, flexible, and can be used in many ways," and "can track bug reports, new features and ideas, and anything else you need to write down." That flexibility is fine for humans, who fill gaps by asking. It is a trap for agentic work, because the reader of your issue will be a Claude Code session started with no memory of the conversation that produced it. The /to-tickets skill you meet in M10 says why in one line: each ticket "is sized to fit in a single fresh context window," and you "work the frontier one ticket at a time … clearing context between tickets." (The frontier is the set of tickets whose blockers have all landed — the ones a fresh session could pick up right now. M10 page 2 computes it and calls each round of it a wave.)

So the standard for an issue body in this course is not "would a teammate understand this?" It is: could a session that has read only CLAUDE.md, CONTEXT.md, and this issue start work, finish it, and know it has finished — without a follow-up question? That is what the ready-for-agent label from M05 asserts: "fully specified, ready for an AFK agent."

The four sections

Every ticket in this course carries the same four headings. They are not a template for its own sake; each one closes a specific kind of question an agent would otherwise have to ask.

SectionThe question it pre-emptsWhat goes there
Context"Why does this exist, and what is true today?"Two sentences. The current state and the reason it must change. Not the history of the discussion.
Acceptance criteria"How will I know I am done?"A checklist of observable statements, each of which can be false, including the test that must exist. Page 2 is entirely about this section.
Out of scope"Should I also…?"The adjacent work an eager implementer would reach for, named so it is not done here. Usually the neighbouring tickets.
Blocked by"Can I start?"The issues that must land first, and why. Recorded as a real GitHub issue dependency in M11, not only as prose.

A ticket that meets the bar

This is issue #1 of the Seed Repo's backlog — the first of fifteen, and the one every other ticket ultimately depends on. Read it as an agent would: cold.

$ gh issue view 1 -R perro-ruidoso/flashcards-seed --json title,body --jq '.title, "", .body' 
Add review state to Card: repetitions, ease factor, interval, due date

## Context

A Card today knows its prompt and its answer and nothing about when it should next be
seen. Every scheduling ticket in this backlog needs somewhere to put that state, so it
goes on the Card first.

## Acceptance criteria

- [ ] `Card` carries `repetitions: int`, `ease_factor: float`, `interval: int`, and `due: date | None`
- [ ] Defaults for a never-reviewed card are `0`, `2.5`, `0`, `None` - the starting ease
      factor is fixed in `docs/adr/0001`
- [ ] `Card` stays frozen and stays free of I/O
- [ ] `tests/domain/test_models.py` pins the defaults, and pins that the new fields are
      optional so existing call sites still construct a Card with three arguments

## Out of scope

Persistence (T02), any arithmetic that changes these fields (T03), and any command that
displays them.

## Blocked by

Nothing. This ticket can start today.

_Layer: `domain`_

Why it works

  • Context names the current state ("knows its prompt and its answer and nothing about when it should next be seen") and the reason ("every scheduling ticket … needs somewhere to put that state"). An agent can verify the first half by reading models.py.
  • Every criterion can fail. Field names and types are exact. The defaults are numbers, and where a number comes from a decision, the decision is cited (docs/adr/0001) rather than restated — so an agent that reads the ADR gets the reasoning, and an agent that does not still gets the value.
  • The test is a criterion, not an afterthought. Its path is given. "Pins that the new fields are optional so existing call sites still construct a Card with three arguments" is a backwards-compatibility requirement expressed as something a test can assert.
  • Out of scope names the neighbours. Persistence, arithmetic, display — the three things an implementer would naturally reach for next — are each assigned to a specific other ticket. The fence is drawn where the temptation is.
  • Blocked by says "nothing" out loud. Silence would be ambiguous. "Can start today" is a statement an agent can act on.
Constraints are criteria too

"Card stays frozen and stays free of I/O" adds no behaviour. It is there because it is the kind of thing an agent will quietly violate while making the other criteria pass — an unfrozen dataclass is easier to mutate, a date import is one step from reading the clock. The Seed Repo's CLAUDE.md states the layer rules once; a ticket that touches a boundary repeats the rule that applies. Redundancy at the boundary is cheap; a review that catches the violation in Week 4 is not.

Four ways issues fail an agent

FailureWhat it looks likeThe question it forces
Intent without state"Add spaced repetition.""Which algorithm? Where does the state live? What exists already?"
Criteria that cannot fail"Works correctly." "Is well tested." "Handles edge cases.""Which cases? Tested how? Correct according to what?"
Unbounded scopeNo out-of-scope section on a ticket whose obvious next steps are three other tickets.None — that is the problem. The agent does not ask; it does the neighbouring work too, and the diff becomes unreviewable (Week 3, M14).
Conversation residue"As we discussed, go with the second option.""Which discussion? Which option?"

The last one is the most common when a ticket is written at the end of a long Claude Code session, and it is exactly why /to-spec (M09) exists: to synthesise the conversation into a document that stands without it.

Hands-on checklist

The exhibit is the Seed Repo. Your own Instance starts with no issues — a template copies files, not issues (verified on a fresh Instance, 2026-09-13) — so the tickets you write this week are the first ones it has.

Self-check

1. Why does this course hold issue bodies to a stricter standard than most teams do?

C. /to-tickets sizes each ticket "to fit in a single fresh context window" and clears context between tickets — so the issue is the whole briefing. GitHub enforces nothing about body structure (A), the rubric grades whether an agent could execute it rather than counting headings (B), and the template ships no issue template at all (D).

2. Which of these belongs under Out of scope on the Seed Repo's ticket #1 (review state on Card)?

B. Out of scope names the adjacent work an implementer would reach for — and persistence is T02, the very next ticket. The default (A) and the frozen constraint (C) are acceptance criteria on this ticket, and the test path (D) is a criterion too: the ticket names tests/domain/test_models.py so "done" is checkable.

3. A ticket's Blocked-by section is empty. What should an agent conclude?

D. Silence is ambiguous, which is why the exhibit says "Nothing. This ticket can start today" in words. Any of A, B, or C might be true; the point of the section is that the agent should not have to guess which.

4. "As we discussed, use the second approach." What is wrong with this in an issue body?

A. Conversation residue. The fix is not to link the transcript (D) — a fresh session should not need to replay a discussion to act — but to state the decision itself. /to-spec exists to do that synthesis.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

The one-sentence test for an agent-ready issue body?
Could a session that has read only CLAUDE.md, CONTEXT.md, and this issue start, finish, and know it has finished — without asking a question?
The four sections of a course ticket, in order?
Context · Acceptance criteria · Out of scope · Blocked by.
What question does Out of scope pre-empt?
"Should I also…?" — it names the adjacent work an implementer would reach for, usually the neighbouring tickets.
Why does /to-tickets justify the "fresh session" standard?
Each ticket "is sized to fit in a single fresh context window"; you work the frontier "clearing context between tickets."
"Works correctly", "well tested", "handles edge cases" — what is the shared defect?
None of them can be false. A criterion that cannot fail cannot tell an agent it is done.
Why does ticket #1 cite docs/adr/0001 for the ease factor instead of explaining it?
The value (2.5) is stated so the agent has it; the reasoning lives once, in the ADR, so it cannot drift between tickets.
How many issues does a fresh Instance start with, and why?
Zero. A template copies files, not issues. The 15-ticket backlog lives on the Seed Repo as an exhibit.
Ask your teacher

Paste one of the Seed Repo's tickets into Claude Code and ask: "You are a fresh session with only CLAUDE.md, CONTEXT.md, and this issue. List every question you would need to ask before starting, and every point where you would have to guess." If the list is empty, ask it to try to break each acceptance criterion with a wrong implementation. Bring anything still unclear to the weekly meeting.
