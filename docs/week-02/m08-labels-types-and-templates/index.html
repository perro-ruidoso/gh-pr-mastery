Labels and Issue Types

A backlog is only useful if the next piece of ready work can be found with one query. Labels, issue types, and templates are three different tools for making that query possible — and they answer three different questions.

M08 · Issues Bloom: Apply Assessed by: A2 (checker)

Objective: Apply labels, issue types, and issue templates so a backlog is filterable and ready work is findable.

Labels

GitHub's definition is one sentence: "You can classify issues, pull requests, and discussions by creating, editing, applying, and deleting labels." Labels are per-repository, free-form, and unlimited in number per issue — which is both their strength and the reason label sets rot. Permissions matter for the maintainer seat later: "Anyone with write access to a repository can create a label," and "Anyone with triage access to a repository can apply and dismiss labels."

You saw in M06 that a well-run repository uses labels on several independent axes — bug is a kind, priority-3 a rank, gh-pr an area. Your Instance now has two families, and they are on different axes too:

AxisLabelsRuleWho applies them
State (triage)needs-triage needs-info ready-for-agent ready-for-human wontfixAt most one at a time — an issue is in one state/triage, /to-spec, /to-tickets, and you
Area (layer)layer:domain layer:storage layer:cliOne or more — a tracer bullet crosses layersYou, when filing

The five state labels came from M05 and A1. The three layer labels are new this week, and the layer: prefix is doing real work: it makes the axis visible in a label list without a colour legend, and it keeps gh label list sortable. Create them with a colour and a description — the description is what a new collaborator (or an agent reading gh label list --json) sees:

$ gh label create layer:domain  --color 1d76db --description "Touches src/flashcards/domain"
$ gh label create layer:storage --color 0e8a16 --description "Touches src/flashcards/storage"
$ gh label create layer:cli     --color fbca04 --description "Touches src/flashcards/cli"
A label must exist before it can be applied

This is the first thing that goes wrong on a fresh Instance. Run on a repository created moments earlier, with only GitHub's ten defaults present:

$ gh issue create --title "Spec: the review loop" --body-file spec.md --label ready-for-agent --type Feature
could not add label: 'ready-for-agent' not found

The issue is not created. gh resolves labels before it creates anything, so a missing label aborts the whole command rather than filing an unlabelled issue — which is the behaviour you want, and the reason A1 had you create the five triage labels before any skill tried to use them.

Issue types

Issue types are newer and stricter than labels. Per GitHub: "You can use issue types to classify and manage different types of issues across your organization." Three things follow from across your organization:

  • They are defined once, at the org (Organization settings → Planning → Issue types), not per repository — so every Instance in perro-ruidoso sees the same set. "The default types are task, bug, and feature," and "You can create up to 25 issue types."
  • An issue has one type or none. That is the whole difference from a label: a type is a single-valued classification, so it is the right home for "what kind of thing is this" and the wrong home for anything an issue can be several of.
  • They are queryable everywhere labels are — "You can filter and search by issue type" — including in gh issue list --type.

The course org carries the three defaults, read back from the API:

$ gh api orgs/perro-ruidoso/issue-types --jq '.[] | "\(.name)\t\(.description)"' 
Task	A specific piece of work
Bug	An unexpected problem or behavior
Feature	A request, idea, or new functionality

The convention this course uses is small: a spec issue is a Feature; every ticket is a Task; anything /qa files in Week 4 is a Bug. Set it at creation with --type, or afterwards with gh issue edit N --type Task (and --remove-type to clear it).

This needs gh 2.94.0 or later

--type, and the sub-issue and dependency flags M11 depends on, arrived in GitHub CLI 2.94.0 (2026-06-10) — "Issue types, sub-issues, and relationships in gh issue." Every transcript on the Week 2 pages was captured with 2.100.0. Check yours with gh --version; on 2.92.0, which the course machine had at the start of Week 2, every one of these flags is "unknown flag". Upgrade before the meeting.

Filtering: the query that finds ready work

The point of all this metadata is one command. On a throwaway Instance with a spec and four tickets filed (the same repository the transcripts on the next three pages come from):

$ gh issue list --label ready-for-agent --label layer:domain --json number,title 
[{"number":4,"title":"SM-2 scheduler: next interval and ease update"},
 {"number":2,"title":"Add review state to Card: repetitions, ease factor, interval, due date"}]

Two --label flags are an AND: both labels must be present. GitHub's search syntax says the same thing two ways — label:"bug" label:"wip" is AND, and label:"bug","wip" (one qualifier, comma-separated) is OR.

$ gh issue list --type Task --json number,title,issueType --jq '.[] | "#\(.number)\t\(.issueType.name)\t\(.title)"' 
#5	Task	review command: one card, prompt, grade, schedule
#4	Task	SM-2 scheduler: next interval and ease update
#3	Task	Persist review state in the deck file
#2	Task	Add review state to Card: repetitions, ease factor, interval, due date

When the flags run out, --search takes any search qualifier. Three worth memorising: no:label finds issues nobody has classified, -label: excludes, and type: filters by issue type inside a search:

$ gh issue list --search "is:open label:ready-for-agent -label:layer:cli" --json number --jq '[.[].number]' 
[4,3,2,1]
$ gh issue list --search "type:Feature" --json number,title 
[{"number":1,"title":"Spec: the review loop"}]
$ gh issue list --search "no:label" --json number,title 
[]

That last empty list is the goal state for a backlog: nothing unclassified. It is also what check_a2.py looks for.

Look at gh issue view 14 -R perro-ruidoso/flashcards-seed: labels: empty, issue-type: empty. Hands-on checklist

check_a2.py verifies the three layer labels exist, every open issue has at least one label and a type, and no open issue matches no:label.

Self-check

1. What is the structural difference between a label and an issue type?

C. Types are single-valued, org-level classifications ("across your organization", up to 25); labels are per-repository, multi-valued, and unlimited. Both are searchable (A is false), the org/repo split is the other way round (B), and applying either needs triage access, not read (D).

2. gh issue create --label ready-for-agent … fails with "could not add label: 'ready-for-agent' not found". What happened?

A. Labels are per-repository, and a fresh Instance has only GitHub's ten defaults. gh resolves labels first and aborts, so no issue is left behind (B is false). Scope (C) and timing (D) are not involved — --label at creation works fine once the label exists.

3. Which query finds open issues that are ready for an agent and touch the storage layer?

D. Repeated --label flags are AND. A is OR — a comma-separated list inside one label: qualifier matches either. B adds --state all, which pulls in closed issues, and C searches the words "layer:storage" as text rather than as a label qualifier.

4. Why does the layer: prefix earn its place in the label names?

B. Labels are free-form text; the prefix is a convention, not a mechanism. It tells a reader (human or agent) that layer:cli and layer:domain are alternatives on one axis, the way priority-3 did in the cli/cli exhibit. GitHub imposes nothing (A), the skills read the label strings you map in triage-labels.md (C), and labels apply to PRs regardless of name (D).

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

Label vs issue type — where is each defined, and how many per issue?
Label: per repository, any number. Type: per organization (up to 25), at most one.
The org's three default issue types?
Task, Bug, Feature. Course convention: spec = Feature, ticket = Task, /qa output = Bug.
Two --label flags on gh issue list — AND or OR?
AND. In search syntax, label:a label:b is AND and label:a,b is OR.
What does gh issue create --label X do when label X does not exist?
Aborts — "could not add label: 'X' not found" — and creates nothing. Create the label first.
Which gh release added --type, --parent, and --blocked-by?
2.94.0 (2026-06-10). On 2.92.0 they are all "unknown flag".
The search qualifier that finds unclassified issues?
no:label — the goal is for it to return an empty list.
Who can apply a label; who can create one?
Apply: triage access. Create, edit, delete: write access.
Your Instance's two label families and their axes?
State: the five triage labels (one at a time). Area: layer:domain|storage|cli (one or more).
