Verify Without Touching

"Connected" is a claim. The evidence is an issue you created with gh appearing in Linear, and a status in Linear changing because of something that happened on GitHub — with your hands off the Linear UI the whole time.

M12 · PM integration Bloom: Apply Assessed by: A2 (checker)

Objective: Connect Linear to the Instance and verify that issues and PRs appear and update without manual touching.

The protocol

Every step below happens on the GitHub side, from the terminal; Linear is only ever looked at. That is what "without manual touching" means, and it is what makes the result evidence rather than a demo.

1. An issue appears

Create a new issue in your Instance the way every ticket this week was created. It must be new — Issues Sync is forward-only — so give it a title you will recognise:

$ gh issue create --title "Sync probe: created from gh on 2026-09-13" \
    --body "Filed from the terminal to verify Issues Sync. Close via gh; do not touch in Linear." \
    --label needs-triage --type Task

Open your Linear team. Within moments an issue with the same title should exist, carrying your team's key (FLASH-n). Linear syncs "title, description, status, assignee, labels, sub-issues, comments," so the body and the needs-triage label should be there too. Note the time and take a capture — a screenshot with the date visible — for the A2 write-up.

2. A status updates from GitHub

Close the issue from the terminal:

$ gh issue close <n> --reason completed

The Linear copy should move to its done state without anyone in Linear doing anything. Capture that too. If it does not move, the sync is one-way in the wrong direction, or the status mapping in Linear's integration settings needs a look — but do not fix it by dragging the card. Fix the configuration, reopen the issue with gh issue reopen, and try again.

3. A comment crosses

$ gh issue comment <n> --body "Comment from gh; should appear in Linear."

Comments are in the synced list. Seeing one cross confirms the sync is live for more than creation events.

4. A PR moves a status (preview of Week 3)

This is the other capability — PR and commit linking — and it needs a branch and a pull request, which are Week 3's subject. Do the smallest possible version now, so the write-up can say both capabilities were seen:

  1. In Linear, look at the synced probe issue and use "Copy git branch name" (Cmd/Ctrl+Shift+.). Reading a name off the UI is not touching the issue.
  2. Reopen the probe issue if you closed it, create the branch locally with that name, make a one-line change (a comment in README.md is enough), push, and open a PR whose title includes the Linear ID — Linear: "Include the Linear issue ID (e.g. ID-123) in the title when creating pull requests."
  3. Watch the Linear issue: "by default, we will move linked issues to 'In Progress' when PRs are open."
  4. Close the PR without merging (gh pr close) — merging is Week 3's work, done properly with a linking keyword. Delete the branch.
Magic words, for later

Linear also reads a PR description for magic words. Closing ones — "close, closes, closed, closing, fix, fixes, fixed, fixing, resolve, resolves, resolved, resolving, complete, completes, completed, completing, implement, implements, implemented, implementing" — move the issue "to the status configured for On PR or commit merge when the PR or commit is merged." Non-closing ones — "ref, refs, references, part of, contributes to, toward, towards" — link without closing. Notice the overlap with GitHub's own closing keywords from M06: one word in a PR body, Closes #12, can close the GitHub issue on merge and move the Linear copy, which is the whole of M34. Not needed this week.

What the checker can and cannot see

check_a2.py runs against GitHub with your gh token. It cannot log in to Linear. So it checks the GitHub side of the protocol — an issue whose title starts with Sync probe, created after the spec, closed with reason completed, with at least one comment — and it looks for the capture file your write-up references. The Linear side is graded from the captures by a human, which is why each capture needs a visible date and the issue's Linear ID in frame.

If the sync cannot be made to work

The course has not yet run this protocol in a live Free workspace (page 1 says so). If, in the meeting, the GitHub Issues section of the integration settings turns out to be unavailable on Free, the objective falls back to capability 1 alone — PR and commit linking, steps 4 above — which is sufficient for M34 and does not depend on Issues Sync. Report what you saw; the page will be corrected with a dated capture.

Hands-on checklist

Self-check

1. Why does the verification protocol create a new issue instead of checking that the spec appeared?

B. "This will only sync issues going forward." Types (A), body length (C), and sub-issues (D) are not the constraint; timing is.

2. The Linear copy did not move when you closed the GitHub issue. What is the right next step?

D. Fixing the symptom by hand (A, C) destroys the evidence the objective asks for — a status that moved because of GitHub. Reconnecting (B) is disproportionate; configuration is the usual cause.

3. What can check_a2.py verify about M12, and what can it not?

A. The checker runs gh with a GitHub token; Linear is a different service with different auth. The Linear side is graded from your dated captures. Whether Linear leaves any trace on the GitHub issue has not been verified, so the checker does not rely on it (C).

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

What "without manual touching" means operationally?
Every action happens on GitHub from the terminal; Linear is only looked at. A status that moved because of a GitHub event is the evidence.
The four steps of the verification protocol?
Create an issue with gh → close it with gh → comment with gh → open a PR with the Linear ID in its title (preview of Week 3).
Linear's default status moves for linked PRs?
"In Progress" when a PR is open, "Done" when it merges.
Two ways a PR gets linked to a Linear issue?
The issue ID in the branch name (use "Copy git branch name") or in the PR title; magic words in the description also link.
Name four closing magic words and two non-closing ones.
Closing: closes, fixes, resolves, implements (and their forms). Non-closing: refs, part of, contributes to, towards.
The Linear copy did not move on gh issue close. First move?
Check sync direction and status mapping in the integration settings — never drag the card.
What must each A2 capture show?
A visible date and the issue's Linear ID in frame — the checker cannot see Linear, so the human grades from these.
Ask your teacher

After the protocol, ask Claude Code: "List every GitHub event I generated in the last hour with gh api repos/O/R/issues/N/timeline, and next to each one say what Linear should have done in response." That is the beginning of M34's discipline — driving status from git activity — and it will tell you whether anything you saw in Linear lacked a GitHub cause. Bring anything still unclear to the weekly meeting.
