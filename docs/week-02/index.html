GitHub Pull Requests for Agentic Coders Week 2

Week 2 — Issues as Units of Agent Work

An issue is the only thing a fresh agent session knows. This week you learn to write one it can execute, decompose a feature into a graph of them, record that graph where GitHub can read it, and put a project-management layer on top that updates itself.

Week 1 gave you a precise model of a pull request and a repository configured for the engineering skills. But your Instance has no issues — a template copies files, not issues — and until it does, there is nothing for an agent to pick up. By the end of this week it will have a spec, six to ten tickets that each cross every layer of the app, real blocking edges between them, a Mermaid picture of the whole thing, and a Linear board that reflects all of it without anyone re-typing anything.

Suggested order

The objectives are in build order, and the later ones consume the earlier ones' output. M07 is the standard everything else is held to. M08 is quick setup — do it before you file anything. M09 and M10 are the two skills that write your backlog; M11 is where the backlog becomes a graph, and its two-parent experiment is the idea of the week. M12 comes last on purpose: Linear only syncs issues created after it is connected, and you want a week of real history first. Do the flashcards again a few days later.

Upgrade gh first

Issue types, sub-issues, and dependencies became gh issue flags in GitHub CLI 2.94.0 (2026-06-10). Every transcript this week was captured with 2.100.0. Run gh --version; on anything older, --type, --parent, and --blocked-by are "unknown flag" and M08 and M11 will not work as written.

Assignment A2

Due before the Week 3 meeting. The full brief is in assignments/a2.md; in short:

  1. Three layer: labels and a Ticket issue template committed to your Instance; every open issue labelled and typed.
  2. One ticket written by hand — due-date filtering — with all four sections.
  3. A spec issue for the review loop published with /to-spec: seven sections, ready-for-agent, type Feature.
  4. Six to ten tickets from /to-tickets, each a sub-issue of the spec, with blocking edges recorded as issue dependencies; no cycle, at least one join; the graph as Mermaid in the spec's body.
  5. Linear connected and the verification protocol run from gh, with dated captures in your write-up.
  6. A short write-up: where your decomposition differs from the Seed's, and what you touched by hand (ideally: nothing).

Items 1, 3, 4 (the counts and the graph), and the GitHub side of 5 are graded by checkers/check_a2.py. Items 2, 4 (the slice quality and the edges' honesty), and 6 are graded by a human against the rubric.
