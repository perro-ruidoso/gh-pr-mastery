From Conversation to Spec

The design conversation you just had with Claude Code is the most valuable and most perishable thing in the session. /to-spec turns it into a document that survives the context being cleared.

M09 · Specification Bloom: Apply Assessed by: A2 (checker)

Objective: Turn a design conversation into a published spec issue with /to-spec, and check the result before filing.

M09 pages 1From Conversation to Spec 2Checking the Spec

What the skill does — and pointedly does not

The skill's own description: "Turn the current conversation into a spec and publish it to the project issue tracker — no interview, just synthesis of what you've already discussed." And the first instruction in its body, in capitals: "Do NOT interview the user — just synthesize what you already know."

That rule tells you when to run it. /to-spec is not a way to start designing; it is what you run at the end of a design conversation, when the decisions have been made in dialogue and are about to be lost. If you run it cold, it will synthesise a thin spec from nothing, because it is forbidden from asking. The skill that interviews you is /grill-me (Week 3's toolbelt, M18); the sequence is grill, then spec.

The process, in the skill's order

  1. Explore the repo "to understand the current state of the codebase, if you haven't already," using "the project's domain glossary vocabulary throughout the spec" and respecting "any ADRs in the area you're touching." This is why M05 had you point the skills at CONTEXT.md and docs/adr/: the spec will say Card, Deck, Grade, and Due in the Seed Repo's sense, and it will not propose freezegun because docs/adr/0001 already decided against it.
  2. Sketch the seams — "the seams at which you're going to test the feature." The skill prefers existing seams, wants "the highest seam possible," and says "the fewer seams across the codebase, the better — the ideal number is one." Then it stops: "Check with the user that these seams match their expectations." This is the one place it does talk to you, and it is a yes/no on a proposal, not an interview.
  3. Write and publish. The spec follows a fixed template (below), is published to the tracker docs/agents/issue-tracker.md names — gh issue create for you — and gets the ready-for-agent triage label: "no need for additional triage."

Why "no file paths" — and the exception

The skill excludes paths and code because "they may end up being outdated very quickly." A spec is read for weeks; a path is true for one commit. The stated exception is a prototype: "if a prototype produced a snippet that encodes a decision more precisely than prose can (state machine, reducer, schema, type shape), inline it … and note briefly that it came from a prototype." Compare M07's rule for tickets, which name a test file on purpose — a ticket is read once, by one session, this week; a spec is not.

What the spec is, in GitHub terms

The published spec is an ordinary issue with a long body, the ready-for-agent label, and — by this course's convention from M08 — the issue type Feature. Its job in the rest of the week is to be the parent: /to-tickets reads it, and the tickets it produces become the spec's sub-issues (M11). So the spec is where GitHub's hierarchy feature earns its keep, one level deep: one Feature, many Tasks.

The skill sets the label but not the type — it predates issue types. Add it yourself after publishing:

$ gh issue edit <spec-number> --type Feature

Hands-on checklist

A2's spec is "the review loop": a learner can grade one card and have it rescheduled and saved — the Seed backlog's T01–T06 territory. check_a2.py verifies an open issue with the seven spec headings exists, labelled ready-for-agent, typed Feature.

Self-check

1. You open a fresh Claude Code session and immediately run /to-spec for a feature you have not discussed. What happens?

C. "Do NOT interview the user — just synthesize what you already know." With nothing discussed, "what you already know" is the repo. The skill does not refuse (B) and does not chain to other skills (D); the sequencing — grill, then spec — is your job.

2. What is the one thing /to-spec checks with you before writing?

A. Step 2 of the process ends with "Check with the user that these seams match their expectations." It is a proposal for a yes/no, and it is the only interaction the skill's process specifies.

3. Why does the spec template exclude file paths while the course's tickets include a test path?

D. The skill's reason is that paths "may end up being outdated very quickly." A ticket's lifetime is one fresh session, and its test path is part of the deliverable, so the trade-off comes out differently. The skill does explore the repo (B is false), and neither GitHub nor the checker is the reason (A, C).

Flashcards

/to-spec in its own five words?
"No interview, just synthesis" — of the conversation you have already had.
When in a session should you run it?
At the end of a design conversation, before context is cleared. Grill first (/grill-me), spec second.
The skill's three steps?
Explore the repo (glossary, ADRs) → sketch the seams and check them with you → write the template and publish with ready-for-agent.
Seven sections of the spec template?
Problem Statement · Solution · User Stories · Implementation Decisions · Testing Decisions · Out of Scope · Further Notes.
The ideal number of seams, per the skill?
One. "The fewer seams across the codebase, the better." Prefer existing seams; place new ones as high as possible.
Why no file paths or code in a spec — and the exception?
They "may end up being outdated very quickly." Exception: a prototype snippet that encodes a decision (state machine, schema, type shape), marked as such.
What the spec becomes in GitHub terms this week?
The parent issue (type Feature); /to-tickets makes its tickets sub-issues of it.
Ask your teacher

Before running the skill, ask Claude Code: "If you ran /to-spec right now, which decisions would you be forced to invent because we have not discussed them?" Discuss those, then run it. Afterwards, ask it to point to the sentence in the conversation that each Implementation Decision came from — any decision with no source is a hallucinated one. Bring anything still unclear to the weekly meeting.
