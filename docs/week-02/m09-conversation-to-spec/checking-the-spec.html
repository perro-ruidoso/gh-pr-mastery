Checking the Spec

The skill publishes as its last step, so "check before filing" really means two things: read the proposal before you say yes to the seams, and audit the issue before anything downstream reads it. A spec with an invented decision in it produces ten tickets with the same invented decision.

M09 · Specification Bloom: Apply Assessed by: A2 (checker)

Objective: Turn a design conversation into a published spec issue with /to-spec, and check the result before filing.

The one gate the skill gives you

Step 2 of the process — "Check with the user that these seams match their expectations" — is the only moment the skill pauses. Everything after your answer runs to publication. So treat that pause as the review it is. Three questions, in order of how often they catch something:

  1. Is the seam one I can name in the Seed Repo's vocabulary? For the review loop, the highest existing seam is the CLI command with scripted stdin and a fixed today — the pattern ticket #5's criteria already describe. If the proposal is "test the scheduler function directly," that is a lower seam, and the skill's own rule says it should have preferred a higher existing one.
  2. Does the seam count exceed one? "The ideal number is one." Two seams is not wrong, but ask which of them could be dropped.
  3. Does it respect the ADR? Any seam that freezes time by patching the clock contradicts docs/adr/0001's decision that today is passed down. The skill is told to respect ADRs; verify that it did.

Auditing the published issue

Once it is filed, read it back from GitHub rather than from the chat — the chat shows you what the agent intended to publish, and the issue shows what it did:

$ gh issue list --label ready-for-agent --search "type:Feature" --json number,title
$ gh issue view <n> --json title,body,labels,issueType --jq '.title, (.labels|map(.name)), .issueType.name, "", .body'

The spec is upstream of everything

M10 decomposes this issue into six to ten tickets, M11 records their edges, and Weeks 3–4 implement and review them. An error here is not one error; it is one error per ticket. Ten minutes reading the published body is the highest-leverage ten minutes of the week — which is why this is a page and not a checklist item.

Editing after publication

The spec is an issue; edit it like one. Small fixes go straight in with gh issue edit N --body-file corrected.md. Larger ones are cheaper in the chat that produced it — "the storage decision is wrong, we use the JSON deck file; regenerate the Implementation Decisions section" — followed by a --body-file edit. Do not re-run /to-spec; it would publish a second issue, and you would have two specs with two numbers, one of which /to-tickets is going to be handed.

Hands-on checklist

check_a2.py reads the spec back with the same gh issue view --json call shown above and checks the seven headings, the label, and the type. The content audit is yours.

Self-check

1. The published spec says cards will be persisted in SQLite. You never discussed storage. What is the right response?

B. An Implementation Decision with no source in the conversation is a hallucination, and the Seed Repo's existing json_store makes this one contradict the codebase too. Re-running publishes a second spec (C), and fixing it per ticket (D) means fixing it up to ten times.

2. Why read the spec back with gh issue view rather than in the chat that produced it?

D. The M06 discipline — observation before inference — applies to your own agent's work. What downstream skills and sessions will read is the issue body on GitHub, so that is the thing to audit.

3. The proposed seam is "unit-test the scheduler function." Why might you push back?

A. "Use the highest seam possible … existing seams should be preferred to new ones." A pure function is easy to test (B is backwards), the ADR says nothing of the sort (C), and the course has no such rule (D). The push-back is about leverage, not correctness: a seam at the command exercises every layer the tracer bullet touches.

Flashcards

Say the answer out loud before you flip. "Again" puts the card back in the queue; "Got it" retires it. Keyboard: Space flips, 1 again, 2 got it.

The only pause /to-spec gives you — and what to check there?
The seam question. Check: named in repo vocabulary, as few seams as possible, consistent with the ADRs.
Where do you read the spec back from, and why?
From GitHub (gh issue view) — the chat shows intent, the issue shows what was published.
The test for an Implementation Decision?
Can you point to the sentence in the conversation it came from? If not, it is invented: fix it or mark it open.
Why is a spec error more expensive than a ticket error?
It is upstream: one wrong decision in the spec becomes one wrong decision in every ticket /to-tickets derives.
How to fix a published spec — and how not to?
gh issue edit N --body-file. Not by re-running the skill, which publishes a second spec.
What should Out of Scope on the spec point at?
The neighbouring Seed backlog tickets (T07–T15), so decomposition does not re-invent them.
Ask your teacher

Paste the published spec body into a new Claude Code session — one with no memory of the design — and ask: "Which decisions in this spec would you have to guess the reasoning for?" A fresh session is the reader the spec is written for, and its confusion is the audit. Bring anything still unclear to the weekly meeting.
