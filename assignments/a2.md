## 1. Labels, types, and a template (M08)

Create three area labels, one per layer of the Seed Repo:

gh label create layer:cli     --color fbca04 --description "Touches src/flashcards/cli"
```

Commit `.github/ISSUE_TEMPLATE/ticket.md` to `main` with `name`, `about`, `labels:
needs-triage`, `type: Task`, and the four headings — Context, Acceptance criteria, Out of
scope, Blocked by — as prompts, **not** pre-filled criteria (the M08 page shows the file).

The checker verifies the three labels, the template on the default branch, and that
**every open issue** in the repository carries at least one label and an issue type — so
`gh issue list --search "no:label"` returns nothing. Do this item first; the skills in
items 3 and 4 apply `ready-for-agent`, which must exist (it does, from A1).

## 2. One ticket by hand (M07)

Before any skill writes tickets for you, write one: **due-date filtering** — the Seed
backlog's T05, "select only cards due today". Work from the one-line description in
`seed/SPEC.md` §6, not from the Seed Repo's issue #6 (compare afterwards). File it with
`gh issue create --body-file`, labelled `layer:domain` and `needs-triage`, typed `Task`.

All four sections. Every acceptance criterion must be a sentence a wrong implementation
would make false, and one must name the test file. Out of scope must name at least two
neighbouring tickets and state the stub behaviour until they land.

The checker finds it by the four headings and reports it; the rubric grades it.

## 3. A spec issue (M09)

Have a real design conversation with Claude Code in your Instance about **the review
loop** — a learner grades one card, it is rescheduled by SM-2, and the result is saved.
Then run `/to-spec`. Answer its seam question deliberately (the M09 pages say what to check).

The published issue must have the seven spec headings — Problem Statement, Solution, User
Stories, Implementation Decisions, Testing Decisions, Out of Scope, Further Notes — the
`ready-for-agent` label (the skill applies it), and the issue type **Feature** (you apply
it: `gh issue edit <n> --type Feature`). Out of Scope should name the Seed backlog tickets
that neighbour the review loop (tags, stats, CSV) so they are not re-decomposed.

Audit the body from `gh issue view`, not from the chat, before going on. Fix with
`gh issue edit --body-file`, not by re-running the skill.

## 4. Six to ten tickets with a real graph (M10, M11)

Run `/to-tickets #<spec>` with the spec's number as the argument. At the quiz step, check
every edge with "could this ticket be *started* without that one?" and every ticket

Then make the graph real on GitHub — the skill may or may not have done all of this:

- every ticket's `parent` is the spec (`gh issue edit N --parent <spec>` for any that is not)
- every Blocked-by line in a ticket body is a recorded dependency
  (`gh issue edit N --add-blocked-by A,B`)
- every ticket is typed `Task`, labelled `ready-for-agent` and at least one `layer:` label

Verify from the terminal:

```

Paste the `--mermaid` output into the **spec issue's body** under a `## Dependency graph`
heading, inside a ```` ```mermaid ```` fence, and confirm it renders in the browser.

The checker verifies: 6–10 open tickets that are sub-issues of the spec; each typed
`Task` with `ready-for-agent`; at least six `blockedBy` edges among them; at least one
ticket with two or more blockers; **no cycle** (GitHub accepts cycles — verified
2026-09-13 — so this is checked here); and a `mermaid` fence in the spec's body. The rubric
grades whether the slices are vertical and whether each edge is genuine.

## 5. Linear, connected and verified without touching (M12)

Do this **last**. Issues Sync copies only issues created after the link is made, so the
spec and tickets above will not appear — that is expected, and it is why the verification
creates a new issue.

Create a Free Linear workspace with one team, install the GitHub integration, and link
your Instance to the team with **two-way** GitHub Issues Sync (the M12 pages quote Linear's
steps). Then run the protocol entirely from `gh`:

```bash
gh issue create --title "Sync probe: created from gh on <date>" \
  --body "Filed from the terminal to verify Issues Sync. Close via gh; do not touch in Linear." \
  --label needs-triage --type Task
gh issue close <n> --reason completed
gh issue comment <n> --body "Comment from gh; should appear in Linear."
```

After each command, look at Linear and take a capture with the date and the Linear ID
(`KEY-n`) visible. Then the PR preview: copy the branch name from the synced issue in
Linear, reopen the probe issue, make a one-line change on that branch, open a PR with the
Linear ID in its title, watch the Linear status move to In Progress, and close the PR
unmerged (`gh pr close`) — merging properly is Week 3.

The checker verifies the GitHub side: an open-or-closed issue whose title begins
`Sync probe`, created after the spec, closed with reason `completed`, with at least one
comment; and, as a note, whether a closed unmerged PR exists whose title contains a
Linear-style ID. It cannot see Linear; the captures are graded by a human. **Do not
create, edit, or move anything in Linear by hand.** If the sync will not work, say so in
the write-up and complete the PR preview alone — see the M12 fallback.

`a2-writeup.md` at the root of your Instance, with:

3. **Linear.** The captures, embedded or linked, and a sentence stating what you touched
   by hand in Linear (the right answer is "nothing").

### Rubric

| | Excellent | Adequate | Not yet |
|---|---|---|---|
| **Ticket quality** (item 2, M07) | Every criterion falsifiable; the test named; out-of-scope fences the neighbours and states the stub | One vague criterion, or the test unnamed | Criteria that cannot fail; no out-of-scope |
| **Slicing** (item 4, M10) | Every ticket crosses the layers it needs and is demoable alone; none is a single layer | One horizontal ticket, or one too wide for a session | Layer-by-layer decomposition |

| **Judgment** (item 6) | Compares the two decompositions with a grounded verdict | Describes both without deciding | — |

A well-argued case that the Seed backlog's decomposition is *worse* than yours earns full
marks. The backlog is an exhibit, not a model answer.
