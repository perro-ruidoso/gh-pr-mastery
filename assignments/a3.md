# Assignment A3 — Two Tickets, One Stack, One Conflict

**Covers:** M13, M14, M15, M16, M17, M18
**Due:** before the Week 4 meeting
**Graded:** items 1–5's evidence by script (`checkers/check_a3.py`); the reviewability
judgement in item 2, the honesty of the PR bodies in item 3, the conflict explanation and
the skill choices in item 6 by a human against the rubric below.

Week 2 left your Instance with a spec and six to ten tickets carrying real blocking edges.
This week you take **two of them that share an edge** through branch → PR → merge, stack
the second on the first, retarget it when the first lands, and resolve the conflict that a
third ticket causes on the way. Every step leaves an artifact GitHub can show a grader, and
that is what the checker reads. The whole sequence was run on a throwaway Instance on
2026-09-13 and the Week 3 pages show every command's real output; yours will look the same
with different numbers.

Everything is done in `perro-ruidoso/flashcards-<your-handle>` from the terminal or from
Claude Code inside it. **You need `gh` 2.94.0 or later.**

---

## 1. Two branches from two tickets (M13)

Pick two tickets from your Week 2 backlog where the second is **blocked by** the first
(`gh issue view N --json blockedBy`). Call them A and B. Create A's branch from the issue:

```bash
gh issue develop <A> --checkout
```

The branch name starts with the issue number — that is what the checker reads, and what
`CLAUDE.md` in your Instance requires. Use `--name <A>-short-slug` if the default is
unwieldy. Do not create B's branch yet; it comes in item 4.

## 2. Ship A as a reviewable PR (M14, M15)

Have Claude Code implement ticket A on that branch — the ticket only. Before you open the
PR, read the diff as a reviewer would:

```bash
git diff --stat main...HEAD
git diff main...HEAD
```

One purpose, bounded size, no changes the ticket did not ask for. If a rename, a README
edit, or a "while I was in there" reformat crept in, take it out (or, if you want the
exercise on record, open the PR anyway, close it with a comment saying what you are
splitting out, and open a clean one — the checker looks for exactly that pair and the
M14 page shows it).

Open the PR with a body file, not `--fill`:

```bash
gh pr create --title "<what it does>" --body-file pr-a.md
```

The body has four headings — `## Intent`, `## Scope`, `## Verification`, `## Risk` — and
ends with `Closes #<A>`. Wait for CI. Then confirm the link took:

```bash
gh pr view --json closingIssuesReferences --jq '[.closingIssuesReferences[].number]'
```

(It is `[]` for the first second or two after creation; ask again.)

## 3. Merge A and watch the issue close itself (M15)

```bash
gh pr merge <PR-A> --squash
gh pr view <PR-A> --json mergedAt --jq .mergedAt
gh issue view <A> --json state,stateReason,closedAt
```

`closedAt` should be within a second or two of `mergedAt` and `stateReason` should be
`COMPLETED`. If you closed the issue by hand, that is what the checker will see.

**Do not pass `--delete-branch`** here if you have already stacked B on this branch (item 4
below explains why; the M16 pages show what happens).

## 4. Stack B on A, then retarget (M16)

You may do this before item 3 — that is the realistic order, and the pages do it that way.
Create B's branch **from A's branch**, so B's diff shows only B's work:

```bash
gh issue develop <B> --name <B>-short-slug --base <A-branch> --checkout
```

Implement B, push, and open its PR. `gh pr create` will pick A's branch as the base on its
own (the `--base` flag above recorded it in git config); check with
`gh pr view --json baseRefName`. Then look at the link:

```bash
gh pr view <PR-B> --json closingIssuesReferences
```

It is empty, and it will stay empty however long you wait, because `Closes #<B>` is
ignored on a PR that does not target the default branch. That is the point of this item.

Once A has merged, retarget:

```bash
gh pr edit <PR-B> --base main
gh pr view <PR-B> --json baseRefName,closingIssuesReferences,changedFiles
```

Now the link appears. So do A's changes, again, in B's diff — because A was squash-merged,
B's branch and `main` no longer share A's commits. Rebase B onto `main` and force-push
(`git rebase origin/main && git push --force-with-lease`); the diff shrinks back to B's
files. The checker reads the retarget from the PR's timeline (a base change onto `main`
after A merged) and checks that B's issue is blocked by A's.

## 5. Manufacture the conflict, and resolve it with the skill (M17)

Pick a third ticket C that is also unblocked once A has merged and touches something B
touches — the domain model is the usual overlap. Branch it from `main` with
`gh issue develop <C> --checkout`, implement it, open its PR, merge it. Now:

```bash
gh pr view <PR-B> --json mergeable,mergeStateStatus
```

Give GitHub half a minute; it reports `UNKNOWN` while it recomputes, then `CONFLICTING` /
`DIRTY`. On B's branch, `git fetch origin main && git merge origin/main` will stop with
`CONFLICT (content)`. Open Claude Code and run **`/resolving-merge-conflicts`**. Read what it
does at each of its five steps — especially step 2, where it goes to the commits, PRs, and
tickets behind each side before touching a hunk. It finishes by committing the merge. Push,
wait for CI, merge B. B's issue closes itself.

The checker looks for a **two-parent commit** on B's branch (the merge of `main`). If you
resolved by rebasing instead, there is no such commit; say so in the write-up and the
grader will read the branch.

## 6. Write-up (~300 words)

`a3-writeup.md` at the root of your Instance, on `main`:

1. **The conflict.** Which file and lines, which two tickets caused it, and *why* both
   tickets touched the same place — one sentence on what that says about the backlog's
   edges (should C have been blocked by B?).
2. **The drive-by.** What you found in your own diff when you read it as a reviewer, and
   what you did with it.
3. **Three situations, three skills** (M18). For each, name the skill and one sentence on
   why, using the installed descriptions from the M18 pages:
   - a feature too large to hold in one session, still foggy;
   - a session whose context is nearly full, with the work half done;
   - a repository where the agent must never be able to `git push`.

### Rubric

## Notes

- Merge with `--squash` throughout; the pages explain what that does to a stack and how
  the rebase fixes it. Your Week 5 ruleset will make squash the only option anyway.
- `gh pr merge --delete-branch` on a parent **closes** any PR stacked on it (verified
  2026-09-13; M16 page 3). Retarget first, delete after.
- The issue must close **itself**. If you `gh issue close` it, the timestamps will show it.
