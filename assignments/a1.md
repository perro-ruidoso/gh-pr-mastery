## 4. The triage labels actually exist

The mapping file names five labels. Create them for real, so the strings correspond to
something:

```bash
for L in needs-triage needs-info ready-for-agent ready-for-human wontfix; do
  gh label create "$L" --repo perro-ruidoso/flashcards-<your-handle> || true
done
```

`wontfix` will report that it already exists — it is in GitHub's default label set, which
every new repository receives (M05 explains why). The checker grades the four you create
and only notes that `wontfix` is present. Do not delete it: the mapping file names it.

## 6. Written analysis (~300 words)

Pick **one merged pull request** in the course repository `perro-ruidoso/gh-pr-mastery` and
answer three questions:

1. **What did it change?**
2. **What was it blocked by** — what had to land first, and how is that dependency recorded?
3. **How can you tell?** Every claim names the artifact supporting it.

Put it in `a1-writeup.md` at the root of your Instance.

The course repo is built the way this course teaches, so its history answers question 2
for real: some of its issues carry **recorded blocking relations**, not just prose saying
so. Start by listing what is there —

```bash
gh pr list --repo perro-ruidoso/gh-pr-mastery --state merged \
  --json number,title,mergedAt,headRefName
```

— then, for whichever issue your PR closed, ask GitHub what blocked it:

```bash
gh api repos/perro-ruidoso/gh-pr-mastery/issues/<n>/dependencies/blocked_by \
  --jq '.[] | "#\(.number) [\(.state)] \(.title)"'
```

That endpoint is the mechanism question 2 is asking about. Note it is **not** the same
feature as a sub-issue: a sub-issue is a hierarchy with one parent, so it cannot express a
ticket blocked by two others. Saying which mechanism recorded the dependency, and how you
checked, is worth more than naming the blocker.

An honest "nothing blocked this one, and here is the evidence for that" is a fine answer
if you picked such a PR.

### Rubric

| | Excellent | Adequate | Not yet |
|---|---|---|---|
| **Grounding** | Every claim names a specific artifact — a JSON field, an issue number, a timestamp, a thread | Most claims are grounded; one or two assert process not visible in the repo | Narrates what probably happened; the repository is barely cited |
| **Inference** | Distinguishes what the evidence proves from what it merely suggests; says so explicitly | Mostly careful, with an over-read field or two | Treats one field as proof of something it does not show |
| **Dependency reading** | Identifies the blocking relationship and the mechanism recording it | Identifies that something came first, vaguely | Dependency not addressed |
| **Judgment** | Offers a defensible opinion about the process, grounded in artifacts | Describes without evaluating | — |

A well-argued **criticism** of the course repository's own process earns full marks. The
repository is an exhibit, not a model answer.
