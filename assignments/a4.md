# Assignment A4 — Review Your Peer's PR, Answer Review on Yours

**Covers:** M19, M20, M21, M22, M23, M24
**Due:** before the Week 5 meeting
**Paired:** the instructor publishes the pairing before the Week 4 meeting. You are the
*author* on your own Instance and the *reviewer* on your peer's.
**Graded:** items 1, 2, 4, 5, and 6 by script (`checkers/check_a4.py --handle you --peer them`,
run in both directions); the quality of your comments (item 2, M22), your classification
of `/code-review`'s findings (item 3, M21), your replies and what you chose to resolve
(item 4, M23), and the out-of-scope call (item 5, M24) by a human against the rubric below.

Week 3 ended with pull requests that closed their tickets. This week the pull request has a
conversation in it. A prepared PR with three planted defects — and a green test suite — is
opened on your Instance by you; your peer reviews it with the terminal and with
`/code-review`; you answer through Claude Code; and both of you file, rather than fix, what
the review turned up outside the PR. The whole sequence was run on a throwaway Instance on
2026-09-14 and the Week 4 pages show every command's real output. One thing the pages could
not show, because the course account was the only human there: the re-request and the second
review. Your pair can.

Everything is done in `perro-ruidoso/flashcards-<your-handle>` (author seat) and in a clone
of `perro-ruidoso/flashcards-<peer-handle>` (reviewer seat). **You need `gh` 2.94.0 or
later**, and the vendored `qa` skill installed (`skills/README.md`, one `curl`).

## 1. Open the drill PR on your own Instance (author)

From a clone of the course repo:

```bash
python seed/tools/plant_review_pr.py --repo perro-ruidoso/flashcards-<your-handle>
```

It files the SM-2 scheduler ticket, creates a branch from it with `gh issue develop`, adds
`scheduler.py` and its tests, and opens a PR that `Closes` the ticket — as **you**. The PR is
the exhibit; do not read the diff for defects yet, and do not touch the branch. If the script
refuses because your Instance already has `src/flashcards/domain/scheduler.py`, tell the
instructor; the guide has the variant for that case.

Then send your peer the PR URL. Confirm with:

```bash
gh pr view <N> --json author,closingIssuesReferences,files --jq '{author: .author.login, closes: [.closingIssuesReferences[].number], files: [.files[].path]}'
```

The author is you; two files; the ticket linked.

## 2. Review your peer's PR from the terminal (reviewer — M19, M22)

In a clone of your peer's Instance, on their drill branch. First, one Conversation comment
saying what you are about to do:

```bash
gh pr comment <N> --body "..."
```

Then read the diff against the specification it claims to implement —
`docs/adr/0001-sm2-rounding-and-the-clock.md` and the ticket — and write a **batched
review** as a JSON file: a summary `body`, `event: "REQUEST_CHANGES"`, and a `comments`
array. Each comment: `path`, `line`, `side`, `body`. Each body: first word **must-fix** or
**nit**; the rule quoted (ADR sentence, `CONTEXT.md` entry, ticket criterion) or a
reproduced value; the fix. At least one comment carries a ` ```suggestion ` block. Submit:

```bash
gh api -X POST repos/perro-ruidoso/flashcards-<peer>/pulls/<N>/reviews --input review.json
gh pr view <N> --json reviewDecision --jq .reviewDecision      # CHANGES_REQUESTED
```

You are not the author, so the verdict is accepted. (Try `gh pr review --approve` on your
**own** PR once, to see the refusal.) The M19 and M22 pages have the JSON shape and the two
422s you may meet on the way.

## 3. Run `/code-review` and classify (reviewer — M21)

In the same clone, in Claude Code, with the drill branch checked out:

> Review branch `<N>-sm2-scheduler` since `main`.

Make sure the skill that ran is the two-axis one (`## Standards` / `## Spec` headings, not a
severity-tagged list — M21 page 1 says how to tell). Paste both reports **unedited** into
`a4-writeup.md` at the root of **your own** Instance, on `main`, under those two headings.
Below them, a table with one row per finding: the finding, your verdict (**must-fix**,
**nit**, **false positive**; or *duplicate* / *pass* where that is what it is), and for every
must-fix the ADR or ticket sentence it violates. Before any verdict, run whatever the
reports claim that can be run — a value, a failing test, a count — and say what came out.

Your comments in item 2 may be written before or after this; either order is defensible,
and the rubric asks which you chose and why.

## 4. Answer review on your own PR (author — M23, M20)

When your peer's review lands:

```bash
gh api repos/perro-ruidoso/flashcards-<you>/pulls/<N>/comments --jq '.[] | "\(.id)  \(.path):\(.line)  \(.body[0:60])"'
```

Direct Claude Code — in a session inside your clone, on the drill branch — to read every
inline thread, fix what each asks (keeping the ticket's intent), run `pytest`, `ruff check .`,
`ruff format --check .`, and `mypy`, commit with a message naming what each change answers,
and push. Then, for each thread, reply **in the thread** with the fixing commit's SHA and one
checkable fact:

```bash
gh api -X POST repos/perro-ruidoso/flashcards-<you>/pulls/<N>/comments/<id>/replies -f body="Fixed in <sha>: ..."
```

Resolve the threads you addressed (GraphQL `resolveReviewThread`, thread ids from the
`reviewThreads` query on M20 page 1); leave any you declined open with your reason in them.
Then — **after** the push — re-request review:

```bash
gh pr edit <N> --add-reviewer <peer>
gh pr view <N> --json reviewRequests,reviewDecision
```

The peer is listed; `reviewDecision` is still `CHANGES_REQUESTED`, and will be until your
peer reviews again. When they approve, merge with `--squash`; the ticket closes itself.

## 5. File what review uncovered, out of scope (author — M24)

Something in the review — a thread, a `/code-review` finding you classified as real but out
of the ticket's scope, something you noticed while fixing — belongs to a different ticket.
Do **not** commit it to the drill branch. In Claude Code, inside your Instance:

> /qa — <what happened, what you expected, steps, whether it is consistent>. Do not touch PR <N>.

Let it file. Read the issue(s) back:

```bash
gh issue view <M> --json labels,issueType,body
gh pr view <N> --json files,closingIssuesReferences
```

The body has the skill's shape (What happened / What's wrong, What I expected, Steps to
reproduce); the labels and type are empty — that is the skill, not you; the PR's files and
closing link are unchanged.

## 6. Second review (reviewer — M20)

When your peer re-requests, review again from the terminal. If every must-fix is fixed:
`gh pr review <N> --approve --body "..."`. If not: another `REQUEST_CHANGES` with the
threads that remain. Either way, read `reviewDecision` before and after and note the change
in `a4-writeup.md`'s last line.

### Rubric

| | Excellent | Adequate | Not yet |
|---|---|---|---|
| **Comments** (item 2, M22) | Every comment located on the line, quoting the rule or a value, with the fix, severity first; the author replied with SHAs and no questions | Located and marked; one comment made the author ask what was meant | Conversation-tab comments about lines, or unsourced "this is wrong" |
| **Findings to verdicts** (item 3, M21) | Every finding classified with its source sentence; at least one claim reproduced and its result stated; a false positive or duplicate named with the reason | All findings classified; sources named for the must-fixes; nothing reproduced | Reports pasted with no verdicts, or the agent's summary repeated as the classification |
| **Answering review** (item 4, M23) | Each thread has a reply naming the fixing commit and one checkable fact; only addressed threads resolved; declined threads left open with a reason; re-request after the push | Replies present but "done"-shaped; everything resolved including a declined one | A Conversation comment "addressed all feedback"; threads unreplied; re-request before the push |
| **Out of scope** (item 5, M24) | The filed issue is genuinely outside the ticket, durable (no paths, domain words, steps), and the PR's file set is unchanged | Filed, but the body cites a file or lacks steps | The out-of-scope fix landed in the PR, or nothing was filed |
| **Verdict discipline** (items 2 and 6, M19/M20) | Marks and verdict agree both times; the second verdict follows a real re-read | Approved with an open must-fix, or requested changes with only nits | No second review |

## Running the checker yourself

```bash
python checkers/check_a4.py --org perro-ruidoso --handle <you> --peer <peer>
```

One line per check. `note` lines are for the human grader. It reads: the drill PR (touches
`scheduler.py`, authored by you); a review by your peer with a verdict; their inline comments
(2+) and a suggestion block; at least one resolved thread; a commit after their verdict; a
`review_requested` event for them after your last commit; issues with `/qa`'s headings filed
after the PR opened; the PR's file set still the drill's two files and not closing those
issues; and `a4-writeup.md` on your Instance with `## Standards`, `## Spec`, and the three
verdict words. Run against the course's single-identity throwaway on 2026-09-14 it failed on
exactly the rules one person cannot satisfy alone — the peer's verdict with inline comments,
and the re-request — which is why this assignment is paired.

## Notes

- The drill PR must be **authored by you**. GitHub refuses an author's own `APPROVE` and
  `REQUEST_CHANGES` ("Review Can not approve your own pull request", verified 2026-09-14), so
  an instructor-opened PR would leave your peer as the only one who could review it and you
  unable to answer as the author.
- A push does **not** clear `CHANGES_REQUESTED`. Neither does resolving threads. Only your
  peer's next review moves `reviewDecision`. Re-request, then wait.
- Re-request **after** the push; the checker compares the `review_requested` timestamp with
  your last commit's, and a request that predates the commit does not count.
- `/qa` applies no labels and no type. The checker notes what it finds; triage is Week 6.
- Everything on your Instance is public; your peer needs no collaborator invitation to
  review, but requesting a review from them needs *you* to have write access — you do.
